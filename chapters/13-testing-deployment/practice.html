本页目录

场景：让每次合并都有证据 ​

团队最常见的诉求是：PR 合并到主干前，自动完成安装、类型检查、构建、E2E；合并后产物可部署到 preview 环境。流水线本身也是文档——新人读一遍 YAML 就知道项目的质量门禁有哪些。

::: steps

  1. 用 pnpm 官方 action 固定包管理器版本
  2. setup-node 开启 pnpm store 缓存，安装走 --frozen-lockfile
  3. 类型检查 + lint，把问题挡在构建之前
  4. 缓存 .next/cache，让 16.4 的构建磁盘缓存跨流水线生效
  5. next build 构建，随后用 Playwright 官方 action 装浏览器并跑 E2E
  6. 产物（含 standalone）归档为构建产物，供部署作业消费 :::

可直接落地的 GitHub Actions ​

yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    env:
      # CI 用占位值即可：NEXT_PUBLIC 变量在构建期内联，必须提供
      NEXT_PUBLIC_API_BASE: https://api.preview.example.com
      SESSION_SECRET: ci-placeholder-secret-not-used-in-prod
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 11 # 与 packageManager 字段对齐

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm # 自动缓存 pnpm store

      - name: 安装依赖
        run: pnpm install --frozen-lockfile # 锁文件不一致立即失败

      - name: 类型检查与 lint
        run: |
          pnpm typecheck
          pnpm lint

      - name: 缓存 Next.js 构建磁盘缓存
        uses: actions/cache@v4
        with:
          path: ${{ github.workspace }}/.next/cache
          # 依赖与源码共同决定缓存键
          key: ${{ runner.os }}-nextjs-${{ hashFiles('pnpm-lock.yaml') }}-${{ hashFiles('**/*.{ts,tsx}') }}
          restore-keys: ${{ runner.os }}-nextjs-${{ hashFiles('pnpm-lock.yaml') }}-

      - name: 构建
        run: pnpm build

      - name: 安装 Playwright 浏览器
        run: pnpm exec playwright install --with-deps

      - name: 运行 E2E（webServer 会自动 build+start，可按需要改为复用产物）
        run: pnpm exec playwright test

TIP

缓存键里带源码哈希意味着每次提交都可能生成新键，restore-keys 的前缀回退保证“源码变了但依赖没变”时仍能命中依赖层缓存。Playwright 浏览器也可以用 actions/cache 按版本号缓存，进一步压缩流水线时间。

E2E 覆盖哪些路径 ​

E2E 昂贵且脆弱，只守“断了会出事故”的关键路径。以本教程的全栈应用为例，建议首批固化四条：

  1. 未登录访问 /dashboard 被重定向到登录页
  2. 登录 → 创建待办 → 列表即时出现（乐观更新）→ 刷新仍存在
  3. 关键列表 → 详情的即时导航用 instant() 断言外壳立即可见
  4. 越权调用删除接口返回 403（第 11 章的归属校验）

👉 第 2、4 条可以直接对着 server-action-todo 全栈实验 的流程先在本地写用例，再搬回仓库；鉴权重定向与 API 状态码可参考 route-handlers-proxy 全栈实验。

E2E 在合并前跑；部署完成后还应有一层更轻的冒烟检查，直接在部署作业里执行：

bash
set -euo pipefail
BASE="${1:?用法: smoke.sh https://preview-url}"

[ "$(curl -s -o /dev/null -w '%{http_code}' "$BASE/api/health")" = "200" ]
# 不跟随重定向：未登录访问受保护区必须得到 307，而不是 200
[ "$(curl -s -o /dev/null -w '%{http_code}' "$BASE/dashboard")" = "307" ]
echo "smoke passed: $BASE"

上线前 15 项检查 ​

  • [ ] 主干为绿：--frozen-lockfile 安装、typecheck、lint、build、E2E 全通过
  • [ ] .env.production 变量逐个评审：无密钥误用 NEXT_PUBLIC_，.env* 未入库
  • [ ] 多实例部署已设置 NEXT_SERVER_ACTIONS_ENCRYPTION_KEY，缓存后端（Redis 等）连通
  • [ ] SESSION_SECRET 等密钥来自平台密钥管理，不写在镜像里
  • [ ] Cookie 在生产带 secure；会话五属性齐备（第 11 章清单）
  • [ ] 关键路由 error.tsx、global-error.tsx、not-found.tsx 已配置且不泄露堆栈
  • [ ] 图片远程域名白名单（remotePatterns）只含真实域名，未用通配兜底
  • [ ] metadata、Open Graph、sitemap、robots 已在生产域名验证（第 10 章）
  • [ ] 第三方脚本全部经 next/script 且策略评审；CSP 头已在预览环境验证不拦资源
  • [ ] Web Vitals 字段上报指向生产分析端点，看板按路由可分
  • [ ] onRequestError 与 OTel exporter 指向生产后端，手动制造一次 500 验证链路
  • [ ] 生产构建用 next start 或 standalone 验证启动；健康检查路径返回 200
  • [ ] CDN 保留 RSC 头、_rsc 入缓存键；on-demand 失效配套 purge 已演练
  • [ ] 回滚方案明确：保留上一版本镜像/构建产物，数据库迁移可逆
  • [ ] 值班与告警就绪：错误率、p75 LCP/INP、缓存命中率有阈值告警

小结 ​

  • 流水线 = pnpm 固定版本 + frozen-lockfile + 静态检查 + .next/cache 缓存 + 生产构建 + Playwright
  • E2E 只守四条关键路径，包含一条 instant() 即时导航断言与一条越权断言
  • 上线靠 15 项清单把关，故障靠排查表按症状定位；回滚路径在上线前就要验证
