先选层：Next 16.3 的测试金字塔 ​

不是所有代码都配一种测试。官方测试指南把测试分为五类，对应到 App Router 项目，推荐的投入比例如下：

层级工具测什么速度/成本
单元测试Vitest纯函数、schema 校验、工具方法极快、大量
组件测试Vitest + Testing Library（jsdom）同步客户端组件的交互与渲染快
集成测试Vitest / Playwright多模块协作、Action + 数据层中
E2E 测试Playwright真实浏览器中的用户关键路径慢、少量但关键
快照测试Vitest稳定展示组件的输出回归辅助

::: warn async 服务端组件是 React 生态的新形态，Vitest 目前不支持直接渲染它们。官方明确建议：异步服务端组件用 E2E 覆盖，Vitest 只测同步组件与可抽出的纯逻辑（例如把取数与鉴权逻辑抽成纯函数后单测）。 :::

初始化两条工具链：

bash
pnpm add -D vitest @vitejs/plugin-react jsdom @testing-library/react @testing-library/dom vite-tsconfig-paths
pnpm create playwright   # 生成 playwright.config.ts 与浏览器依赖

Playwright 最小用例 ​

E2E 应跑在生产构建上，行为才接近真实用户。推荐让 Playwright 的 webServer 自动拉起服务，而不是手工开两个终端：

ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  use: { baseURL: 'http://localhost:3000' }, // 用例里可直接 page.goto('/about')
  webServer: {
    command: 'pnpm build && pnpm start', // 对生产产物测试
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
  projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],
});

为即时导航写保险：instant() ​

第 6 章的即时导航有个测试难题：数据最终总会到达，普通断言无法区分“点击瞬间就有外壳”还是“白屏等了 800ms 才一起出来”。@next/playwright（pnpm add -D @next/playwright @playwright/test）提供的 instant() 辅助函数在回调期间按住动态内容，让断言只针对“点击那一刻立即可用的 UI”：

ts
import { test, expect } from '@playwright/test';
import { instant } from '@next/playwright';

test.describe('商品详情 /store/[slug]', () => {
  test('直接打开时静态外壳即时可见', async ({ page, baseURL }) => {
    await instant(
      page,
      async () => {
        await page.goto('/store/hats');
        // 外壳内的商品名立即可见
        await expect(page.locator('h1')).toContainText('Baseball Cap');
        // 动态库存此时被按住，不应出现
        await expect(page.getByText('In stock')).toHaveCount(0);
      },
      { baseURL },
    );
    // 回调结束后动态内容流出
    await expect(page.getByText('In stock')).toBeVisible();
  });
});

同一条路由要分别验证两种到达方式：page.goto() 对应直访的静态外壳；点击 <Link> 对应客户端导航的预取外壳。一个 Suspense 边界可能只覆盖其中一种——这正是 instant() 能抓到、人肉很难发现的回归。

::: warn instant() 依赖 DevTools 的测试 Cookie 冻结动态内容。官方已知问题：Cookie 按域名而非端口隔离，本机同时跑多个项目（都在 localhost）会互相干扰，切换项目时清理该 Cookie 即可。 :::

服务端可观测钩子：instrumentation.ts ​

测试证明“功能对”，可观测回答“线上好不好”。在项目根（用了 src/ 就放 src/ 内）建 instrumentation.ts，它导出两个可选钩子：

ts
import type { Instrumentation } from 'next';

// 服务器实例启动时执行一次，且必须在开始接请求前完成
export function register() {
  // 进阶篇在这里接 OpenTelemetry
  console.log('[instrumentation] server starting');
}

// 捕获服务端错误：渲染、Route Handler、Action、proxy 均会进入
export const onRequestError: Instrumentation['onRequestError'] = async (
  err,
  request,
  context,
) => {
  const message = err instanceof Error ? err.message : String(err);
  const digest =
    typeof err === 'object' && err !== null && 'digest' in err
      ? String((err as { digest?: unknown }).digest)
      : undefined;

  await fetch('https://report.example.com/error', {
    method: 'POST',
    body: JSON.stringify({ message, digest, path: request.path, context }),
  });
};

context.routeType 会告诉你错误来自 'render'、'route'、'action' 还是 'proxy'，分流告警时非常有用。异步任务必须 await，否则进程可能在上报完成前结束。

INFO

React 渲染中抛出的错误可能被加工过，原始类型未必保留。用 digest 字段识别错误种类，不要假设 err instanceof MyError 一定成立。

常见误区 ​

  • 用 Vitest 硬渲染 async 服务端组件：当前不支持，抽纯逻辑单测 + E2E 覆盖组件
  • E2E 只对 dev server 跑：dev 无压缩、无生产缓存，测出来的时序没有意义
  • 用 CSS class 当主定位器：样式重构即全红；语义定位器更稳
  • onRequestError 里发上报却不 await：日志间歇性丢失
  • 给所有页面堆 E2E：慢且脆；E2E 只守关键路径，数量交给单元层

小结 ​

  • 金字塔：Vitest 测纯逻辑与同步组件，Playwright 守关键用户路径，async 服务端组件归 E2E
  • instant() 专门冻结动态内容，把“即时外壳”变成 CI 里可回归的断言
  • instrumentation.ts 的 register/onRequestError 是服务端启动与错误上报的统一入口
