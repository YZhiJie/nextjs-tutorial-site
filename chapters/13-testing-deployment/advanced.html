OpenTelemetry：从“报错了”到“哪一跳慢” ​

生产事故的高频问题不是“有没有错误”，而是“哪个环节拖垮了整条链路”。Next.js 内置 OpenTelemetry 埋点，框架自身的渲染、取数、缓存调用会自动产生 span，你只需注册一个 exporter。官方脚手架包 @vercel/otel 把样板压到最小：

bash
pnpm add @vercel/otel @opentelemetry/sdk-logs @opentelemetry/api-logs @opentelemetry/instrumentation
1
ts
import { registerOTel } from '@vercel/otel';

export function register() {
  registerOTel({ serviceName: 'saas-web' }); // 追踪后端按服务名聚合
}

export { onRequestError } from './observability/on-request-error'; // 错误上报沿用基础篇模式

之后在 Jaeger、Tempo、Datadog 等兼容后端里，一次慢请求会呈现为一条 trace：proxy → RSC 渲染 → DAL 查询 → 'use cache' 命中与否。链路追踪和 onRequestError 是互补的：trace 回答时序，错误钩子回答异常。

TIP

instrumentation.ts 放在项目根或 src/ 根，与 app/ 平级，不要放进 app/ 目录。它在服务器实例启动时执行一次，异步 register 会在接请求前被 await。

Instant Insights：让框架替你做导航体检 ​

开启 cacheComponents 后，dev 默认对每个 Page/Default 段做即时导航校验（validationLevel: 'warning'）。它会精确指出三类问题：哪种导航会阻塞、哪里缺 Suspense 边界、哪块数据未缓存就到达用户。同一个页面的直访与客户端导航会被分别校验——这正是人工走查最容易漏的。

需要收紧为“只校验显式声明的段”时调整配置：

ts
const nextConfig: NextConfig = {
  cacheComponents: true,
  experimental: {
    instantInsights: {
      validationLevel: 'manual-warning', // 默认 'warning'（全量校验）
    },
  },
};

::: warn Instant Insights 是开发期工具，它能证明“外壳存在且结构正确”，但不能判断“外壳里是不是正确的内容”。内容层面的回归仍靠第 13.1 篇的 instant() E2E。 :::

16.4 新增：让智能体替你升级框架 ​

框架升级是典型的「步骤繁琐但路径固定」的工作——正是编码智能体的甜区。16.4 把升级链路原生接到智能体上：

bash
npx next@canary upgrade --agent
1

--agent 会检查当前版本、选定目标版本，准备好迁移指南、所需 codemod 与验证步骤交给智能体执行：应用更新、解决迁移问题、确认应用仍能工作。另有 experimental.agentUpgrade 让框架在日常 dev/build 时主动提醒升级：

ts
const nextConfig: NextConfig = {
  experimental: {
    agentUpgrade: 'security', // 默认：仅提醒修复已知漏洞的升级
    // 'latest'：有新 major/minor 就提醒；false：关闭提醒
  },
};

配套的 experimental.agentFeedback: true 允许智能体把遇到的框架错误、文档不清等问题整理成草稿报告，经你审阅后反馈给 Next.js 团队。生产环境的纪律不变：智能体只负责准备与验证，合并与发布仍走你的 CI 与回滚预案。

自托管：三种产物形态 ​

方式产物适用
next build + next start需 Node 环境的完整服务虚拟机、PM2、单实例起步
output: 'standalone'仅含必要运行时文件的最小目录Docker 最小镜像、容器平台
output: 'export'纯静态 HTML/JS/CSS纯静态站；不支持 proxy、ISR、部分预取

容器化首选 standalone。构建后产物在 .next/standalone，官方 with-docker 示例给出了多阶段 Dockerfile：deps 层安装 → builder 层构建 → runner 层只拷贝 standalone 与静态资源，镜像体积与攻击面都显著缩小。

ts
const nextConfig: NextConfig = {
  output: 'standalone',
};
1
2
3

自托管还有三个必须知道的事实：

  1. 前置反向代理：官方建议用 nginx 等挡在 Next 之前，处理畸形请求、慢连接、限流与体积上限，让 Next 专注渲染
  2. 多实例缓存不共享：默认缓存写各实例本地磁盘。K8s 多 Pod 下要用 cacheHandlers（'use cache'）或 cacheHandler（ISR/页面缓存）接 Redis/S3，并把 cacheMaxMemorySize 设为 0，否则用户会在不同 Pod 间看到不一致的新旧数据
  3. 多实例 Action 密钥：不同镜像若产生不同加密密钥，闭包 Action 会跨实例失效，用 NEXT_SERVER_ACTIONS_ENCRYPTION_KEY 统一（第 11 章）

Build Adapters：正在成形的部署抽象 ​

16.4 的 API 文档中包含 Build Adapters 章节，定位是让平台方把 Next 的构建/运行模型对接到特定基础设施（如 Node 以外的 Serverless 运行时）。当前仍处于 alpha：API 与输出契约会变化，适合平台工程师评估，业务项目不应把生产链路押在上面。现阶段自托管生产仍以 next start 与 standalone 为准。

环境变量：构建期内联 vs 运行期读取 ​

这是自托管最常踩的坑。两类变量的行为完全不同：

变量读取时机可见范围换环境怎么办
NEXT_PUBLIC_*构建时内联进 JS bundle任何人（公开）必须重新构建
普通变量服务端运行时读取 process.env仅服务端同一镜像注入不同值即可

所以“一个镜像 promotion 过 dev/staging/prod”的前提是：所有随环境变化的配置都走普通变量，并在动态渲染中读取。静态生成时读取的值在构建期就被固化了；显式 await connection() 可让组件进入请求时渲染，从而读到运行期环境：

tsx
import { connection } from 'next/server';

export default async function Page() {
  await connection(); // 等待真实请求：此后 process.env 按运行环境求值
  const apiBase = process.env.INTERNAL_API_BASE; // 无 NEXT_PUBLIC，不进客户端
  const res = await fetch(`${apiBase}/health`);
  // ...
}

.env* 文件由 Next 自动加载（使用 src/ 时文件仍放项目根，不在 src/ 内）。需要在 ORM 配置、测试脚本等框架外读取时，用 @next/env 的 loadEnvConfig(process.cwd())。所有 .env* 必须在 .gitignore 中。

DANGER

把“按环境变化的值”误加 NEXT_PUBLIC_ 前缀，会逼你为每个环境单独构建，且密钥直接出现在客户端 JS 里。给环境变量做评审时，先问一句：这个值换环境会变吗？会变就不能 public。

CI 缓存的原理（YAML 在实战篇） ​

next build 把可复用结果写进 .next/cache；16.4 默认开启的构建磁盘缓存就在这里。CI 不持久化这个目录，每次都是冷构建，还可能看到 “No Cache Detected” 提示。缓存键要同时考虑依赖锁文件与源码：依赖变了全量失效，只改源码时允许回退到上一份依赖缓存。pnpm 还需额外缓存其 content store（Linux 上默认 ~/.local/share/pnpm/store）。

小结 ​

  • OpenTelemetry 经 register() 注册即拿到框架级 span；Instant Insights 做结构体检，instant() 做内容回归
  • 生产自托管走 next start 或 standalone；多实例必须解决缓存共享与 Action 密钥；Build Adapters 仍是 alpha
  • NEXT_PUBLIC_ 构建期内联且公开；环境相关配置走普通变量 + 动态渲染读取，实现单镜像多环境
  • CI 持久化 .next/cache 与 pnpm store，冷构建不享受 16.4 磁盘缓存
