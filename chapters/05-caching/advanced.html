自定义寿命：预设之外的精确控制 ​

七档预设覆盖 80% 场景，剩余 20% 有两条定制路径。

在 next.config.ts 中注册可复用 profile，全应用按名字引用，类型与自动补全由 next typegen 生成：

ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  cacheComponents: true,
  cacheLife: {
    // 编辑部内容：客户端 10 分钟内不问服务器，服务端 1 小时后台刷新，1 天彻底过期
    editorial: { stale: 600, revalidate: 3600, expire: 86400 },
  },
};

export default nextConfig;

一次性需求直接传内联对象，仅作用于当前作用域；省略的字段继承 default：

ts
import { cacheLife } from 'next/cache';

export async function getFlashSale() {
  'use cache';
  cacheLife({
    stale: 60, // 客户端最多用 1 分钟旧价
    revalidate: 300, // 服务端 5 分钟后台刷新
    expire: 3600, // 1 小时彻底过期
  });
  return promotionService.current();
}

也可以按数据走不同分支：未发布的文章 cacheLife('minutes') 短缓存减压，已发布文章 cacheLife('days')。一次函数执行中只允许一条 cacheLife 实际生效，分支互斥即可。

三档时间如何决定缓存去向 ​

时间控制的位置设太短的后果
stale浏览器/客户端缓存低于 30s 不进预渲染；预取链接可能“点之前就过期”
revalidate服务端后台刷新为 0 时成为动态洞，被排除出预渲染
expire无流量后的最终寿命低于 5 分钟不进预渲染；过期后下一个请求同步等待

expire 必须大于 revalidate，配置非法会构建报错。客户端 stale 有 30 秒下限，是框架为预取可用性做的强制保护。

::: warn 嵌套缓存的寿命传播 外层缓存显式声明 cacheLife 时，一律以外层为准（无论内外谁长谁短）。外层不声明时，内层更短的寿命会把外层 default 一起拉短；若内层是短寿命缓存，构建直接报错防止误配。结论：嵌套链路上每一层都写清楚寿命。 :::

三种失效函数怎么选 ​

写操作后让缓存更新，16.x 提供三个函数，语义差异必须分清：

函数可用位置行为适用
updateTag(tag)仅 Server Actions立即过期，下一次读取等新数据用户读己之写（发帖、改资料后立刻看到）
revalidateTag(tag, profile?)Server Actions / Route Handlersstale-while-revalidate：先给旧内容，后台刷新Webhook、CMS 改稿，允许短暂延迟
revalidatePath(path)Server Actions / Route Handlers失效该路径下全部缓存不知道标签、整页兜底失效
ts
'use server';

import { updateTag } from 'next/cache';
import { redirect } from 'next/navigation';
import { db } from '@/lib/db';

export async function createPost(formData: FormData) {
  const post = await db.post.create({
    data: {
      title: String(formData.get('title') ?? ''),
      content: String(formData.get('content') ?? ''),
    },
  });

  // 列表与新详情都立即过期，redirect 后用户看到的就是新内容
  updateTag('posts');
  updateTag(`post-${post.id}`);
  redirect(`/posts/${post.id}`);
}

DANGER

在 Route Handler 里调用 updateTag 会直接抛错——它只能在 Server Action 内使用。反过来，Server Action 中需要“用户立刻看到”的场景也不要用 revalidateTag，那仍可能先返回一屏旧数据。

revalidatePath 是“宁可多失效”的粗粒度工具；标签失效更精准、风暴更小。实践上优先标签：集合标签（posts）+ 条目标签（post-42）成对设计。

缓存组件中的运行时数据 ​

cookies()、headers()、searchParams、未由 generateStaticParams 覆盖的 params 都是请求时才存在的数据，不能直接出现在缓存组件里。标准模式是“外层不缓存、先读取、再以参数下发给缓存组件”：

tsx
import { Suspense } from 'react';
import { cookies } from 'next/headers';
import { UserDashboard } from '@/components/user-dashboard';

export default function ProfilePage() {
  return (
    <Suspense fallback={<p>加载个人面板…</p>}>
      <ProfileContent />
    </Suspense>
  );
}

async function ProfileContent() { // 不缓存：读取请求级 cookie
  const sessionId = (await cookies()).get('session')?.value;
  return <UserDashboard sessionId={sessionId} />;
}

接收方 UserDashboard 是普通的 'use cache' 异步组件：入参 sessionId 自动参与缓存键，cacheLife('minutes') 声明寿命——不同会话各持有一条独立缓存，互不可见。

还有两个专用变体：'use cache: private' 允许函数内部直接读 cookie/header，但结果只存浏览器（不进共享服务端缓存）；'use cache: remote' 把结果写入持久化的远端缓存处理器，适合高命中率、多实例/Serverless 场景——默认的内存缓存在 Serverless 实例间不共享、生命周期短。

TIP

想把异步访问尽量压深、扩大静态外壳，就把 params Promise 整体下发到 Suspense 内的子组件再 await，而不是在布局顶层解构。外壳越大，即时导航的空间越大（第 6 章主题）。

没开 cacheComponents：旧模型指引 ​

存量项目尚未开启 cacheComponents 时，缓存走的是另一套 API，别把两套混用：

ts
// ① fetch 选项（仍然有效）
await fetch('https://api/posts', {
  cache: 'force-cache',
  next: { revalidate: 3600, tags: ['posts'] },
});

// ② 非 fetch 数据用 unstable_cache 包装
import { unstable_cache } from 'next/cache';

export const getCachedUser = unstable_cache(
  async (id: string) => db.user.findUnique({ where: { id } }),
  ['user'], // 缓存键前缀
  { revalidate: 3600, tags: ['user'] }
);

// ③ 路由段配置：页面/布局/route 中导出
export const revalidate = 3600; // 整段 ISR 秒数
export const dynamic = 'force-dynamic'; // 或强制每请求动态

旧模型中失效函数仍是 revalidateTag / revalidatePath（无 updateTag）。官方提供了迁移指南（migrating-to-cache-components），建议按路由逐个切换而不是全站一次性翻转；两套模型在同一应用的不同路由上可以并存。

小结 ​

  • cacheLife 支持配置级自定义 profile 与函数级内联对象，expire 必须大于 revalidate
  • 嵌套缓存显式寿命优先；短寿命缓存会变成动态洞并被排除出预渲染
  • updateTag 限 Action、立即过期；revalidateTag 支持 SWR 与 Webhook；revalidatePath 兜底粗粒度
  • 运行时数据先在外层读取再以参数进入缓存组件，必要时用 private/remote 变体
  • 旧模型（fetch 选项 + unstable_cache + 段配置）仍可用，按路由渐进迁移
