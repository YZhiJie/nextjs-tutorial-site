三个动作与一张反向索引 ​

基础篇学会了在 'use cache' 作用域里写 cacheTag，进阶篇在 updateTag / revalidateTag / revalidatePath 之间做了选型。把这三个 API 放回一张图上看，所谓标签失效，其实是三个动作围绕一张数据结构展开：

  1. 存档（use cache）：把函数结果按参数存档，相同参数的后续调用直接取档，参数变了就是一条新档
  2. 贴标签（cacheTag）：给存档挂一个或多个逻辑标签，一条档可以同时挂在「集合」与「单条」之下
  3. 撕毁（updateTag / revalidateTag）：按标签批量作废，被撕毁的条目在下一次读取时回源重建

核心数据结构是一张反向索引：tag → keys。正表回答「这个 key 存了什么」，反向索引回答「这个 tag 名下挂着哪些 key」——失效之所以能只扫相关条目而不是全库扫描，全靠这张索引。

text
写入侧（生产者）                          失效侧（触发者）
remember(k1, v, ['users', 'profile'])
remember(k2, v, ['users'])
  store:    k1→v, k2→v
  tagIndex: users   → {k1, k2}    expireTag('users')
            profile → {k1}          │ 查反向索引得 {k1, k2}
                                    ▼ 逐个 store.delete(k)

完整实现：约 70 行的迷你 tag 缓存 ​

实现分三块：cacheKey 用「函数名 + 序列化参数」生成存档键；createCached(fn, { tags, ttl }) 返回一个先读缓存、未命中回源并登记的包装函数；expireTag 按标签撕毁并顺手清理悬空引用。纯 TypeScript，可以直接跑：

ts
/* ---------- 数据结构：正表 + 反向索引 ---------- */
type Entry = { value: unknown; tags: string[]; expiresAt: number };

const store = new Map<string, Entry>();          // 正表：key → 存档
const tagIndex = new Map<string, Set<string>>(); // 反向索引：tag → key 集合

/* ---------- 缓存键：函数名 + 序列化参数 ---------- */
function cacheKey(fn: { name: string }, args: unknown[]): string {
  return `${fn.name}(${JSON.stringify(args)})`;
}

/* ---------- 包装器：先读缓存，未命中回源并登记 ---------- */
type Options = { tags?: string[]; ttl?: number };

function createCached<A extends unknown[], R>(
  fn: (...args: A) => Promise<R>,
  { tags = [], ttl = 60_000 }: Options = {}
) {
  return async function (...args: A): Promise<R> {
    const key = cacheKey(fn, args);
    const hit = store.get(key);

    // ① 命中且未过期：直接取档
    if (hit && hit.expiresAt > Date.now()) return hit.value as R;

    // ② 未命中（或已过期）：回源执行原函数
    const value = await fn(...args);

    // ③ 登记：写正表，并把 key 挂到每个 tag 名下
    store.set(key, { value, tags, expiresAt: Date.now() + ttl });
    for (const tag of tags) {
      if (!tagIndex.has(tag)) tagIndex.set(tag, new Set());
      tagIndex.get(tag)!.add(key);
    }
    return value;
  };
}

/* ---------- 失效：按 tag 批量撕毁，顺手清理悬空 ---------- */
function expireTag(tag: string): number {
  const keys = tagIndex.get(tag);
  if (!keys) return 0; // 没登记过这个 tag，幂等返回
  let torn = 0;
  for (const key of keys) {
    const entry = store.get(key);
    if (!entry) {
      keys.delete(key); // 悬空引用：存档早已不在，摘掉即可
      continue;
    }
    store.delete(key); // 撕毁存档
    // 同时把 key 从该条目其它 tag 的索引里摘掉，不留悬空
    for (const t of entry.tags) {
      if (t !== tag) tagIndex.get(t)?.delete(key);
    }
    torn++;
  }
  tagIndex.delete(tag); // 本 tag 的索引使命完成，整组清掉
  return torn;
}

/* ---------- 使用示例 ---------- */
let dbCalls = 0;
async function getUser(id: string) {
  dbCalls++; // 观察：只有真正回源时才会自增
  return { id, name: `user-${id}` };
}

const getUserCached = createCached(getUser, { tags: ['users', 'profile'] });
await getUserCached('42'); // 回源，dbCalls = 1
await getUserCached('42'); // 命中存档，dbCalls 仍为 1
expireTag('users');        // 按标签撕毁，返回 1
await getUserCached('42'); // 未命中，回源，dbCalls = 2

实现只有两处细节值得停下来看：

  • 登记发生在未命中之后。命中路径只做一次 Map.get 加一次时间比较，tag 登记的成本只付给真正回源的那次调用——和真实缓存「写入时贵、读取时便宜」的取舍一致。
  • expireTag 是幂等的。撕毁不存在的 tag 返回 0，重复撕毁第二次也是 0。失效代码因此可以放心地「多撕几次」，这正是 updateTag 在 Server Action 里随手连调多个 tag 也不会出错的底气。

幼稚失效 vs 标签传播 ​

很多人给缓存做失效的第一版是「哪里写入，哪里手动删 key」。把两种写法放在一起看：

diff
- // 幼稚做法：失效方必须自己知道每一个缓存 key
- store.delete('getUser(["42"])');
- store.delete('getUser(["43"])');
- store.delete('getUser(["42","verbose"])');
- // key 的形状是缓存实现的私有细节，拼错一个就静默失效失败；
- // 新增缓存点或改参数形状，还得回来补删——漏一条，旧数据多活一个 TTL
+ // 标签传播：生产者写入时登记 tag，失效者只报 tag 名
+ const getUserCached = createCached(getUser, { tags: ['users'] });
+ expireTag('users'); // 该 tag 名下所有 key 一次撕毁，新增缓存点自动覆盖

手删 key 的脆弱之处在于：key 由「函数名 + 序列化参数」拼成，这是缓存实现的私有细节，调用方一旦拼错格式，删除就静默失败、不报任何错；而 tag 是生产者与失效者之间的公开契约，双方只认名字、不认形状。

DANGER

漏打 tag 的缓存无法定向失效。createCached(fn) 不传 tags，条目照样被缓存、照样命中，但反向索引里没有它的踪迹——expireTag 够不着它，唯一手段是全量清空 store，或者干等 TTL 自然过期。因此 tag 粒度应跟着「失效的触发者」设计，而不是「数据的生产者」：先想清楚谁会在什么时机触发失效（用户发帖、运营改稿、CMS webhook），tag 就按那个事件命名，并打给所有会因此变脏的条目；生产者只是挂标签的手，失效事件才是边界。

自测

一个 key 同时打了 ['users','profile'] 两个 tag，expireTag('users') 后再读该函数会发生什么？tagIndex['profile'] 里残留什么？

距离真实的 Next.js 还差什么 ​

这个迷你实现跑通了「按参数存档 → 按标签撕毁」的主干，但真实框架还多出四个维度：

  • 持久化与 LRU 淘汰：内存 Map 重启即失、无容量上限；真实实现把条目落进持久层或远端缓存处理器（进阶篇的 'use cache: remote'），并在内存吃紧时用 LRU 先赶走最冷的条目
  • 双 TTL 与 stale-while-revalidate：迷你版只有一个 ttl，到期即失效；真实的 cacheLife 是 stale / revalidate / expire 三档时间——revalidate 到期后仍先把旧内容交给用户、后台刷新（进阶篇演练过的 SWR 语义），expire 才是硬过期
  • 跨实例失效：Map 只存在于单个进程里，多副本部署时实例 A 的 expireTag 传不到实例 B，各副本各持一份旧数据；真实方案要么共享存储，要么把失效事件广播给所有副本
  • 编译期自动改写：'use cache' 是指令而不是函数调用，编译器负责把函数体抽成可缓存单元、自动生成包含闭包捕获的 cacheKey、把 cacheTag 调用收集为元数据；手写版里这些全靠人肉

失效传播这套模型在真实源码里有直接对应物：updateTag 的实现只有寥寥数行——校验「只能在 Server Action 里调用」，然后转手把 tag 交给底层的 revalidate 立即撕毁。点开下面的源码对照，找一找它与 expireTag 的对应关系：

小结 ​

  • use cache 的三个动作：按参数存档、贴标签、按标签撕毁；核心数据结构是 tag → keys 反向索引
  • 登记发生在写入侧（生产者），失效者只需一个 tag 名——这是标签传播比按 key 手删健壮的根源
  • 多 tag 条目被单个 tag 撕毁后，其余 tag 名下会留下悬空引用，可在失效时顺手清理
  • 漏打 tag 等于不可定向失效；tag 粒度跟着失效触发者设计，而不是数据生产者
  • 真实框架还要补持久化淘汰、SWR 双 TTL、跨实例广播与编译期改写
