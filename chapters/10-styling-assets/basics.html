样式方案的选择 ​

Next.js 不对样式框架做强制绑定，官方一等支持两类常规方案：Tailwind CSS（实用类优先，官方脚手架默认）与 CSS Modules（组件级作用域，零额外依赖）。Sass、CSS-in-JS 等生态方案也都可用。选型首先是团队习惯问题，其次看场景：

方案作用域适合场景上手成本
Tailwind v4类名即样式（v4 有层叠/源码驱动）快速迭代、设计系统统一需要熟悉令牌与类名
CSS Modules每个 .module.css 自动哈希隔离组件库、偏好原生 CSS 的团队零额外概念
Sass嵌套/混入/变量存量 SCSS 资产迁移需装 sass 包
CSS-in-JS运行时/构建时注入动态主题、强运行时样式需配置 RSC 样式注册

Tailwind v4：装包、PostCSS、一行 import ​

v4 的接入方式与 v3 差别明显：不再需要 tailwind.config.js 和 @tailwind base/components/utilities 三条指令，配置收敛进 CSS 本身。

bash
pnpm add -D tailwindcss @tailwindcss/postcss

::: warn 全局 CSS 的引入边界 官方规定：非模块的全局样式表只能在 root layout 中引入（例外是外部 npm 包的样式表，可以在任意组件 import）。虽然其它 layout/page 也能引全局 CSS，但客户端导航离开对应路由时样式不会被移除，可能污染整个应用——除 root layout 外不要这样做。 :::

CSS Modules：默认作用域隔离 ​

不想引入 Tailwind 时，CSS Modules 是内置方案：文件名以 .module.css 结尾，import 得到的是一个类名映射对象，类名在构建期被哈希，天然防冲突。

css
.primary {
  padding: 8px 16px;
  border-radius: 8px;
  background: var(--color-brand);
  color: white;
}

.primary:hover {
  background: var(--color-brand-dark);
}

需要全局选择器（如覆盖第三方组件）时用 :global(.foo)；条件组合直接 clsx/cx 之类的小工具拼接 styles.xxx 即可。生产构建会自动把模块 CSS 合并成最小的 chunk，随路由按需加载。

两种方案可以共存

Tailwind 做布局与间距、CSS Modules 写复杂组件局部样式是常见组合。冲突面很小：Tailwind 类是全局命名，Modules 类是哈希命名，各管各的。

Sass：存量资产的平滑入口 ​

执行 pnpm add -D sass 后即可直接 import .scss/.module.scss，支持嵌套与 @use，零额外配置。需要自定义选项时在 next.config.ts 的 sassOptions 中设置：例如 implementation: 'sass-embedded' 切换为更快的嵌入式实现，或用 includePaths、quietDeps 管理大型样式库的依赖噪声。

常见误区 ​

  • 误区一：沿用 v3 三件套指令。 v4 只需要 @import 'tailwindcss'，令牌写在 @theme。
  • 误区二：在页面里引第二份全局 CSS。 客户端导航后不会卸载，会造成跨页样式泄漏。
  • 误区三：CSS Modules 里写死全局类名。 默认就是局部作用域，需要全局时显式 :global()。
  • 误区四：装了 Tailwind 但忘配 PostCSS。 没有 @tailwindcss/postcss 插件，@import 'tailwindcss' 不会被处理。

小结 ​

  • Tailwind v4 接入三步：装 tailwindcss @tailwindcss/postcss、PostCSS 挂插件、globals.css 里 @import 'tailwindcss' + @theme 定义令牌
  • 全局样式只在 root layout 引入；CSS Modules 用 .module.css 获得构建期类名隔离；Sass 装包即用
  • 方案之间可以共存，按「布局实用类 + 复杂组件局部模块」的分工组织样式
