一次请求在 16.4 中经历了什么 ​

会用框架和理解框架的分界线，在于你脑子里有没有一张请求生命周期图。下面是用户访问一个动态页面时的完整时间线：

::: steps

  1. 代理层（proxy.ts）：请求最先到达代理，可以在这里做鉴权跳转、灰度、Header 改写。16.x 中它取代了 middleware.ts，并且运行在 Node 运行时
  2. 路由匹配：框架按 app/ 目录树解析布局链与页面组件
  3. 服务端渲染：RSC 在服务端执行服务端组件，遇到 await 决定「流式 / 缓存 / 阻塞」（16.4 的 Stream/Cache/Block 模型，第 6 章细讲）
  4. RSC 序列化流：服务端输出的不是完整 HTML，而是一种流式负载——静态外壳 + 动态 UI 数据块
  5. 浏览器渐进呈现：外壳先显示，Suspense 边界内的部分随数据到达而流式补齐
  6. 水合：客户端组件的 JS 下载完成后在已有的 HTML 上附加交互
  7. 预取（后台持续进行）：视口内的 <Link> 提前拉取下一条路由的外壳 :::

这张图解释了为什么 16.4 的导航可以“即时”：第 7 步在点击前就已经开始，点击时浏览器手里已经握着一张页面外壳。

下面的演练场用定时器模拟这条时间线：页面外壳立即出现，三块动态内容按各自延迟随“数据流”到达——这正是 Suspense 流式渲染的体感：

演练场：外壳先行，动态内容流式补齐tsx · 客户端演练

点击「运行」在浏览器内编译并执行；这是纯客户端示例，不连服务端。

RSC 负载：服务端到底发给浏览器什么 ​

服务端组件不会向浏览器发送“组件代码”，而是发送一棵序列化的 React Server Component 树，大致由三类元素组成：

元素例子是否下发 JS
服务端元素纯展示、直接读数据库的组件否（零客户端 JS）
客户端元素引用'use client' 边界组件是（带模块 id）
可序列化 props字符串、数字、普通对象、数组作为数据下发

::: warn 正因为跨边界传递的是序列化数据，服务端组件不能把函数、类实例、Symbol 当 props 传给客户端组件。这是第 3 章会反复遇到的高频报错根源。 :::

Turbopack：为什么它又快又省内存 ​

16.0 起 Turbopack 是默认且稳定的打包器（开发与生产构建都是），16.4 又在它身上做了两件大事。

① 函数级增量缓存 + 内存回收（16.4）

Turbopack 把编译结果缓存到“函数级”：改动一个文件，只重算受影响的下游节点。16.4 之前这些缓存常驻内存，长时间 dev 会涨到几十 GB；16.4 利用文件系统缓存把不活跃的结果驱逐出内存，官方在 vercel.com 仪表盘上测得 50 条路由的场景从 21.5GB 降到 2GB（约 90%）。

② 构建也吃磁盘缓存（16.4 默认开启）

ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  // next build 复用 .next/cache 中的持久化结果
  // CI 中记得缓存该目录，冷构建不享受收益
};

export default nextConfig;

SSR 从 Web Streams 迁移到原生 Node 流 ​

16.4 把服务端渲染的底层流实现从 Web Streams 换成 Node.js 原生流。收益不是语法层面的，而是运行时吞吐：

  • 高负载下无需改代码，官方称可多处理约 22% 的请求
  • 与 Node 生态（压缩、日志、中间件）对接时少一层适配开销

与之配套的决定是：Edge Runtime 正式废弃。

维度旧：Edge Runtime新：Node Runtime（统一）
API 覆盖只能用 Web 标准 API 子集Node 完整生态
middleware/proxy跑 Edgeproxy.ts 跑 Node
冷启动理论极快Node 持续优化，差距收窄
踩坑面两套运行时行为不一致单一运行时，行为可预期

TIP

你在旧项目里看到的 export const runtime = 'edge' 应当规划迁移。绝大多数中间件场景直接删掉该声明、改用 Node 默认运行时即可。

React 19.2 带来的配套能力 ​

Next 16 对应 React 19.2，三个能力值得提前知道（后续章节都会用到）：

  1. View Transitions：配合 unstable_ViewTransition 做原生跨页面过渡动画
  2. useEffectEvent：把 Effect 里读取的最新逻辑抽成“事件函数”，减少依赖数组心智负担
  3. React Compiler（稳定）：自动记忆化，16.4 还新增了实验性 Rust 实现

开启 React Compiler 只需一行：

ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  reactCompiler: true, // 16.0 起稳定；无需手写 useMemo/useCallback 包裹
};

export default nextConfig;

15.x → 16.4 升级决策表 ​

升级不要凭记忆改，官方提供了 codemod 做机械迁移：

bash
pnpm dlx @next/codemod@latest upgrade latest
1

codemod 会自动完成下面表格的大部分条目，但每一项你都应该知道它改了什么：

变化点15.x 写法16.4 写法风险等级
打包器next dev --turbopacknext dev（默认 Turbopack）低
中间件middleware.ts + middleware()proxy.ts + proxy()中
动态参数const { id } = paramsconst { id } = await params高（漏改即运行时报错）
PPRexperimental.pprcacheComponents: true高（语义重写）
缓存默认fetch 默认缓存默认动态，需要 'use cache'高
Lintnext lintESLint CLI（codemod 会迁移脚本）低
稳定 APIunstable_xxx去掉 unstable_ 前缀低

DANGER

params / searchParams / cookies() / headers() 的异步化是升级中最容易漏的：TypeScript 有时只能提示“这里是个 Promise”，运行时才会真正炸。升级后请全仓搜索 params. 逐一确认 await。

升级后建议立刻跑三件事验证：

bash
pnpm install
pnpm build        # 构建期就能发现绝大多数 async API 类型问题
pnpm dev          # 打开关键页面检查导航与数据新鲜度

ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  reactStrictMode: true,
  reactCompiler: false, // 稳定特性，确认项目无极端动态写法后开启

  // 16.4 旗舰：缓存组件 + 部分预取（逐路由灰度，别一上来全站开）

  // partialPrefetching: true,

  // 外链图片域名白名单（使用 next/image 时必需）
  images: {
    remotePatterns: [
      { protocol: 'https', hostname: 'images.example.com' },
    ],
  },
};

export default nextConfig;

小结 ​

  • 16.4 的架构关键词：RSC 流 + 即时外壳预取 + Node 原生流 + 函数级增量编译
  • Edge 退场、Node 统一，降低了运行时行为分叉
  • 升级是“codemod 打底 + 手动核对异步 API 与缓存语义”的组合拳

实战篇我们会把这些理解落成一个可持续跟随 Next 版本演进的学习仓库，并亲手完成一次升级演练。
