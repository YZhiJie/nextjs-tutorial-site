Next.js 在解决什么问题 ​

只用 React 写应用时，你需要自己把一堆“零件”拼成一辆车：路由库、SSR/SSG 方案、打包器、代码分割策略、缓存策略、部署适配……Next.js 把这些零件预先组装好，并在 React 之上规定了一套基于文件约定的全栈架构。

它的核心价值可以浓缩成三句话：

  1. 路由即文件系统：在 app/ 目录下放一个文件，就自动得到一条路由
  2. 服务端与客户端都是一等公民：组件默认在服务端渲染，需要交互时再加一行 'use client'
  3. 框架级缓存与渲染优化：流式渲染、部分预渲染、缓存组件等能力由框架统一调度

术语解释：SSR（Server-Side Rendering）指首屏 HTML 由服务器生成；SSG（Static Site Generation）指构建时就生成 HTML；CSR（Client-Side Rendering）指浏览器拿到 JS 后再渲染。Next.js 允许你在同一个应用里为每条路由分别选择策略。

先厘清三个词：客户端、服务端与全栈 ​

三个术语的定义 ​

术语代码运行在负责什么典型技术
客户端开发用户的浏览器 / App界面渲染、交互响应、浏览器能力React、Vue、CSS
服务端开发你控制的服务器（Node 进程等）接收请求、执行业务规则、读写数据库与缓存、保管密钥与鉴权Express、Koa、NestJS、FastAPI、数据库
全栈开发两端贯通同一个应用（往往也是同一个工程师）同时交付客户端与服务端能力Next.js 这类一体化框架

“服务端”不是“后端框架”的同义词

服务端开发的本质是“代码跑在服务器、处理请求与数据”，与用什么框架无关：用 Koa 手写 HTTP 服务是服务端开发；在 Next.js 服务端组件里查数据库，同样是服务端开发——区别只在代码如何组织。

Next.js 模型：一个应用里的全栈 ​

Next.js 把两层收进一个仓库、一次部署：同一条路由上，服务端产出的 HTML 与客户端交互叶子由框架统一调度，不必为“首屏取数”单独设计一层 API：

text
浏览器
└─ 服务端组件直出的 HTML（首屏即可见）+ 客户端组件（交互叶子）
      │  仅在需要时：Server Actions（POST）/ Route Handlers
┌─────┴─────────────┐
│ 同一个 Next 服务    │  服务端组件 · Actions · route.ts
│ 鉴权 · 取数 · 渲染  │
└─────┬─────────────┘
      ├─ 数据库
      └─ Redis / 内部服务

两种模型系统对比 ​

维度SPA + 独立后端Next.js 全栈
仓库与部署两个仓库、两条发布线一个仓库、一次部署
接口契约所有交互都经显式 HTTP API组件直接取数；仅对外能力才写 API
首屏客户端渲染（需额外接 SSR 方案）默认服务端渲染，HTML 直出
数据获取前端 fetch 自家接口，至少一跳组件内直连数据库/内部服务，无自调一跳
写操作手写接口 + 客户端调用 + 手动刷新Server Actions：执行、失效、重渲染一个往返
鉴权落点后端中间件统一拦截每个 Action / Handler / 数据层内部重复校验
团队分工前端/后端边界清晰按能力分层，要求工程师贯通两端
适合场景多客户端共用 API、复杂域逻辑、独立扩缩容Web 产品为主体、追求交付速度与首屏体验

边界：什么时候仍然需要独立后端 ​

Next.js 可以承担 BFF（面向前端的编排层），但官方明确它不是完整后端的替代品。以下能力应留在独立服务（第 14 章的 BFF 边界表给出同一结论）：

  • 核心业务规则与跨服务事务：下单、计费、对账
  • 高吞吐后台任务、消息队列消费、定时批处理
  • 同时服务移动端与第三方系统、需要长期稳定契约的公共 API
  • 需要独立于 Web 层扩缩容的计算密集型服务

给有独立后端经验的读者

如果你熟悉 Express/Koa 的中间件模型，可以这样迁移心智：服务端组件相当于“请求处理器 + 模板渲染”合一；Route Handlers 就是你熟悉的裸 HTTP 端点；proxy.ts 只做粗粒度网关动作，不替代鉴权中间件。原有业务后端不必推倒，常见形态是 Next.js 作为它前面的 BFF——第 14 章的 TeamHub 正是这一结构。

16.x 代际：动态优先，显式缓存 ​

理解 Next.js 16.3 之前，先要理解 16.0 定下的基调。早期 App Router（13/14）带有大量隐式缓存：fetch 默认会被缓存、路由默认静态化，行为像一本“默认规则手册”，很多开发者记不清哪条数据到底新不新鲜。

从 16.0 开始，模型翻转为：

  • 动态是默认值：所有动态代码（访问请求信息、取数、未显式缓存的部分）默认在请求时执行，没有隐藏缓存
  • 缓存是显式 opt-in：想缓存？在组件或函数顶部写下 'use cache'，意图即代码
  • Turbopack 成为默认打包器：开发冷启动、HMR、生产构建全面提速
  • middleware.ts 更名为 proxy.ts：明确它是网络边界代理，且运行在 Node 运行时
  • 请求 API 全部异步：params、searchParams、cookies()、headers() 都需要 await

16.3 的位置

16.3 不是一次推倒重来，而是把 16.0 铺好的“动态优先 + 显式缓存”地基推向极致：新增 Instant Navigations（即时导航） 工具集，配合 Turbopack 的内存与构建优化、原生 Node 流 SSR，以及一整套面向 AI 编程智能体的开发链路。

环境要求与安装 ​

Next.js 16.3 的最低运行环境：

  • Node.js ≥ 20.9.0（本教程在 Node 24 上验证）
  • 包管理器：本教程统一使用 pnpm（11.x）
  • 编辑器：VS Code（或任何能使用 TypeScript 插件的编辑器）

记住三个最重要的约定文件：

  • page.tsx：路由的叶子，一个文件对应一个可访问 URL

小结与下一步 ​

  • Next.js 是 React 之上的全栈应用框架，核心是文件路由 + 服务端能力 + 框架级优化
  • 服务端开发 = 代码跑在服务器处理请求与数据；全栈 = 一个应用贯通两端——Next.js 全栈并不排斥独立后端，两者按 BFF 边界协作
  • 16.x 的基调是动态默认、显式缓存，16.3 的旗舰是 Instant Navigations
  • 用 pnpm + create-next-app 起步，pnpm dev 默认 Turbopack
