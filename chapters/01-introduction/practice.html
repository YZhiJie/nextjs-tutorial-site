场景：为整本书搭建“练功房” ​

学框架最忌“每章新开一个随机项目”。我们要建一个贯穿全书的单仓库：

  • 每个大练习有独立的入口页，但共享一套依赖
  • 版本锁定，团队/CI/未来的你装出来的依赖树一致
  • 升级 Next.js 时能一条命令对照差异，而不是手工回忆

最终目录长这样：

text
nextjs-playground/
├── src/
│   └── app/
│       ├── layout.tsx
│       ├── page.tsx              # 练习导航首页
│       └── lab-xx/               # 每章一个练习路由
│           └── page.tsx
├── content-notes/                # 你自己的学习笔记（可选）
├── next.config.ts
├── pnpm-workspace.yaml
├── package.json
└── .npmrc

第一步：初始化并锁定工具链 ​

bash
mkdir nextjs-playground && cd nextjs-playground
pnpm dlx create-next-app@latest . --ts --app --tailwind --eslint --src-dir --import-alias "@/*" --use-pnpm
1
2

::: warn 末尾的 . 表示在当前目录初始化。目录必须为空（或只允许存在 .git），否则脚手架会提示交互确认。 :::

安装完成后，显式锁定教程版本，避免不同时间安装到不同补丁：

bash
pnpm add next@16.3.0
1

在 package.json 中声明 packageManager 字段（pnpm 会自动写入），并确认脚本：

json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "typecheck": "tsc --noEmit",
    "lint": "eslint ."
  },
  "packageManager": "pnpm@11.10.0"
}

第二步：pnpm 的工程化配置 ​

在仓库根加一个 .npmrc，让团队行为一致：

ini
# peer 依赖严格度：Next 生态部分包的 peer 范围更新滞后，宽松解析减少无谓报错
auto-install-peers=true
# 保存依赖时默认写入 ^ 范围（补丁/小版本可跟进）
save-prefix=^

第三步：健康检查三连 ​

任何框架教程的第一天，都值得花 10 分钟确认“工具链真的健康”，避免把环境问题误学成框架问题。

::: steps

  1. pnpm -v 与 node -v 确认满足 pnpm 11 / Node ≥ 20.9
  2. pnpm dev 启动后访问首页，确认 Turbopack 正常且无报错
  3. 改 app/page.tsx 任意文字并保存，确认 Fast Refresh 秒级生效；再跑 pnpm build 确认生产构建通过 :::
bash
pnpm build
# 期望：看到 Route (app) 表格输出，ƒ / 表示动态路由，○ 表示静态，无类型错误
1
2

构建输出表是你未来的好朋友：

标记含义
○静态生成（构建期产出 HTML）
ƒ动态（请求时执行）
ƒ (Cached)启用缓存组件后的动态但可缓存段
—不产生独立可访问路由（layout 等）

第四步：建一个练习导航首页 ​

把默认的 src/app/page.tsx 改成练习索引，后续每学一章加一条：

tsx
const LABS = [
  { slug: 'lab-01', title: '01 · 安装与结构', status: 'done' },
  { slug: 'lab-02', title: '02 · 路由与布局', status: 'todo' },
  { slug: 'lab-03', title: '03 · 组件边界', status: 'todo' },
];

export default function Home() {
  return (
    <main className="mx-auto max-w-2xl px-6 py-16">
      <h1 className="text-2xl font-bold">Next.js 16.3 练功房</h1>
      <p className="mt-2 text-gray-500">每章一个路由，全部用 pnpm 与锁定版本管理。</p>
      <ul className="mt-8 space-y-3">
        {LABS.map((lab) => (
          <li key={lab.slug}>
            <a
              href={`/${lab.slug}`}
              className="flex items-center justify-between rounded-xl border p-4 hover:border-blue-300"
            >
              <span>{lab.title}</span>
              <span className={lab.status === 'done' ? 'text-emerald-600' : 'text-gray-400'}>
                {lab.status === 'done' ? '已完成' : '待练习'}
              </span>
            </a>
          </li>
        ))}
      </ul>
    </main>
  );
}

真实团队场景：版本演进的协作纪律 ​

当一个 Next.js 项目由团队维护时，“升级框架”不应该是某个人的玄学操作。推荐三条纪律：

  1. 锁文件必须进 Git：pnpm-lock.yaml 提交，禁止个人随意重新生成
  2. 升级走独立 PR：一条 PR 只做版本升级 + codemod + 修复，不夹带业务需求
  3. 把版本写进 CI 验证：安装、类型检查、构建、关键路径 E2E 缺一不可
yaml
# pnpm/action-setup 启用 pnpm
# actions/setup-node 配合 cache: pnpm
steps:
  - pnpm install --frozen-lockfile   # 锁文件不一致立刻失败
  - pnpm typecheck
  - pnpm lint
  - pnpm build
  # 缓存 .next/cache 后，第二次构建可明显加速（16.3 磁盘缓存）
