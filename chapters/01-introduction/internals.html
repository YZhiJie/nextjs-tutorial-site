十几个环节里，哪五段是骨架 ​

1.2 把一次页面请求拆成了一条长链：匹配路由 → 执行服务端组件 → 生成 RSC 载荷 → 拼 HTML 外壳 → 写入响应 → 客户端水合。链条上大部分环节都在做同一件事的加固：编译、缓存、错误边界、埋点。

把加固全部摘掉，剩下的骨架只有五段：

  │ ② 路由表          路径 → 服务端组件函数
  │ ③ 文档外壳        layout.tsx 的最小对应物
  │ ④ Flight 序列化   组件执行结果当数据下发
  │ ⑤ 两段式 flush    外壳先发，慢数据后补
  ▼

下面这份实现把五段全部塞进一个文件。它不是为了替代框架，而是为了让 1.2 的每个名词都落到某一行代码上——之后各章主攻的，恰好是其中某一段的重型实现。

① 渲染器：宿主元素长什么样 ​

服务端组件的产物不是 JSX，而是宿主元素（host element）树：{ type: 'h1', props: { children: '...' } }。渲染器要做的只有两件事——把 props 拼成属性字符串，递归拼接 children。约 15 行就够。

② 路由表：服务端组件就是普通函数 ​

page.tsx 的默认导出是一个函数，调用它就得到元素树。所以在最简管线里，路由表就是「路径 → 函数」的映射，命中即调用——没有编译器、没有清单文件：

ts
const routes: Record<string, () => VNode> = {
  '/': () => h('main', { children: [h('h1', { children: 'mini-next' })] }),
};

真实的 routes[pathname] 来自构建期产物：Turbopack 把每个 page.tsx 编译成模块，路由清单再把「路径 → 模块」写进 JSON。查找动作没变，变的是这张表的来源（2.4 会把手写的建表与匹配完整拆一遍）。

③ 外壳：layout 与「两棵树的交集」 ​

layout.tsx 负责 <html>/<body> 这一层，页面组件只负责 <div id="root"> 里面的内容。最简实现里，外壳被拆成 shellHead / shellTail 两个字符串函数——拆成两段这件事本身就是后文的关键。

④ Flight 载荷：为什么要把渲染结果再发一遍 ​

页面 HTML 已经在首屏里了，为什么还要内联一份 JSON？因为水合需要知道「这棵树是什么」，而不只是「它长什么样」。客户端拿到的 HTML 只是一串字符串，没有元素类型、没有 key、没有 props 边界。载荷（payload）就是服务端把元素树序列化后交给客户端的「结构说明书」。

它同时解释了 3.2 的边界：载荷里能装的只有数据。写在这里的每一个值都必须能 JSON.stringify——函数、类实例装不进去，这不是风格约定，是序列化格式的物理限制。

⑤ 两段式 flush：首字节与慢数据 ​

真实页面总有快段与慢段。如果在服务端等所有数据齐了再 res.end，用户会盯着空白页直到最慢的那个接口返回。所以响应被切成两段：

  1. 外壳 + 已就绪内容先 res.write 出去——浏览器立刻能渲染、能下载 JS
  2. 慢数据 resolve 后，把补丁片段 res.end 出去

这正是 1.2 里「SSR 从 Web Streams 迁移到原生 Node 流」的动机：渐进式响应要求能在任意时刻把已完成的片段推给客户端，原生流在背压与缓冲上的开销更低，高负载下同样的机器能多扛约 22% 请求。流不是优化技巧，它是「先给用户看点什么」的唯一手段。

完整实现：约 70 行 ​

ts
import { createServer } from 'node:http';

/* ---------- ① 宿主元素渲染器 ---------- */
type VNode = { type: string; props: Record<string, unknown> };
const h = (type: string, props: Record<string, unknown> = {}): VNode => ({ type, props });

const ESCAPES: Record<string, string> = { '&': '&', '<': '<', '>': '>', '"': '"' };
const esc = (s: string) => s.replace(/[&<>"]/g, (c) => ESCAPES[c]);

function renderToHtml(node: VNode | string | number | null | undefined): string {
  if (node === null || node === undefined) return '';
  if (typeof node !== 'object') return esc(String(node));
  const { children, ...attrs } = node.props as { children?: unknown };
  const attrText = Object.entries(attrs)
    .map(([k, v]) => ` ${k}="${esc(String(v))}"`)
    .join('');
  const kids = Array.isArray(children) ? children : [children];
  return `<${node.type}${attrText}>${kids.map(renderToHtml).join('')}</${node.type}>`;
}

/* ---------- ② 路由表：服务端组件 = 返回元素树的函数 ---------- */
const routes: Record<string, () => VNode> = {
  '/': () => h('main', {
    children: [
      h('h1', { children: 'mini-next' }),
      h('p', { class: 'now', children: `服务端渲染于 ${new Date().toISOString()}` }),
    ],
  }),
  '/about': () => h('main', { children: h('h1', { children: '关于' }) }),
};

/* ---------- ③ 文档外壳：layout.tsx 的最小对应物 ---------- */
const shellHead = (title: string) =>
  '<!DOCTYPE html><html lang="zh-CN"><head><meta charset="utf-8">' +
  `<title>${esc(title)}</title></head><body><div id="root">`;

const shellTail = (flight: string) =>
  '</div>' +
  `<script id="__flight" type="application/json">${esc(flight)}</script>` +
  '<script type="module" src="/client.js"></script></body></html>';

/* ---------- ④ 慢数据：Suspense 边界里那个"迟到的服务端组件" ---------- */
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

/* ---------- ⑤ 请求入口：两段式 flush ---------- */
createServer(async (req, res) => {
  const pathname = (req.url ?? '/').split('?')[0];
  const loader = routes[pathname];

  res.writeHead(loader ? 200 : 404, {
    'content-type': 'text/html; charset=utf-8',
    'cache-control': 'no-store', // 动态渲染的全部含义：每次请求都重新执行组件
  });

  if (!loader) {
    res.end(shellHead('404') + renderToHtml(h('h1', { children: '404' })) + shellTail('null'));
    return;
  }

  const vnode = loader();                     // 组件执行：发生在服务端
  const first = renderToHtml(vnode);          // 已就绪的宿主元素

  res.write(shellHead('mini-next') + first);  // ① 首段：外壳 + 快内容

  await sleep(120);                           // ② 慢数据（真实场景是数据库 / 第三方 API）
  const late = renderToHtml(h('p', { children: '慢数据终于到了' }));

  res.end(late + shellTail(JSON.stringify(vnode))); // ③ 尾段：补内容 + Flight 载荷
}).listen(3000, () => console.log('mini-next ready on http://localhost:3000'));

三段代码之外，有三处细节值得停下来看：

  • 组件执行与 HTML 生成是两件事。loader() 产出元素树，renderToHtml 把它变成字符串。RSC 的产物是前者（数据），SSR 的产物是后者（HTML）——这条分界线在第 3 章会被反复用到。
  • 载荷在内联脚本里，而不是在客户端 bundle 里。它随页面一起到达，所以首屏不需要额外请求；这也意味着载荷体积直接进首屏字节数（12.2 的体积预算要把它算进去）。
  • no-store 就是「动态」。框架层面的「渲染模式」不是魔法开关，它最终表达成一个响应头。反过来，改动这个头就等于改渲染模式——这正是 8.x 里 ○ / ● / ƒ 三种符号的物理含义。

DANGER

把这个响应头改成 's-maxage=60'，服务端组件里的 new Date() 就只会在缓存填充的那一刻执行一次。之后 60 秒内的所有请求都拿到同一份 HTML——页面上那句「服务端渲染于 …」会僵在那儿不动。这就是 ISR 的雏形，也是 5.1「缓存默认全动态、必须显式 opt-in」存在的原因：在自研管线上，缓存语义完全暴露在响应头上，最难不出错。

距离真正的 next dev 还差什么 ​

这份 70 行实现跑通了主干，但每一段在真实框架里都长了几十倍：

环节真实实现的增量
渲染器React 完整 reconciler、Suspense、错误边界、Portal
路由表Turbopack 编译 TSX、动态段/并行/拦截路由（2.4）、重写规则
外壳metadata 合并与 <head> 序列化（10.4）、字体与图片优化
载荷行式 Flight 协议、流式追加、引用表、服务端引用加密（3.4）
响应Cache Components 缓存条目、标签失效（5.x）、排障与埋点（13.x）

骨架不变：执行组件 → 序列化结果 → 分段下发 → 客户端接管。抓住这四步，再看任何渲染模式的取舍都不会迷路。

小结 ​

  • 一次 SSR 请求的骨架只有五段：渲染器 / 路由表 / 外壳 / 载荷 / 分段响应
  • 服务端组件就是普通函数，调用它就是「在服务端渲染」
  • Flight 载荷是结构说明书，随首屏内联下发，体积要计入首屏预算
  • 「动态」最终落在一个响应头上；改响应头就是改渲染模式
  • 两段式 flush 是流式渲染的动机：先给用户看点什么，再补齐
