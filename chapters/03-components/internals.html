服务端组件渲染的“产物”不是 HTML ​

3.1 说过服务端组件“零 JS 下发”。这背后是一个关键事实：RSC 请求的响应体不是 HTML，而是一份行式 JSON 流（line-delimited JSON stream），常称 RSC payload 或 wire format。每一行是一个独立的 chunk，主要有三类：

  • 模型行（model row）：序列化后的 UI 描述，元素形如 ["$", type, key, props]
  • 引用行（reference row）：客户端组件的“名片”——模块 id 与导出名，供客户端去 bundle 里解析
  • 提示/错误行（hint / error row）：预加载提示、流式过程中的异常等

以一个具体例子看：服务端组件 Article 包着一个客户端组件 LikeButton，序列化后的 payload 长这样：

text
1:I["./like-button.tsx","LikeButton"]
0:["$","article",null,{"className":"post","children":[["$","h1",null,{"children":"RSC 手记"}],["$","$L1",null,{"initialCount":3}]]}]
1
2

读法：第 2 行是模型行——一棵 article > h1 + LikeButton 的树；其中 LikeButton 的位置写的是字符串 "$L1"，它不是组件本身，而是指向第 1 行引用行的指针。客户端解析时先查表，再把 $L1 换回真正的组件。

为什么不是 JSON.stringify(vnode) ​

直接 JSON.stringify 一棵元素树会卡在两个地方：函数（组件类型）不可序列化；客户端组件的代码也根本不该出现在服务端输出里。行式协议的回答是把“值”和“引用”分开运输：值留在模型行，引用单独成行并给编号，模型行里用 $L{id} 占位。

这也解释了 3.2 的可序列化规则——凡是不能写成“值或引用”的东西（普通函数、类实例、数据库连接），协议里没有一种行可以放它，只能在序列化时报错。边界规则不是 lint 约定，而是格式约束。

手写最小序列化器 ​

下面是一个只覆盖“同步模型层”的最小实现：服务端把 vnode 编码成行式 payload，客户端按行解析、查表并重建元素树。约 70 行：

ts
/* ================= 服务端 ================= */
type VEl = { type: unknown; key?: string | null; props: Record<string, unknown> };
// 客户端组件在服务端只是一张名片：模块路径 + 导出名
type ClientRef = { $$client: true; module: string; name: string };

const isEl = (v: any): v is VEl => v && typeof v === 'object' && 'type' in v;
const isClient = (v: any): v is ClientRef => v && v.$$client === true;

function serializeRSC(vnode: unknown): string {
  const rows: string[] = [];
  const refs = new Map<ClientRef, string>(); // ClientRef -> "$L1"

  const refId = (ref: ClientRef) => {
    if (!refs.has(ref)) refs.set(ref, `$L${refs.size + 1}`);
    return refs.get(ref)!;
  };

  const encode = (v: any): any => {
    if (v === null || ['string', 'number', 'boolean'].includes(typeof v)) return v;
    if (Array.isArray(v)) return v.map(encode);
    if (isClient(v)) return refId(v); // 名片 → "$L1"
    if (isEl(v)) {
      return [
        '$', // 元素标记
        typeof v.type === 'string' ? v.type : refId(v.type as ClientRef),
        v.key ?? null,
        Object.fromEntries(
          Object.entries(v.props).map(([k, val]) => [k, encode(val)])
        ),
      ];
    }
    throw new TypeError('RSC 无法序列化该值'); // 函数/类实例在此被拒绝
  };

  const model = encode(vnode);
  for (const [ref, id] of refs) {
    rows.push(`${id.slice(2)}:I${JSON.stringify([ref.module, ref.name])}`);
  }
  rows.push(`0:${JSON.stringify(model)}`);
  return rows.join('\n');
}

/* ================= 客户端 ================= */
function parseRSC(
  payload: string,
  loadClient: (mod: string, name: string) => unknown
) {
  const table = new Map<string, unknown>(); // "$L1" -> 真实客户端组件
  let model: any = null;

  for (const line of payload.split('\n')) {
    if (!line) continue;
    const sep = line.indexOf(':');
    const id = line.slice(0, sep);
    const body = line.slice(sep + 1);
    if (body.startsWith('I')) {
      const [mod, name] = JSON.parse(body.slice(1));
      table.set(`$L${id}`, loadClient(mod, name)); // 从客户端 bundle 解析
    } else {
      model = JSON.parse(body); // 模型行
    }
  }

  // 把模型里的 "$L1" 字符串换回真实组件，'$' 数组还原为元素
  const revive = (v: any): any => {
    if (typeof v === 'string') return table.get(v) ?? v;
    if (Array.isArray(v)) {
      if (v[0] === '$') return { type: revive(v[1]), key: v[2], props: revive(v[3]) };
      return v.map(revive);
    }
    if (v && typeof v === 'object') {
      return Object.fromEntries(
        Object.entries(v).map(([k, val]) => [k, revive(val)])
      );
    }
    return v;
  };
  return revive(model);
}

对照 wire format，看三个设计点：

  1. '$' 是元素的标签。真实协议同样用 $ 表示 React 元素——所以普通字符串 '$' 必须转义成 '$$' 才不至于被误当成元素，本实现从略。
  2. 行与行互相独立。引用行先写只是排版选择；格式允许任意顺序，客户端先把引用登记进表、最后统一 revive 即可。这正是流式传输能成立的前提。
  3. 函数在序列化层就被拒绝。encode 遇到函数直接抛错——“函数 props 不能跨边界”在协议层的本来面目：不是规则不允许，是格式里根本没有这种行。

协议如何让“服务端组件不进 bundle”成立 ​

把 3.2 的结论放到协议上看，会变得非常具体：

  • 服务端组件在序列化之前就已执行完毕，payload 里只剩宿主标签（"article"、"h1"）与数据。代码从未成为响应的一部分，客户端自然无从下载。
  • 客户端组件从不执行，只登记成引用行。loadClient(module, name) 查的是客户端自己的 bundle——只有被引用行点名的模块才需要进包。
  • 因此 bundle 的边界不是配置出来的，而是由引用行的集合决定：payload 里有几张名片，客户端就打包几个入口。

INFO

真实的 RSC 响应由框架边渲染边写出：主体模型行可以先发，Suspense 边界内的子树 resolve 之后再追加新行。行与行独立、可拼接——这就是“外壳先到、慢数据后流”的传输基础。行式（line-delimited）是流式（streaming）的前提。

这个实现没覆盖什么 ​

最小协议只覆盖同步模型层。真实 RSC 协议还要处理：

  • 流式写入：行随渲染进度分批 flush，而不是一次性拼好再发
  • Promise 与异步迭代器：模型里可以出现“等第 N 行 resolve”的延迟占位
  • 二进制与特殊值：Date、Map/Set、BigInt、undefined 各有专门编码
  • 服务端引用（server reference）：'use server' 函数序列化成可回调的加密 id，这是第 7 章的主角

但骨架不变：行是运输的最小单位，引用让代码与数据分道走。抓住这两点，再去看 DevTools 里真实的 RSC 响应就不会迷路。

小结 ​

  • RSC 响应是行式 JSON：模型行描述 UI，引用行登记客户端组件名片
  • 值与引用分开运输，“不可序列化”由此从报错信息变成格式约束
  • 服务端组件只留渲染结果、客户端组件只留名片，bundle 边界由引用行集合决定
  • 行式格式天然支持流式；本实现省略了流、Promise 与二进制编码
