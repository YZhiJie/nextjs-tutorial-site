场景：一个内容站的导航提速 ​

假设你维护一个电商内容站：首页是商品列表，点击进入 /store/[slug] 详情页。现状是典型的 15.x 写法——页面顶部 await params、fetch 靠默认缓存、动态段在 next build 输出里全标 ƒ。用户反馈「点了商品要愣一下才出页面」。

目标：不推倒重写，按官方迁移路径分 PR 灰度，最终做到列表点进详情瞬时出现，并且用自动化测试锁住不回退。

::: warn 迁移铁律：先 Cache Components，再 Partial Prefetching 官方两个 adoption skill 和手工迁移文档都强调同一顺序：先让每条路由「结构上即时」，再切换预取模型。反过来做会在外壳尚未就绪时先改变 <Link> 行为，制造大量难以归因的问题。 :::

第一步：开开关并移除旧段配置 ​

ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  cacheComponents: true,
  // partialPrefetching 留到第二阶段
};

export default nextConfig;

开启后，仍导出 dynamic、revalidate、fetchCache 的段会直接报错。按第 5 章的映射处理：revalidate = 3600 换成 'use cache' + cacheLife('hours')，force-dynamic 直接删除，fetch 的 next: { revalidate, tags } 换成缓存函数内的 cacheLife/cacheTag。

第二步：先让全站「构建通过、照常服务」 ​

不要试图一天改完所有路由。官方路径是先批量允许阻塞、让应用恢复绿色，再逐条改造：

::: steps

  1. 对所有未声明 instant 的 page/layout/default 批量加 export const instant = false（官方提供 codemod）
  2. 处理无法被 instant = false 豁免的同步 I/O 构建错误：预渲染中的 new Date()、Math.random()、crypto.randomUUID() 必须移到请求时——包进 <Suspense> 并先 await connection()，或移入客户端组件
  3. 部署这个「机械迁移 PR」，此时用户行为与之前一致，但你已经站在新模型上 :::
bash
npx @next/codemod@canary cache-components-instant-false ./src/app
1

TIP

路径传错不会报错，只会输出 0 ok。执行后务必核对被修改的文件数是否符合预期。

第三步：列表 → 详情，一次完整改造 ​

挑最高价值的 /store 路由第一个改造。列表页的数据少变、适合缓存；详情页库存实时、适合流式。

tsx
import Link from 'next/link';

async function getProducts() {
  'use cache';
  cacheLife('minutes'); // 商品列表分钟级新鲜，可进入外壳
  return db.products.findAll();
}

export default async function StorePage() {
  const products = await getProducts();
  return (
    <ul>
      {products.map((p) => (
        <li key={p.slug}>
          <Link href={`/store/${p.slug}`}>{p.name}</Link>
        </li>
      ))}
    </ul>
  );
}

详情页的关键动作是把 params 的读取下沉到 Suspense 内的叶子组件，删掉该文件的 instant = false，然后按 dev overlay 的 insight 逐个消除：

  • 商品信息取数加 'use cache'（Cache）
  • 实时库存保留未缓存、留在 Suspense 内（Stream）
  • 用 Navigation Inspector 分别做一次刷新（看 Page load 外壳）和一次列表点详情（看 Client nav 外壳），确认标题立即出现、只有库存区显示回退
tsx
import { Suspense } from 'react';
import { ProductInfo, Inventory } from './details';

export default function ProductDetailPage({ params }: { params: Promise<{ slug: string }> }) {
  return (
    <div>
      <Suspense fallback={<h1>正在加载商品…</h1>}>
        <ProductInfo params={params} />
      </Suspense>
      <Suspense fallback={<p>查询库存中…</p>}>
        <Inventory params={params} />
      </Suspense>
    </div>
  );
}

第四步：开启 Partial Prefetching 并审计链接 ​

全部路由改造完后再打开第二个开关，然后审计每一个存量 <Link prefetch={true}>（按进阶篇的五选一表处理）。商品列表卡片指向同一路由且详情内容依赖 params——若商品信息值得逐链接预热，保留链接上的 prefetch={true}；库存是实时数据，预取了也会陈旧，让它流式补入即可。

写操作后的新鲜度

详情页若在 Server Action 里改了数据（第 7 章会讲），用 updateTag('product') 让下一次读取等待新数据；预取也会随失效静默刷新，不会把旧外壳展示给刚下单的用户。

第五步：用 E2E 锁住「即时」（预告） ​

Instant Insights 只能证明外壳存在，证明不了外壳里的内容对不对。官方提供 @next/playwright 的 instant() 辅助函数，把断言范围限定在「导航完成瞬间立即可见的 UI」。完整工程化在第 13 章展开，这里先认识形态：

ts
import { test, expect } from '@playwright/test';
import { instant } from '@next/playwright';

test('从列表点进详情是即时的', async ({ page }) => {
  await page.goto('/store');
  await instant(page, async () => {
    await page.click('a[href="/store/hats"]');
    await page.waitForURL((url) => url.pathname === '/store/hats');
    // 回调内：商品标题必须在即时 UI 中可见
    await expect(page.locator('h1')).toContainText('棒球帽');
    // 实时库存此时不应该出现（还在 Suspense 里流式补入）
    await expect(page.getByText('库存')).toHaveCount(0);
  });
  // 回调结束：动态内容放行
  await expect(page.getByText(/库存/)).toBeVisible();
});

最佳实践清单 ​

  • [ ] 迁移顺序固定为「codemod 打底 → 同步 I/O 清零 → 逐路由改造 → 最后开 partialPrefetching」，每步独立可部署
  • [ ] 改造粒度遵循「下沉（push down）→ 缓存（cache）→ 逐链接预取（per-link）」三个杠杆，优先把 I/O 推进 Suspense 叶子
  • [ ] Suspense 边界尽量低且贴近数据，避免一个高层边界把整页换成单个大骨架
  • [ ] 每个缓存函数显式写 cacheLife，不依赖隐式 default profile
  • [ ] <Link prefetch={true}> 只出现在「URL 数据 + 可缓存 + 高流量」三者同时满足的链接上
  • [ ] 关键用户流（列表→详情、搜索→结果）各配一条 instant() 回归测试
  • [ ] 性能结论只在缓存预热后成立，冷缓存页面要有合理的骨架设计

亲手验证 ​

第 5 章的全栈实验已经包含 'use cache'、cacheLife、cacheTag 与 updateTag 的完整链路，而它们正是即时外壳的内容来源。建议在实验里再观察一次：开启 cacheComponents 后，缓存命中的内容如何成为点击瞬间可见的外壳。

小结 ​

  • 即时导航落地是一场有顺序的渐进迁移：开关与段配置先行，instant = false 兜底，同步 I/O 必须清零，路由逐条转绿，预取最后切换
  • 列表→详情的标准结构是「缓存列表进外壳 + params 下推 Suspense + 实时数据流式补入」
  • Navigation Inspector 负责开发期肉眼验证，instant() 负责 CI 中把即时性变成不可回退的契约
