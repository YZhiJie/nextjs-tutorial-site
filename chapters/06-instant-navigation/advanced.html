预取的旧模型与新模型 ​

未开启 Partial Prefetching 时，预取是「全有或全无」的：静态路由整页预取，动态路由默认跳过。一个页面上有 20 个指向不同详情页的链接，就可能触发 20 份独立的预取负载，且每份都包含该链接 URL 特有的数据。

Partial Prefetching 把模型改成「每路由一份共享外壳（App Shell）」：

  • 同一目标路由的任意多个链接，共享一份 App Shell，第一个链接进入视口时请求一次即可
  • 外壳里装的是该路由的静态输出、不依赖 URL 的缓存内容，以及会话级（cookies()/headers()）内容
  • 依赖具体 URL 的数据（params、searchParams）不能进共享外壳，导航后从 Suspense 边界流式补入

为什么会话内容可以进外壳

cookies()、headers() 是按会话变化而不是「按链接变化」的，同一会话内所有链接共享同一份值，因此外壳可以携带；而 params、searchParams 每条链接都不同，无法共享。

一次外壳请求里到底有什么 ​

一个 App Shell 由三类内容构成：

构成来源点击时表现
静态内容构建期即可确定的 JSX立即呈现
缓存内容'use cache' 且 stale 窗口 ≥ 5 分钟的缓存函数结果（默认 profile 即满足）立即呈现
回退 UI动态区域外层 <Suspense> 的 fallback立即呈现，真实内容随后流式替换

外壳只「推进到缓存结构允许的最远位置」：一旦遇到未缓存读取或运行时 API，推进停止，该处由 Suspense 接管。短于 5 分钟 stale 的缓存（如 seconds profile）不会进入外壳，而是在导航后流式补入。

默认外壳 vs prefetch={true} URL 级预取 ​

普通 <Link> 只拿共享外壳。当目标路由的部分内容依赖 searchParams 或 params、且这部分内容本身也有缓存生命周期时，可以在具体链接上开启 URL 级预取：

tsx
import Link from 'next/link';

export default function Home() {
  return (
    <nav>
      {/* prefetch={true}：除外壳外，还提前解析该链接 URL 对应的缓存内容 */}
      <Link href="/search?q=react" prefetch={true}>
        React
      </Link>
      <Link href="/search?q=next" prefetch={true}>
        Next.js
      </Link>
    </nav>
  );
}

代价必须算清楚：

维度默认：共享 App Shellprefetch={true}：逐链接预取
作用范围每条路由一份每个可见的 prefetch={true} 链接一份
内容路由输出减去逐链接数据额外解析该链接的 URL 数据（params/searchParams）
成本上限路由数量级可见链接数量级——一屏卡片墙等于一屏服务器调用
角色默认预取点击前渲染更多内容

::: warn 卡片墙不要无脑开 官方指出：网格中每个可见的 <Link prefetch={true}> 进入视口都会触发一次服务器调用，且是尽力而为——慢网络下没预取完就点击，仍回退到外壳。低频路由、必须每请求新鲜的实时内容、无 URL 数据依赖的页面，都不该开。卡片密集场景可改为悬停时再预取（onMouseEnter 时把 prefetch 从 false 切到 null）。 :::

审计存量 <Link prefetch={true}> ​

开启全局开关后，旧的 prefetch={true} 不再预取动态内容，需要逐条审计目标路由：

目标路由情况处理方式
纯静态或内容已缓存删掉多余的 prefetch={true}
有未缓存内容想提前拿到先用 'use cache' 缓存，再删 prefetch={true}
内容依赖 cookies()/headers()在缓存函数外读取会话值、作为参数传入，再删属性
读取 params/searchParams 且内容可缓存保留 prefetch={true}
必须每请求新鲜的实时内容删掉 prefetch={true}，让内容流式补入

不想一次性全站开启时，可以先全局关着、在单条路由导出 export const prefetch = 'partial' 灰度接入，最后再用 codemod 统一清理这些导出。

16.4 新增：用 navigation() / prefetch() 分阶段延迟渲染 ​

预取把「点击前的等待」消灭了，但也带来成本问题：一屏可见的每条链接都会把目标页的全部缓存内容提前拉回来——即使用户永远不会点开。16.4 从 next/cache 新增两个 API，让你按导航阶段精确控制内容何时渲染：

API排除出哪个阶段内容何时渲染
await navigation()预取（外壳 + 显式 prefetch）真实导航发生时
await prefetch()路由外壳（首次发现时的请求）显式预取或导航时

以邮件应用为例：列表页有几十封邮件的链接，每封邮件页要加载整个会话线程。给所有链接开 prefetch 等于把几十条线程全部提前查库——太贵。把线程拆进调用 navigation() 的组件，预取就只带首封邮件，其余等用户真正点进来再加载：

tsx
import { Suspense } from 'react';
import { navigation } from 'next/cache';

async function Message({ id }: { id: string }) {
  const message = await getMessage(id); // 'use cache'：预取阶段就会渲染
  return (
    <>
      <p>{message.subject}</p>
      <div>{message.body}</div>
      <Suspense fallback={<Spinner />}>
        <Thread id={id} />
      </Suspense>
    </>
  );
}

async function Thread({ id }: { id: string }) {
  await navigation(); // 预取到此为止：以下内容只在真实导航时渲染
  const thread = await getThread(id); // 'use cache'
  return (
    <>
      {thread.map((m) => (
        <div key={m.id}>{m.body}</div>
      ))}
    </>
  );
}

两个 API 必须与 'use cache' 模型配合使用；在未被缓存覆盖的位置调用没有延迟效果。选型口诀：外壳太重用 prefetch()，预取太贵用 navigation()。

16.4 新增：ensureStatic 静态保证 ​

即时导航的价值建立在「外壳与预取内容是静态的」之上——但一个不小心的 cookies() 调用就能让整条路由退化为请求时渲染，而且往往到账单或压测时才暴露。16.4 新增路由段配置 ensureStatic，把「必须是静态」从约定变成构建期约束：

tsx
export const ensureStatic = 'navigation'; // 该路由混入任何动态内容时构建失败

export default function Page() {
  return (
    <>
      <UserAvatar /> {/* 🔴 动态组件：构建直接失败 */}
      <Content />    {/* 'use cache'：静态预渲染，合法 */}
    </>
  );
}

三档严格程度，按需选择：

取值保证范围适用场景
'shell'首次发现路由时只取静态外壳允许导航时动态，守住首发现成本
'prefetch'显式预取只取静态内容守住预取成本
'navigation'完整导航也必须静态电商、营销页、博客等纯静态路由

ensureStatic 也可以写在布局上，对该布局下所有页面生效；在根布局声明 ensureStatic = 'navigation' 即可保证全站导航零请求时渲染，个别需要动态内容的路由再往嵌套布局下放。Instant Insights 告诉你「哪里不够即时」，ensureStatic 则保证「这里永远即时」。

Instant Insights：校验规则与可操作错误 ​

默认配置（validationLevel: 'warning'）下，开发环境会自动校验每个 Page 和 Default 段：模拟整页加载与不同层级的客户端导航两种路径，找出会阻塞即时渲染的组件。

ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  cacheComponents: true,
  experimental: {
    instantInsights: {
      validationLevel: 'manual-warning', // 默认 'warning'
    },
  },
};

export default nextConfig;

校验产出的 insight 会点名具体组件，并给出三类修复卡片，恰好对应三选一：

  • Block：在该段加 export const instant = false

用 Navigation Inspector 肉眼验证

Next.js DevTools 的 Navigation Inspector 开启「Pause on navigations」后，会把页面冻结在点击瞬间的初始 UI：刷新看到的是静态外壳，点链接看到的是预取的目标 UI。搭配 React DevTools 的 Suspense 面板，可以确认每个回退边界各盖住哪块区域。校验只证明「外壳存在」，外壳里有没有有意义的内容，要靠人眼（或 E2E）判断。

一个高频 insight 是「URL data outside of Suspense」：在 Suspense 之外读取了 params/searchParams，把外壳绑死到了单个 URL。修法是不要 await，把 Promise 原样下传：

tsx
import { Suspense } from 'react';
import { ProductDetails } from './product-details';

// 页面同步渲染：URL 无关的布局留在共享外壳里
export default function Page({ params }: { params: Promise<{ slug: string }> }) {
  return (
    <ProductLayout>
      <Suspense fallback={<DetailsSkeleton />}>
        <ProductDetails params={params} /> {/* Promise 直接传，不 await */}
      </Suspense>
    </ProductLayout>
  );
}

已知限制与边界 ​

以下限制均需带着「截至 16.4 的已知问题/社区反馈」的视角使用，升级前请重新核对发行说明：

  • 静态导出不兼容：output: 'export' 与 Partial Prefetching 当前不兼容，纯静态站点不要开启
  • 自托管缓存持久性：'use cache' 默认使用进程内内存存储，serverless 多实例间不共享、实例销毁即丢失；官方建议需要持久化时使用 'use cache: remote' 或配置 cache handler
  • styled-jsx 全局样式：社区反馈在缓存组件场景下存在全局样式泄漏的边界问题，使用 styled-jsx 的项目需重点回归样式；Tailwind v4 / CSS Modules 不受此影响
  • DevTools cookie 共享：Navigation Inspector 用 next-instant-navigation-testing cookie 冻结动态内容，cookie 按域名不按端口隔离，本机同时跑多个项目可能互相干扰，切换项目时清掉该 cookie

小结 ​

  • Partial Prefetching 把逐链接的整页预取合并为每路由一份共享 App Shell，外壳由静态、缓存、回退三类内容构成
  • prefetch={true} 是有成本的 URL 级预取，按可见链接计费，只该给「依赖 URL 数据且内容可缓存」的链接
  • Instant Insights 在开发时按整页加载与客户端导航两条路径校验，修复动作就是 Cache/Stream/Block；Navigation Inspector 负责肉眼确认外壳质量
  • 静态导出、自托管多实例、styled-jsx 等边界要带着版本意识评估
