导航慢在哪：不是渲染慢，是「点了才发请求」 ​

基础篇给每个动态 await 做了 Stream / Cache / Block 三选一，进阶篇算清了共享外壳与 prefetch={true} 的成本账。这一篇把两者踩着的底层直觉挑明：导航慢，往往不是因为渲染慢，而是浏览器在点击那一刻才开始发请求——服务器再快，也要等一个完整的往返。预取做的事，就是把这段往返提前到 hover；真正的难点不在「预不预取」，而在颗粒度：整页预取，一屏链接就是一屏带宽；什么都不预取，点击就得干等。Partial Prefetching 的答案是第三条路：静态外壳全量预取，动态洞只预取第一段流。

先立模型：页面 = 外壳 + 动态洞 ​

把 Cache Components 的页面抽象到极致，只剩两种材料。外壳（shell）：与具体 URL 无关的布局、静态内容、缓存内容和 Suspense 回退，任何链接被 hover 时都可以提前拿到；动态洞（hole）：依赖 params/searchParams、或每次请求都要新鲜的数据所在的 Suspense 边界，只能在导航发生后按 URL 现取。预取只针对外壳，洞留给流——这就是「部分」二字的全部含义。

基础篇的三种策略，在这个模型里就是「洞」的三种处理方式，点按后的表现各不相同：

模型点按后表现适用场景
Stream外壳立即上屏，洞的位置先显示回退 UI，数据到达后流式替换每次请求都要新鲜的数据
Cache洞在预取阶段已被填进外壳，点击瞬间整块可见，不存在等待变化不频繁、可接受 stale 窗口的数据
Block放弃外壳先行，等服务器把整段渲染完再一次性切换整页必须同步就绪的段（如支付确认）

注意 Cache 严格说是「消灭洞」而不是「填洞」：'use cache' 命中后，内容直接编入外壳，点按之后那里根本没有洞。模型立住了，下一节的代码就只剩翻译工作。

完整实现：约 70 行的 mini-prefetch ​

下面用纯 TypeScript 把模型跑起来：prefetch(url) 模拟 hover，只拉外壳；navigate(url) 模拟点击，命中缓存走 Stream，未命中退化为 Block。网络用 setTimeout 模拟——外壳 30ms，动态洞 300ms，这个悬殊的差距本身就是教学点：外壳便宜，洞昂贵。

ts
// mini-prefetch.ts —— 即时导航最小模型：可缓存外壳 + 动态洞
// 运行：npx tsx mini-prefetch.ts

type Status = 'prefetching' | 'ready';
type Entry = { shell: string[] | null; status: Status };

/* ---------- 预取缓存：Map 当 LRU 用，上限 5 条模拟「预取预算」 ---------- */
const MAX_ENTRIES = 5;
const prefetchCache = new Map<string, Entry>();

function touch(url: string, entry: Entry): void {
  prefetchCache.delete(url); // 先删再放：刚使用的条目被挪到 Map 队尾
  prefetchCache.set(url, entry);
  if (prefetchCache.size > MAX_ENTRIES) {
    // Map 迭代按插入序，队首即最久未用——超预算就淘汰它
    prefetchCache.delete(prefetchCache.keys().next().value!);
  }
}

/* ---------- 模拟网络：外壳 30ms，动态洞 300ms ---------- */
const fetchShell = (url: string) =>
  new Promise<string[]>((r) => setTimeout(() => r([`【外壳】布局 + 商品骨架（${url}）`]), 30));

const fetchHole = (url: string) =>
  new Promise<string>((r) => setTimeout(() => r(`【洞】实时库存 42 件（${url}）`), 300));

const render = (lines: string[]) => console.log(lines.join('\n'), '\n');

/* ---------- hover 时调用：只拉外壳，绝不碰动态洞 ---------- */
export function prefetch(url: string): void {
  const hit = prefetchCache.get(url);
  if (hit) return touch(url, hit); // 已预取过：只刷新 LRU 位置，不发请求
  const entry: Entry = { shell: null, status: 'prefetching' };
  prefetchCache.set(url, entry);
  fetchShell(url).then((shell) => {
    entry.shell = shell;
    entry.status = 'ready'; // 30ms 后外壳就绪；洞永远不在预取范围内
  });
}

/* ---------- 等一个还在飞行中的外壳（真实框架会存 Promise，这里用轮询简化） ---------- */
function waitShell(entry: Entry): Promise<string[]> {
  return new Promise((r) => {
    const t = setInterval(() => {
      if (entry.shell) { clearInterval(t); r(entry.shell); }
    }, 5);
  });
}

/* ---------- click 时调用：命中 → Stream；未命中 → 退化为 Block ---------- */
export async function navigate(url: string): Promise<void> {
  const hit = prefetchCache.get(url);

  // 未命中：等外壳 + 洞全部返回才切换——这正是传统导航的样子
  if (!hit) {
    render([await fetchShell(url), await fetchHole(url)]);
    console.log('↳ 未预取（Block）：用户等了 330ms 才看到任何内容');
    return;
  }
  touch(url, hit);
  const shell = hit.shell ?? (await waitShell(hit)); // 命中但外壳还在路上：只能等它

  // 命中且就绪：外壳立即上屏（0ms），动态洞的位置先给回退 UI
  render([...shell, '【洞】加载中… ▱▱']);
  console.log('↳ 命中（Stream）：外壳 0ms 上屏，动态洞流式补入中');

  const hole = await fetchHole(url); // 300ms 后流到达，只替换洞那一块
  render([...shell, hole]);
}

/* ---------- 演示 ---------- */
async function main() {
  prefetch('/store/hat'); // hover 链接：30ms 后外壳进缓存
  await new Promise((r) => setTimeout(r, 50));
  await navigate('/store/hat'); // 命中：骨架立即出现，洞 300ms 后补齐
  await navigate('/store/bag'); // 没预取过：Block，等 330ms 整页出现
}
main();

两处细节值得停下来看：

  • Map 的插入序就是免费的 LRU。delete 再 set 把刚用过的条目挪到队尾，队首永远是最久未用的——不必手写双向链表。上限 5 条的「预取预算」对应真实框架对预取流量的克制：进阶篇算过，逐链接预取的成本上限是可见链接数量级，预算就是给这条曲线装的刹车。
  • 未命中路径就是传统导航。缓存没命中时 navigate 要等外壳与洞全部返回才渲染——这正是基础篇说「冷缓存不算数」的原因：预取没发生过，即时性就无从谈起。代码里退化成 Block 不是缺陷，而是诚实的兜底。

全量预取 vs Partial Prefetch：一笔带宽账 ​

手写版里 hover 只花 30ms 拉一个小外壳。反过来想，如果每个链接 hover 都拉整页 payload，同一屏会发生什么：

diff
- // 全量预取：每个链接各自拉整页 payload
- hover('/store/hat') → 布局 + 商品卡 + 库存 + 评论 ≈ 86KB
- hover('/store/bag') → 布局 + 商品卡 + 库存 + 评论 ≈ 86KB
- …… 20 个链接 = 20 份整页载荷，布局部分完全重复
 （hover 扫完全部 20 个链接，用户最终点击了其中一个）
+ // Partial Prefetch：外壳按路由共享，洞按点击补取
+ hover 扫过 20 个链接 → 共享外壳 ×1 ≈ 9KB（布局 + 缓存结构 + 回退 UI）
+ 点击其中 1 个 → 只拉该 URL 的首段流 ≈ 1KB（实时库存）
+ 总载荷从「链接数 × 整页」降到「路由数 × 外壳 + 点击数 × 首段流」

省的不只是带宽：全量预取还把 20 次服务器渲染提前压进 hover 瞬间——与进阶篇「卡片墙不要无脑开 prefetch={true}」是同一条成本曲线，只是换了个观察角度。

价格页与支付页：激进预取的高危区

外壳里的缓存内容有 stale 窗口。用户 hover 时预取到的可能是调价前的旧价格：点击瞬间页面先渲染「旧价格」骨架，几秒后跳变成真实值。如果用户恰好在这几秒内点了「购买」，提交的就是一次基于过期信息的操作——而骨架看上去和真页面毫无区别。这类页面应整页 Block（段级 instant = false），宁可放弃即时性，也不能让用户在错误的信息上做决定。

预取缓存命中但动态洞的流还没到，用户此刻点击「购买」按钮会发生什么？

距离真实的 Next.js 还差什么 ​

这个 200 行不到的玩具跑通了「外壳先行、洞后补」的主干。真实实现在同一条主干上还叠着四层：

  • Router Cache 的客户端分段缓存与失效：玩具里条目被 LRU 淘汰就彻底没了；真实框架把外壳按段存进客户端 Router Cache，并接上 revalidate 与 Server Action 的失效机制，决定外壳什么时候作废重取——只缓存不失效，就成了旧价格事故的温床
  • 两个开关的编译期行为：cacheComponents 与 partialPrefetching 不只是运行时开关。构建期要给每个段标注「外壳能推进到哪」，把外壳编译成可独立响应的产物，hover 请求才有「只拿外壳」可拿
  • Instant Insights 的「不够即时」自动上报：玩具不知道自己退化了。真实框架在开发期模拟整页加载与各级客户端导航，发现外壳路径上有未缓存的动态读取就报错，点名组件并给出 Cache/Stream/Block 修复卡片
  • @next/playwright 的 instant() 防退化：即时性是性能特性，会被人无意改坏。E2E 里用 instant() 断言「点击后外壳在限定时间内可见」，重构破坏了即时导航，红的是测试而不是用户

小结 ​

  • 导航慢的根源是「点了才发请求」；预取的正确颗粒度是外壳全量、动态洞只取首段流
  • 页面 = 可缓存外壳 + 动态洞；Stream / Cache / Block 是洞的三种处理方式，Cache 本质是把洞消灭进外壳
  • Map 插入序即 LRU：预取缓存限 5 条，hover 拉外壳，点击命中走 Stream、未命中诚实退化为 Block
  • 价格与支付类页面应整页 Block：不能让用户在旧价格骨架上做出购买决定
  • 距离真实实现还有四层：Router Cache 分段缓存与失效、两开关的编译期产物、Instant Insights 自动上报、instant() 防退化

导航解决了「页面何时可见」，下一章解决「变更何时生效」。
