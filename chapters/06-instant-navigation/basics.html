痛点：点击之后，用户在等什么 ​

传统客户端导航的时序是这样的：用户点击链接 → 浏览器发出 RSC 请求 → 服务器渲染目标路由（其中可能有慢查询）→ 响应返回 → 页面切换。只要服务器这一步慢，用户看到的就是旧页面纹丝不动，或者整块白屏。等待时长取决于最慢的那个数据请求。

Next.js 16.4 的 Instant Navigations（即时导航） 要消灭的就是这段等待。它的目标定义很具体：

用户点击的那一刻，浏览器就能开始渲染新页面——静态内容、缓存内容、回退 UI 立刻出现，剩余内容由服务器流式补入。

冷缓存不算数

官方明确：即时性的前提是缓存已预热（warm cache）。冷缓存（首次访问、缓存过期后）仍需服务器计算一次，第一次导航可能还是会等。预热之后，后续导航才是即时的。

两个开关 ​

即时导航不是一个 API，而是两个配置开关共同作用的结果：

ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  // 开关一：缓存组件，允许用 'use cache' 标记可缓存内容
  cacheComponents: true,
  // 开关二：部分预取，<Link> 默认预取每条路由的共享外壳
  partialPrefetching: true,
};

export default nextConfig;

  • cacheComponents：启用 Cache Components 模型，页面可以被拆成「静态外壳 + 动态区域」，并允许用 'use cache' 精确指定缓存
  • partialPrefetching：改变 <Link> 的预取行为——视口内的链接只预取一份共享 App Shell，而不是整页

两个开关有依赖关系：partialPrefetching 必须在 cacheComponents 启用后才工作。

核心心智：每个 await 三选一 ​

启用 Cache Components 后，框架在预渲染时会沿着组件树往下走，直到遇到一个「需要等待」的 await（读 params、查数据库、读 cookies() 等）。对这个 await，你只有三种合法处理方式：

策略做法用户看到什么适用数据
Stream（流式）把 await 放进 <Suspense> 包裹的子组件先看到回退 UI（骨架屏），数据到了流式补入每次请求都要新鲜的数据
Cache（缓存）在异步函数内写 'use cache'（可配 cacheLife）内容直接进入外壳，点击瞬间可见变化不频繁、可接受陈旧窗口的数据
Block（阻塞）段文件导出 export const instant = false导航在服务器上阻塞等待（放弃即时性）暂时无法改造、或整页必须同步就绪的段

没有第四种选择：如果一个未缓存、又没包 Suspense 的动态读取出现在外壳路径上，开发时的 Instant Insights 会直接报错。

最小可跑 demo：商品详情页 ​

一个最小但完整的例子。商品详情页 /store/[slug] 取两类数据：商品信息（很少变）和实时库存（每次要新鲜）。

tsx
import { Suspense } from 'react';
import { db } from '@/lib/db';

// 页面本身保持同步、不 await params：外壳不被任何 URL 绑定
export default function ProductPage({ params }: { params: Promise<{ slug: string }> }) {
  return (
    <div>
      {/* Stream：包裹读取 params 的子组件，先给回退 UI */}
      <Suspense fallback={<p>正在加载商品…</p>}>
        <ProductInfo params={params} />
      </Suspense>
      <Suspense fallback={<p>正在查询库存…</p>}>
        <Inventory params={params} />
      </Suspense>
    </div>
  );
}

// Cache：商品信息少变，函数级缓存，结果可进入静态外壳
async function getProduct(slug: string) {
  'use cache';
  return db.products.findBySlug(slug);
}

async function ProductInfo({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params; // await 发生在 Suspense 边界内部
  const product = await getProduct(slug);
  return (
    <>
      <h1>{product.name}</h1>
      <p>¥{product.price}</p>
    </>
  );
}

// Stream：库存不缓存，每次请求实时查询，流式补入
async function Inventory({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const item = await db.inventory.findBySlug(slug);
  return <p>库存 {item.count} 件</p>;
}

记忆口诀

静态内容进外壳，缓存内容进外壳，其余全部下推到 Suspense。 页面组件本身尽量是同步的「壳」，把 await params 和取数下沉到被 <Suspense> 包裹的叶子组件里。

预热后从 /store/shoes 点进 /store/hats：商品名和价格（缓存）瞬间出现，库存区域先显示「正在查询库存…」，随后流式补齐。这就是一次即时导航。

暂时放弃：instant = false ​

不是每条路由都值得立刻改造。在 page.tsx 或 layout.tsx 导出一个段配置，即可让该段「允许阻塞」，不再报即时性错误：

tsx
// 该段进入时可以等待服务器；其下方兄弟段之间的导航仍会被校验
export const instant = false;

export default function DashboardLayout({ children }: { children: React.ReactNode }) {
  return <>{children}</>;
}

常见误区 ​

  • 误区一：开了开关就全站即时。 开关只给能力，路由仍要按 Stream/Cache/Block 改造，由 Instant Insights 逐个驱动。
  • 误区二：在页面顶部 await params。 这会把外壳绑死到某一个 URL，动态段页应把 params Promise 直接下传给 Suspense 内的子组件。
  • 误区三：开发环境里感觉不即时就以为没生效。 开发模式不执行预取，导航手感以 next start（生产）为准；但校验错误在开发时就能看到。

小结 ​

  • 即时导航 = cacheComponents + partialPrefetching 两个开关，加上对每个动态 await 做 Stream/Cache/Block 三选一
  • 缓存内容与静态内容组成点击瞬间可见的外壳，未缓存内容在 Suspense 回退之后流式补入
  • 暂时无法改造的段用 export const instant = false 显式允许阻塞
