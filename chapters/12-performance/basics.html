性能优化的第一性原理 ​

没有度量的优化叫“许愿”。Next.js 16.3 的性能话题分三层：框架默认给你的（Turbopack、服务端组件、代码分割、预取）、一个开关拿到的（React Compiler、缓存组件）、必须自己测量后决策的（bundle 体积、懒加载边界、第三方脚本）。前两层本篇解决，第三层进阶篇展开。

先记住 Core Web Vitals 三个核心指标，所有优化最终都要回答它们：

指标衡量什么关注点
LCP（最大内容绘制）首屏主内容何时出现服务端响应、图片、字体、阻塞脚本
INP（交互到下一次绘制）交互响应是否跟手客户端 JS 体积、长任务、渲染开销
CLS（累计布局偏移）内容是否跳动图片/广告尺寸预留、字体切换

辅助指标还有 TTFB（首字节时间）与 FCP（首次内容绘制）。TTFB 差通常是服务端取数或动态渲染问题，与前端 bundle 无关——先定位层，再动手。

TIP

实验室数据（Lighthouse）用于本地回归，字段数据（真实用户上报）用于决策。两者可能矛盾：高端笔记本上满分的页面，在中端手机弱网下 INP 可能不及格。

React Compiler：一行配置换掉手写记忆化 ​

React 19.2 的 Compiler 能自动分析组件，在安全的地方插入记忆化，省去手写 useMemo/useCallback/React.memo。Next 16 中该特性已稳定，由 SWC 只处理含 JSX/Hook 的文件，构建开销被控制在局部。

先装 Babel 插件（pnpm add -D babel-plugin-react-compiler），再打开开关：

ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  reactCompiler: true, // 16.x 稳定；自动记忆化，先删冗余 useMemo 再开启
};

export default nextConfig;

Turbopack 16.3：更快的 dev 与更省的内存 ​

Turbopack 在 16.x 是默认且稳定的打包器，pnpm dev 与 pnpm build 都走它，无需任何 --turbo 参数。16.3 在它身上有两项与日常开发强相关的变化：

  • dev 内存回收：不活跃的函数级编译结果从内存驱逐到文件系统。官方称在 vercel.com 仪表盘 50 条路由的场景中，内存占用从 21.5GB 降到约 2GB（约 90%，据官方报告）
  • build 磁盘缓存默认开启：next build 复用 .next/cache 中的持久化结果，CI 第二次构建明显变快——前提是 CI 缓存了这个目录（第 13 章配置）

排查诡异缓存问题时可临时关闭内存驱逐：

ts
const nextConfig: NextConfig = {
  experimental: {
    turbopackMemoryEviction: false, // 默认 'auto'
  },
};

度量埋点：useReportWebVitals ​

在 App Router 中，hook 从 next/web-vitals 导入，且必须在客户端组件里。最佳做法是独立一个极小客户端组件挂进根布局，不把整棵树拖进客户端边界：

tsx
'use client';

import { useReportWebVitals } from 'next/web-vitals';

// 回调引用保持稳定，避免重复上报
const report = (metric: { name: string; value: number; rating: string; id: string }) => {
  const body = JSON.stringify(metric);
  // 优先 sendBeacon：页面卸载时也能把数据发出去
  if (navigator.sendBeacon) {
    navigator.sendBeacon('/api/vitals', body);
  } else {
    fetch('/api/vitals', { method: 'POST', body, keepalive: true });
  }
};

export function WebVitals() {
  useReportWebVitals(report);
  return null; // 纯埋点，不渲染 UI
}

第三方脚本：next/script 的四种策略 ​

第三方脚本（统计、客服、A/B）是 INP 和 LCP 的常见杀手。一律用 next/script 而非裸 <script>，并按必要性选策略：

策略时机典型用途
beforeInteractive页面水合前极少数必须前置的脚本
afterInteractive（默认）早期水合后统计、主流分析 SDK
lazyOnload浏览器空闲时客服挂件、低频营销脚本
worker（实验性）Web Worker（Partytown）App Router 尚不支持，谨慎
tsx
import Script from 'next/script';

export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN">
      <body>
        {children}
        {/* 客服组件不抢首屏资源 */}
        <Script src="https://example.com/chat.js" strategy="lazyOnload" />
      </body>
    </html>
  );
}

常见误区 ​

  • 开了 Compiler 就删光手写 memo 并期待提速：它只处理引用稳定性，先看 INP 数据
  • 本地 Lighthouse 满分即收工：缺字段数据，中端设备和弱网才是大多数用户
  • 所有第三方脚本放根布局默认策略：非关键脚本应用 lazyOnload，能延迟一大块主线程工作
  • CI 不缓存 .next/cache 却抱怨构建慢：磁盘缓存只在持久化时生效

小结 ​

  • 性能工程的纪律是度量先行：LCP 看首屏、INP 看交互、CLS 看稳定
  • React Compiler 一行开启自动记忆化；Turbopack 16.3 带来 dev 内存回收与 build 磁盘缓存
  • useReportWebVitals 用独立客户端叶子接字段数据；next/script 按策略安置第三方代码
