场景：移动端评分告急的内容站 ​

假设你接手一个带商品详情的内容站，业务方反馈“手机上点商品卡到能下单要等很久”。没有任何埋点，只有同事一句“感觉挺慢”。优化的目标不是把 Lighthouse 跑分刷满，而是建立可回归的性能预算，让之后每次迭代都知道是否越线。

::: warn 以下任何收益数字都是区间与前提，不是承诺：实际收益取决于设备档位、网络、路由数量与缓存命中率。文中引用官方报告处会显式标注。你要对自己的站点重复同样的测量，而不是照搬数字。 :::

第一步：立预算，埋基线 ​

先与业务约定每条关键路由的预算。参考 Core Web Vitals 的 good 门槛并结合自身设备分布收紧：

指标商品列表（移动 4G）商品详情营销落地页
LCP≤ 2.5s≤ 2.5s≤ 2.0s
INP≤ 200ms≤ 200ms≤ 200ms
CLS≤ 0.1≤ 0.1≤ 0.1
路由首屏 JS（gzip 后）≤ 170KB≤ 200KB≤ 120KB
第三方脚本≤ 2 个，且非阻塞同左统计 1 个

埋点按基础篇的 WebVitals 组件接 Route Handler 落库；本地用生产构建做实验室基线（Lighthouse 无痕窗口），并跑一次 bundle 分析留存：

bash
pnpm build && pnpm start
# 另一终端：
pnpm next experimental-analyze --output
cp -r .next/diagnostics/analyze ./perf-baseline

第二步：定位，而不是猜 ​

::: steps

  1. 字段数据按路由聚合：发现详情页 LCP 中位数 3.8s、列表页 INP p75 约 380ms
  2. LCP 元素定位：详情页首图是裸 <img>，且字体外链导致 LCP 文本二次绘制
  3. 分析器定位 INP：商品卡列表在客户端跑 Markdown 摘要渲染，整条渲染库进了首屏 chunk
  4. 网络面板：根布局挂了 3 个默认策略第三方脚本；商品列表 30 个链接全部 URL 级预取，入屏即 30 次调用 :::

第三步：按优先级修改 ​

先做不改变交互的“低垂果实”，再动结构：

  reactCompiler: true, // 自动记忆化，先在非关键页观察一周再全量

    remotePatterns: [{ protocol: 'https', hostname: 'cdn.example.com' }],
  },
  experimental: {
    optimizePackageImports: ['@your/icons'], // 收敛图标桶导入
  },
};
export default nextConfig;

tsx
import Image from 'next/image';
import { codeToHtml } from 'shiki'; // 仅服务端执行，不进客户端包
import Script from 'next/script';

export default async function ProductDetail({ id }: { id: string }) {
  const product = await getProduct(id);
  const summaryHtml = await codeToHtml(product.summary, { lang: 'md', theme: 'github-dark' });

  return (
    <main>
      {/* 尺寸预留防 CLS；现代格式 + 按需缩放，LCP 图优先加载 */}
      <Image
        src={product.hero}
        width={1200}
        height={630}
        preload // 16 新名（旧 priority 已废弃）
        alt={product.name}
      />
      <section dangerouslySetInnerHTML={{ __html: summaryHtml }} />
      {/* 评价弹层在客户端叶子内 dynamic + ssr:false，见进阶篇 */}
      <ReviewLauncher productId={id} />
      {/* 客服脚本延迟到空闲，统计保持 afterInteractive */}
      <Script src="https://example.com/chat.js" strategy="lazyOnload" />
    </main>
  );
}

列表链接的预取改为分级：主商品卡保留默认外壳预取，只有“精选位”第一条加 prefetch={true}，把 30 次/入屏的服务端调用降到个位数。数据侧给商品摘要加 'use cache' + cacheTag('product-summary')（第 5 章模式），命中后 TTFB 同步改善。

TIP

缓存策略与静态资源是这轮优化的两条暗线：缓存命中降低 TTFB 从而拉低 LCP；next/font 自托管消除字体外链的二次绘制。两者都可以在实验里对照观察——👉 cache-hit 全栈实验 与 👉 styling-assets 全栈实验。

第四步：复测与归档 ​

同一网络节流、同一设备档位复测，对比 .next/diagnostics/analyze 前后两份报告：

bash
pnpm build && pnpm start
pnpm next experimental-analyze --output
mv .next/diagnostics/analyze ./perf-after
# 字段数据观察至少一个完整业务周期（含周末流量）再宣布结论

一个负责任的复盘表述方式是：“在中端安卓机 + 4G 节流的实验室条件下，详情页 LCP 从约 3.8s 降到约 2.4s 区间，主要贡献来自图片优化与摘要渲染上移；字段数据待一周后复核。”——带设备、带网络、带区间、带待验证项。Turborpack 侧 16.4 的 dev 内存回收与 build 磁盘缓存改善开发体感，官方报告在特定 50 路由场景内存降幅约 90%，但那是开发期指标，不计入用户侧 Web Vitals。

最佳实践清单 ​

  • [ ] 关键路由有书面性能预算，新增依赖与第三方脚本需对照预算评审
  • [ ] 字段埋点（useReportWebVitals）与实验室跑分双轨，结论以字段为准
  • [ ] 所有内容图使用 next/image 且声明尺寸；首屏 LCP 图加 preload（旧名 priority 已废弃）
  • [ ] 字体走 next/font，无外链字体请求
  • [ ] 纯“数据→HTML”计算留在服务端，客户端只收标记
  • [ ] 第三方脚本登记造册：默认策略、lazyOnload 或直接移除
  • [ ] prefetch={true} 逐条评审，侧栏列表不滥开
  • [ ] bundle 报告进 PR 模板，体积超预算阻断合并
  • [ ] CI 缓存 .next/cache 与包管理器 store，保证复测环境稳定
  • [ ] 每次优化前后留存分析报告，可 diff、可回溯

小结 ​

  • 性能优化闭环 = 预算 → 基线 → 定位 → 修改 → 复测，数字必须带设备/网络/区间前提
  • 低垂果实（image/font/script/导入收敛）先摘，结构性改动（渲染上移、预取分级、缓存）随后
  • 预算与 bundle 报告进入 PR 流程，性能才能“不回退”而不是“一次性冲刺”
