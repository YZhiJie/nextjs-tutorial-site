从“许愿”到“门禁” ​

实战篇的闭环还停留在流程层：预算表写在文档里，靠人记得核对。工程化的要求是——预算变成每次合并都会自动亮红的门禁（gate），任何路由越线，CI（持续集成，Continuous Integration）就失败。这一篇把它变成可执行代码：读两份 JSON、按「路由 × 指标」比较、用退出码（exit code）说话的校验器（validator），node 直接跑。

数据模型：两份 JSON 的约定 ​

budgets.json（预算表）与 metrics.json（构建实测）都是路由路径 → 指标 → 数值的两层结构，指标含 firstLoadJS（KB，gzip 后）、cssBytes（字节）、lcpMs（毫秒）。预算的键是路由而非全站单一数字：

  "/products/[id]": { "firstLoadJS": 200, "cssBytes": 32000, "lcpMs": 2500 },

流水线：budgets.json → 校验器 → 退出码 ​

整个门禁是一条短路管线，任一 fail 都让退出码非零：

text
budgets.json + metrics.json + baseline.json ──▶ perf-budget.ts（逐路由 × 逐指标比较）
                                                  │
                  pass / warn / fail 结果表 ──▶ 退出码 0（放行）/ 1（阻断）──▶ CI

手写校验器：约 70 行 ​

ts
import fs from 'node:fs';

type Budget = Record<string, Record<string, number>>; // 路由 → 指标 → 阈值
type Metrics = Record<string, Record<string, number>>; // 路由 → 指标 → 实测
type Baseline = Metrics;                               // 上次构建留存的实测
type Status = 'pass' | 'warn' | 'fail';
type Row = { route: string; metric: string; actual: number; budget: number; delta: number; status: Status };

const WARN_RATIO = 0.1; // 超预算 10% 以内算 warn，超过才算 fail
const UNITS: Record<string, string> = { firstLoadJS: 'KB', cssBytes: 'B', lcpMs: 'ms' };

function load<T>(file: string): T {
  return JSON.parse(fs.readFileSync(file, 'utf8')) as T; // metrics 须已是 gzip 后口径
}

function judge(actual: number, budget: number): Status {
  if (actual <= budget) return 'pass';
  return actual <= budget * (1 + WARN_RATIO) ? 'warn' : 'fail';
}

// 逐路由逐指标比较，同时算相对上次构建的回归量 delta
function check(budgets: Budget, metrics: Metrics, baseline: Baseline): Row[] {
  const rows: Row[] = [];
  for (const [route, spec] of Object.entries(budgets)) {
    const actual = metrics[route];
    if (!actual) {
      // 预算表里有、产物里没有：路由被删或改名，直接判 fail
      rows.push({ route, metric: '*', actual: 0, budget: 0, delta: 0, status: 'fail' });
      continue;
    }
    for (const [metric, budget] of Object.entries(spec)) {
      const value = actual[metric] ?? 0;
      const prev = baseline[route]?.[metric];
      rows.push({
        route,
        metric,
        actual: value,
        budget,
        delta: prev === undefined ? 0 : value - prev,
        status: judge(value, budget),
      });
    }
  }
  return rows;
}

function print(rows: Row[]): void {
  const pad = (s: string, n: number) => s + ' '.repeat(Math.max(1, n - s.length));
  console.log(pad('路由', 22) + pad('指标', 12) + pad('实测', 12) + pad('预算', 12) + pad('Δ', 10) + '结论');
  for (const r of rows) {
    const sign = r.delta >= 0 ? '+' : '';
    const unit = UNITS[r.metric] ?? '';
    console.log(
      pad(r.route, 22) + pad(r.metric, 12) + pad(`${r.actual}${unit}`, 12) +
      pad(`${r.budget}${unit}`, 12) + pad(`${sign}${r.delta}`, 10) + r.status.toUpperCase()
    );
  }
}

const budgets = load<Budget>('budgets.json');
const metrics = load<Metrics>('metrics.json');
const baseline = fs.existsSync('baseline.json') ? load<Baseline>('baseline.json') : {};
if (!metrics) { console.error('缺少 metrics.json，无法校验'); process.exit(1); }

const rows = check(budgets, metrics, baseline);
print(rows);

const failed = rows.filter((r) => r.status === 'fail');
const warned = rows.filter((r) => r.status === 'warn');
console.log(`\n${rows.length} 项检查：${failed.length} 项 FAIL，${warned.length} 项 WARN`);
if (failed.length > 0) process.exit(1); // 非零退出码 = 门禁失败

四个关键原理 ​

① 预算按「路由 × 指标」粒度 ​

全站一个“总包 ≤ 640KB”的门禁几乎必然失察：列表页瘦 30KB、详情页胖 50KB，总量只涨 20KB 看似安全，用户真正访问的详情页却变慢了。粒度落到「路由 × 指标」，回归发生在哪条路由、哪个指标才一目了然。

② 门禁用 gzip 后体积 ​

自测

体积门禁为什么用 gzip 后体积，而不是源码体积或未压缩体积？

③ 回归对比 baseline 优于绝对阈值 ​

绝对阈值只答“是否越线”，baseline（基线）对比答“这次改动是否造成回退”。一条仍在预算内的路由，若某次提交让它涨 15%，也值得拦截——把上次构建的 metrics 留存为 baseline.json，校验器顺带打印 delta 列。

④ 退出码即门禁 ​

CI 判断成败只看退出码：process.exit(1) 就是红灯。把校验器作为流水线一步，超预算即阻断合并。

bash
node perf-budget.ts           # FAIL 时退出码为 1，直接中断流水线
cp metrics.json baseline.json # 通过后把本次度量留作下次基线

幼稚实现 vs 正确实现 ​

最常见的错误门禁是“只看总包”：

diff
- // 只看全站总量：单路由回退被其他路由的收益平均掉
- const total = metrics.sumFirstLoadJS;   // 例如 620KB
- return total <= BUDGET.totalJS ? 0 : 1; // 620 < 640，永远绿
+ // 按「路由 × 指标」逐条比较：任何一条越线都单独暴露
+ for (const [route, spec] of Object.entries(budgets))
+   for (const [metric, budget] of Object.entries(spec)) {
+     if (metrics[route][metric] > budget) return fail(route, metric);
+   }

总量门禁的致命伤是平均效应：一条路由回退 50KB、另一条优化省下 60KB，总量反降，门禁放行——而用户还留在变慢的页面上。逐路由比较把回归还原到它真实发生的位置。

对照真实的 next build 输出 ​

next build 的路由表有三类符号与两列体积：○ Static（构建期预渲染为静态 HTML）、● SSG（用 generateStaticParams 预渲染）、ƒ Dynamic（请求时按需服务端渲染）；两列是 Size（该路由自身 JS）与 First Load JS（该路由 + 全站共享包）。门禁应锚定 First Load JS——共享包膨胀会同时抬高所有路由，逐路由比较立刻能发现这类回归。定位“体积来自哪个依赖”则用 @next/bundle-analyzer（Webpack）或 next experimental-analyze（Turbopack，本教程 16.3 主路径）看 treemap 与导入链，而不是猜。校验器的 firstLoadJS 须与这两列同为 gzip 后口径，否则永远对不上。

反例与陷阱 ​

DANGER

只看总包体积：单路由回退会被其他路由的收益平均掉，门禁持续绿灯，用户却在对的页面上变慢。粒度必须落到「路由 × 指标」。

::: warn 拿开发环境体积当生产预算：next dev 含 HMR 与调试代码，数字远高于生产，基线必须在 next build && next start 下采集。阈值定得死板导致噪音失败（flaky gate）：阈值卡在实测值正上方，任何无关补丁都触发红牌，团队很快开始无视门禁；用 warn 缓冲带（本例 10%）区分“关注”与“阻断”。 :::

小结 ​

  • 性能预算的落地形态是可执行校验器：budgets.json（路由 × 指标）× metrics.json（构建实测），逐条比较产出 pass/warn/fail
  • 门禁四原理：粒度到「路由 × 指标」、用 gzip 后体积、对 baseline 看 delta 防回退、以退出码接入 CI
  • 只看总量会被平均效应掩盖回归；开发环境体积与死板阈值是两类典型噪音源
  • 真实对照面：next build 的 ○/●/ƒ 与 First Load JS 列，@next/bundle-analyzer / experimental-analyze 定位体积来源
