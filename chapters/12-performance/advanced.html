定位体积：先有地图再开枪 ​

“感觉包很大”无法指导优化。16.3 默认打包器是 Turbopack，对应的主路径分析器是官方随包的实验性工具（v16.1 起提供），它直接读 Turbopack 模块图，能展示每个模块的完整导入链：

bash
pnpm next experimental-analyze            # 打开交互式 treemap
pnpm next experimental-analyze --output    # 落盘到 .next/diagnostics/analyze，便于 diff
1
2

在 UI 中按路由、环境（client/server）、类型（JS/CSS/JSON）过滤；点开大矩形即可看到“谁导入了它”。优化前后各 --output 一次，拷贝目录做对比，比凭感觉可靠。

如果你为特定场景切回了 Webpack，则使用老牌的 @next/bundle-analyzer，配合 ANALYZE=true pnpm build 出报告。两套工具不要混用：

工具打包器状态输出
next experimental-analyzeTurbopack实验性（官方持续迭代中）交互 UI + 磁盘报告
@next/bundle-analyzerWebpack稳定treemap HTML

::: warn 实验性分析器的界面与 CLI 参数可能随版本调整。以你本机随包文档 02-guides/package-bundling.md 为准；本教程锚定 16.3 的命令是 experimental-analyze。 :::

大依赖的三类修法 ​

① 多导出包：收敛导入

图标、工具类库常因桶文件（barrel export）把几百个模块拖进来。optimizePackageImports 让打包器只装实际用到的模块；部分热门库已被框架自动优化，无需列入：

ts
const nextConfig: NextConfig = {
  experimental: {
    optimizePackageImports: ['icon-library'], // 按实际包名填写
  },
};

② 重型客户端工作：上移到服务端

语法高亮、Markdown 渲染、图表库这类“数据 → HTML”的纯计算，放在客户端组件里会把整个引擎发给浏览器。改成服务端组件执行，客户端只收渲染好的标记：

tsx
import { codeToHtml } from 'shiki';

export async function CodeBlock({ code }: { code: string }) {
  const html = await codeToHtml(code, { lang: 'tsx', theme: 'github-dark' });
  // shiki 只在服务端运行，完全不进客户端 bundle
  return <div dangerouslySetInnerHTML={{ __html: html }} />;
}

③ 服务端重依赖：排除打包

服务端组件与 Route Handler 导入的包默认会被打包。带有原生二进制或大型 Node 生态依赖（如部分 ORM、PDF 引擎）时，用 serverExternalPackages 排除，改从 node_modules 直接 require：

ts
const nextConfig: NextConfig = {
  serverExternalPackages: ['package-name'], // 仅服务端生效
};

next/dynamic：懒加载边界划在哪里 ​

懒加载只适用于客户端组件与浏览器侧库。服务端组件本身已自动按段代码分割，应交给流式渲染（第 4 章）而不是 dynamic。

tsx
'use client';

import { useState } from 'react';
import dynamic from 'next/dynamic';

// ssr:false 只能出现在客户端组件中
const PreviewModal = dynamic(() => import('./preview-modal'), {
  loading: () => <p className="muted">正在加载预览…</p>,
  ssr: false,
});

export function ModalLauncher() {
  const [open, setOpen] = useState(false);
  return (
    <>
      <button className="primary" onClick={() => setOpen(true)}>
        打开预览
      </button>
      {open && <PreviewModal onClose={() => setOpen(false)} />}
    </>
  );
}

DANGER

两条硬约束：ssr: false 在服务端组件中直接报错；服务端组件里 dynamic 导入客户端组件时不支持自动代码分割。需要 ssr: false 时，把 dynamic 调用挪进客户端叶子。

Turbopack 还支持专属魔注释：/* turbopackIgnore: true */ 跳过打包（运行时取模块）、/* turbopackOptional: true */ 抑制可选模块的构建报错。注意仅对动态 import() 生效。

预取调优：即时性是有单价的 ​

第 6 章建立了即时导航模型，这里从成本角度做决策。预取不是“开越多越好”：

方式预取内容成本适用
默认（链接入屏）共享路由外壳低，多个链接合并普通导航
<Link prefetch={true}>该 URL 的完整数据（params/searchParams）每个链接一次服务端调用高确定性入口（搜索结果首条、主 CTA）
export const instant = false不参与即时校验退回阻塞渲染迁移过渡期、重个性化页

::: warn 侧栏里铺 50 个 /orders/[id] 链接且全加 prefetch={true}，等于入屏瞬间发起 50 次服务端调用。官方明确建议只在“等待确实值得”的链接上按条加。开启 URL 级预取还需要 partialPrefetching，且与静态导出（output: 'export'）当前不兼容。 :::

CDN 缓存：看懂 Next 下发的 Cache-Control ​

Next 按渲染策略自动设置缓存头，CDN 尊重它们就能正确缓存：

路由类型典型 Cache-Control
纯静态页s-maxage=31536000
ISR 页s-maxage={revalidate}, stale-while-revalidate=...
动态页 / Draft Modeprivate, no-cache, no-store, max-age=0, must-revalidate
/_next/static/*public, max-age=31536000, immutable（内容哈希文件名）

两个部署事实必须知道：

  1. on-demand 失效不会自动传播到 CDN。revalidateTag()/revalidatePath() 只失效 Next 服务端缓存，CDN 副本要到 TTL 到期才更新。要求即时一致时，在失效调用后主动 purge CDN 对应键（含 HTML 与 RSC 两种变体）
  2. RSC 头不能被 CDN 剥离，_rsc 查询参数必须进缓存键。剥掉会导致 RSC 请求拿到 HTML，客户端导航整体退化为整页刷新。proxy.ts 应位于 CDN 缓存之前，作为鉴权与重写的事实源

内存占用排查 ​

dev 或 build 出现内存吃紧时，官方给的排查顺序：

::: steps

  1. 先用 Bundle Analyzer 清点异常庞大的依赖，能删则删
  2. node --heap-prof node_modules/next/dist/bin/next build 生成 .heapprofile，在 Chrome DevTools 加载定位
  3. 需要持续观察时用 next build --experimental-debug-memory-usage，接近内存上限会自动抓堆快照，也可发 SIGUSR2 手动抓
  4. 确认是否服务启动时预加载模块导致基线偏高——可用 experimental.preloadEntriesOnStart: false 对照 :::

不要用“关闭类型检查/关 source map”作为常规手段，那只适合 CI 已有独立静态分析环节时的临时救急。

React Compiler 不覆盖什么 ​

  • 渲染中触发的昂贵计算仍应自己 useMemo 或下沉（如大数组排序）
  • context 值变化引发的整棵消费树重渲染，需要拆分 Provider 粒度
  • 命令式副作用、事件处理器逻辑不在编译优化范围
  • 极动态写法可在文件内用 'use no memo' 局部退出，而不是全局关闭

小结 ​

  • 体积优化四板斧：Turbopack 分析器定位 → 收敛多导出导入 → 重活上移服务端 → 懒加载客户端叶子
  • ssr: false 只能在客户端组件；prefetch={true} 每链一调用，按价值投放
  • CDN 靠标准缓存头工作；on-demand 失效需配合主动 purge，RSC/_rsc 不可剥离
  • 内存问题先量化（heapprofile）再处理，Compiler 不替你修算法与 Provider 结构

实战篇我们会立一份性能预算表，走一遍“测量 → 定位 → 修改 → 复测”的完整优化叙事。
