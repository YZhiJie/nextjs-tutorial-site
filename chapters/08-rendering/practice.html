场景：一个更新频繁的技术博客 ​

博客是渲染模式的「集大成场景」：

  • 文章详情页有几千篇，90% 的流量集中在最新 20 篇
  • 首页和列表几分钟可以容忍滞后，但作者点了发布就要立刻看到
  • 草稿预览必须是实时的个性化内容
  • RSS、sitemap 要随文章更新

如果全用 SSR，每篇文章的每次访问都付一次服务器成本；如果全用 SSG，任何笔误修正都要整站重发版。正确答案是按页面、甚至按区域混合策略。

第一步：给每种页面定策略 ​

页面策略理由
/about、/termsSSG（纯静态）几乎不变，CDN 直接服务
文章列表 /blogISR，revalidate = 300容忍 5 分钟滞后，发布时再按需失效
热门文章 /blog/[slug]generateStaticParams 预渲染 + ISR 60 秒热点零成本，修正快速生效
长尾文章首次访问按需生成 + 后台再生不为零访问页面付构建时间
草稿预览 /preview/[id]动态（读 cookie 授权）个性化、实时、不可缓存

不要在构建期预渲染所有文章

官方对 Cache Components ISR 的建议同样适用于经典模型：只预渲染受益最明确的路径（热门、可预测的内容），不常访问的页面按需生成。每多一个预渲染页面，都是构建时间与存储成本。

第二步：详情页与列表页 ​

tsx
import { notFound } from 'next/navigation';
import { getPost, getHotPostSlugs } from '@/lib/posts';

export const revalidate = 60; // 经典模型：60 秒 stale-while-revalidate

export async function generateStaticParams() {
  const slugs = await getHotPostSlugs(20); // 只预渲染最热的 20 篇
  return slugs.map((slug) => ({ slug }));
}

export default async function PostPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const post = await getPost(slug); // 未预渲染路径首次访问时按需生成
  if (!post) notFound();

  return (
    <article>
      <h1>{post.title}</h1>
      <time dateTime={post.publishedAt}>{post.publishedAt}</time>
      <div>{post.content}</div>
    </article>
  );
}

第三步：发布即再生（on-demand） ​

秒级窗口对作者体验仍然太慢。在后台的发布 Action 里调用 revalidatePath，发布与改稿后立刻安排对应路径再生：

ts
'use server';

import { revalidatePath } from 'next/cache';
import { redirect } from 'next/navigation';
import { getSession } from '@/lib/auth';
import { db } from '@/lib/db';

export async function publishPost(formData: FormData) {
  const session = await getSession();
  if (session?.user?.role !== 'editor') throw new Error('无权限'); // 服务端重复鉴权

  const title = String(formData.get('title') ?? '');
  const content = String(formData.get('content') ?? '');
  const post = await db.post.create({ data: { title, content, status: 'published' } });

  // 先失效、后跳转：redirect 会抛控制流异常，其后的代码不执行
  revalidatePath('/blog');              // 列表页
  revalidatePath(`/blog/${post.slug}`); // 详情页
  revalidatePath('/sitemap.xml');       // 站点地图（文件约定同样可按路径失效）
  redirect(`/blog/${post.slug}`);
}

外部 CMS 的 webhook 不经过 Action，改用 Route Handler 接收并调用 revalidateTag('posts', 'max')（16 的新模型要求第二个参数传缓存 profile），即可由内容系统驱动再生。

第四步（可选）：升级到 Cache Components 版本 ​

当博客进一步要求「列表点进详情即时打开」时，把详情页迁移到第 6 章的结构：generateStaticParams 至少返回一篇用于产出外壳，页面把 params 下推到 Suspense 叶子，取数函数改用 'use cache' + cacheLife('minutes') + cacheTag('posts')，发布 Action 改用 updateTag('posts') 让作者立即看到自己的新稿。两个版本可以在不同路由组灰度并存。

::: warn 元数据也要跟着缓存走 文章页的 generateMetadata 若直接查库，在 Cache Components 下会阻塞外壳。给它复用同一个加了 'use cache' 的 getPost(slug)（配合 React cache() 去重），元数据与正文只查一次。 :::

渲染策略选型决策表 ​

诉求选择关键 API/配置
内容基本不变，追求零成本分发SSG无动态输入即可，必要时 output: 'export'
内容会变、可容忍秒级/分钟级滞后ISR（经典）generateStaticParams + export const revalidate
编辑后必须立刻更新ISR + 按需再生Action 内 revalidatePath / updateTag
每用户不同、必须实时动态 SSRcookies()/headers()/searchParams
组件级混合 + 即时导航Cache ComponentscacheComponents + 'use cache' + Suspense
非确定性输出但不读请求信息软动态await connection() 后执行
纯外部系统触发的再生Route HandlerrevalidateTag(tag, 'max')

最佳实践清单 ​

  • [ ] 先按「变化频率 × 实时性要求」给每个页面定级，再选策略，而不是全站一刀切
  • [ ] generateStaticParams 只返回高价值路径；构建后检查 Route 表标记是否符合预期
  • [ ] 再生路径与标签提前在数据层规划：列表一个标签、详情一个 post-${id} 标签
  • [ ] 发布动作把「失效 → 跳转」顺序写对，并对 sitemap/RSS 一并失效
  • [ ] 404 走 notFound() 并配好 not-found.tsx，不要依赖 dynamicParams: false（Cache Components 下不受支持）
  • [ ] 草稿/预览走独立动态路由 + 鉴权，与公开静态路由物理隔离
  • [ ] 再生失败要有监控：ISR 失败时用户会持续拿到旧页

上线前检查 ​

  • [ ] 发布一篇新文章后，列表页与详情页在下一次请求即更新（无需发版）
  • [ ] 修正旧文章后，ISR 窗口内外的表现都符合预期
  • [ ] 未预渲染的老 URL 首次访问可打开，不存在的 slug 返回 404
  • [ ] 草稿链接在未登录会话下被拒绝
  • [ ] next build 的 Route 表与策略表一致（○/ƒ/ISR 标记各就其位）

小结 ​

  • 真实内容站是混合架构：静态页零成本、ISR 兜长尾、on-demand 保发布时效、动态路由留给个性化预览
  • revalidatePath 精确失效、revalidateTag(tag, 'max') 承接外部系统、updateTag 服务读己所写
  • 选型表与 Route 表互相对照，是防止「策略漂移」的最有效手段
