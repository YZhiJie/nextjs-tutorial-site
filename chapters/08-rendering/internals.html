从现象到原理：判定其实是一道可计算的题 ​

前三篇讲的是现象与经验：什么让路由变动态（8.1）、Cache Components 把边界下沉到组件（8.2）、博客该怎么按页选型（8.3）。这一篇换个视角——把经验收敛成一个纯函数。给它一组关于页面的「事实」，它返回一种模式，外加一句「为什么」。

它不依赖 Next 运行时，也不需要跑 next build：输入是你自己声明的信号，输出是可打印的判定结果。写完之后再回头对照框架的真实产物，差距就变成了可解释的规则。

页面的事实（信号）                纯函数                结论
──────────────────────────        ──────────────        ───────────────
readRequestInput?  dynamicSeg?    decideRenderMode()    static  ○
hasGSP?  revalidate?  cc?         （按优先级短路）      isr     ●
                                                        ssr     ƒ
                                                        partial ƒ

输入信号：页面里可读的四个事实 ​

判定器的输入抽象成一个 ctx 对象。每个字段都对应一条你在代码里能直接观察到的声明，而不是运行时才知道的状态：

信号从哪读出来它指向什么
readRequestInput渲染链是否触达 cookies() / headers() / searchParams强制动态
dynamicSegment路径是否含 [slug] 这类动态段参数是否构建期已知
hasGenerateStaticParams是否导出 generateStaticParams能否在构建期枚举路径
revalidate是否写了 export const revalidate = N静态产物的再生窗口
cacheComponents配置里是否开启默认语义是动态还是静态

注意 readRequestInput 才是真正的「动态信号」，revalidate 与 generateStaticParams 都只是调度策略。把这两类信号混在一起，是判定器写歪的第一步。

输出：模式枚举 + 理由字符串 ​

只返回一个枚举值不够用——8.3 的决策表告诉我们，理由才是最该被打印的东西。所以让函数返回一个对象：模式、一句理由、以及一个能对上 next build 的标记符号：

ts
type RenderMode = 'static' | 'isr' | 'ssr' | 'partial';
type Decision = { mode: RenderMode; reason: string; routeMark: string };

判定优先级：谁先命中谁说了算 ​

优先级是一条短路链（short-circuit chain）：从上往下，第一个命中的分支直接返回，后面的不再评估。顺序本身就是最容易被忽视的「隐式规则」：

text
① 动态信号  readRequestInput ─────────► ssr
② 再生窗口  revalidate > 0 ───────────► isr
③ 动态段    dynamicSegment + hasGSP ──► static（构建期枚举）
            dynamicSegment 无 hasGSP ─► ssr（params 属请求时输入）
④ 默认      无动态输入（经典模型） ───► static
            无动态输入（cacheComponents）► partial

顺序颠倒会出错：如果先判「有没有 generateStaticParams」再判「有没有动态信号」，一个既读 cookies() 又写了 generateStaticParams 的路由会被误判成静态——真实情况是动态输入一票否决，generateStaticParams 根本救不回来。

完整实现：约 70 行的 decideRenderMode ​

ts
type RenderMode = 'static' | 'isr' | 'ssr' | 'partial';

type Decision = { mode: RenderMode; reason: string; routeMark: string };

type RenderContext = {
  readRequestInput: boolean;        // 触达 cookies()/headers()/searchParams
  dynamicSegment: boolean;          // 路径含 [slug] 这类动态段
  hasGenerateStaticParams: boolean; // 导出了 generateStaticParams
  revalidate: number | null;        // 显式声明；null 表示「缺省」
  cacheComponents: boolean;         // 是否开启 Cache Components
};

function decideRenderMode(ctx: RenderContext): Decision {
  /* ① 动态信号最高优先：一票否决，静态与 ISR 全部让位 */
  if (ctx.readRequestInput) {
    return {
      mode: 'ssr',
      reason: '渲染链触达 cookies()/headers()/searchParams，非请求期不可渲染',
      routeMark: 'ƒ',
    };
  }

  /* ② revalidate > 0 → ISR：仍是静态产物，但带后台再生窗口 */
  if (ctx.revalidate !== null && ctx.revalidate > 0) {
    return {
      mode: 'isr',
      reason: `静态产物 + ${ctx.revalidate}s 后后台再生（ISR）`,
      routeMark: '●',
    };
  }

  /* ③ 动态段：构建期能否枚举路径，决定它是静态还是动态 */
  if (ctx.dynamicSegment) {
    if (ctx.hasGenerateStaticParams) {
      return {
        mode: 'static',
        reason: 'generateStaticParams 在构建期枚举路径，params 构建期已知',
        routeMark: '○',
      };
    }
    return {
      mode: 'ssr',
      reason: '动态段未预渲染，params 本身就是请求时输入',
      routeMark: 'ƒ',
    };
  }

  /* ④ 默认分支：经典模型自然静态，Cache Components 下转为部分预渲染 */
  if (ctx.cacheComponents) {
    return {
      mode: 'partial',
      reason: 'Cache Components 默认动态；静态需显式 opt-in（use cache + 外壳）',
      routeMark: 'ƒ',
    };
  }
  return {
    mode: 'static',
    reason: '无任何请求时输入，构建期自然预渲染',
    routeMark: '○',
  };
}

两处值得停下来看：① 一定要排在最前，因为「动态输入」是事实层面的不可逆约束；理由字符串写具体（带上 60s、带上具体 API 名），因为它是排查「为什么这页是 ƒ」时唯一的线索。

对照真实：next build 的路由清单 ​

判定器的 routeMark 就是照着构建产物设计的。next build 结束时打印的 Route 表，标记含义为：

text
○  (Static)   构建期产出 HTML，每次请求直接命中静态文件      → mode: static
●  (SSG)      构建期产出 + 增量再生（ISR / 预渲染动态段）      → mode: isr / static
ƒ  (Dynamic)  请求期执行，结果不缓存                          → mode: ssr / partial
1
2
3

于是「判定器输出」和「构建产物」可以互相校验：判定为 static 的路由，构建表里应该是 ○；判定为 isr 的应是 ●；判定为 ssr 或 partial 的应是 ƒ。两边对不上，就是某条信号的读取漏了。

cacheComponents 时代：默认动态，显式 opt-in ​

开启 cacheComponents 后，判定器的第 ④ 步被改写：默认从 static 翻转为 partial。静态不再「自然发生」，而是一个必须显式声明的选择——把静态部分包进缓存边界、动态部分包进 Suspense，外壳即刻响应、参数区流式补入。

与经典链的差异

经典模型下「没有动态输入 ⇒ 静态」，是默认给静态；Cache Components 下是默认给动态，静态要靠 'use cache' 主动争取。这就是 8.2 说的「默认动态、显式 opt-in 缓存」在判定器里的具体形态。

三个陷阱：判定器也会看走眼 ​

判定器再准，也只能对你喂进去的信号负责。下面三种情况，问题都出在信号本身失真：

陷阱一：把 ISR 当成纯静态

看到构建表是 ● 就当「静态」对待，于是内容更新后仍以为要发版才生效——实际它会在 revalidate 窗口后后台再生，也可能被 revalidatePath 立即失效。● 与 ○ 语义不同：一个是「静态 + 再生」，一个是「纯静态」。

::: warn 陷阱二：动态传染藏在 helper 里 readRequestInput 常常不是页面直接读出来的。它可能藏在某个被封装的 getSession()、某个第三方 SDK 的初始化里，一线 cookies() 调用就让整个渲染链变动态。判定器此时会如实报告它拿到的信号，但它拿不到「信号的来源」——所以「这页为什么是 ƒ」的答案，往往在依赖树深处，而不是页面文件里。 :::

陷阱三：revalidate = 0 不等于「缺省」。 缺省（null）是「不声明，让框架按有无动态输入自然判定」；revalidate = 0 是显式声明「不要缓存、每次都要新鲜」，语义上更接近动态。判定器里用 number | null 区分二者，正是为了防止把「显式不缓存」误当成「没说」。若用 0 表示缺省，这条路由的再生行为就被静默改写了。

自测

某路由既没写任何 dynamic 声明、也没有 revalidate，但 next build 把它标成了 ƒ。判定器把它判为动态，最可能的两种原因是什么？

小结 ​

  • 渲染模式判定是一道可计算的题：把页面事实喂给纯函数，返回模式 + 理由 + 构建标记
  • 优先级是一条短路链：动态信号一票否决 → revalidate > 0 走 ISR → 动态段看 generateStaticParams → 最后才是默认
  • routeMark 与 next build 的 ○ / ● / ƒ 对表，可用来反查漏读的输入信号
  • 三种失真值得警惕：把 ISR 当纯静态、动态传染藏在 helper 里、revalidate = 0 被当成缺省

判定器把「模式与时机」收敛成规则后，渲染这条主线就讲完了——下一章转向Route Handlers 与 proxy.ts，看请求在到达页面之前要穿过哪几层。
