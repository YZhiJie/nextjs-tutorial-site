三个决策，一段管线 ​

14.1 拍板了三件事：多租户怎么隔离、缓存怎么分层、i18n 怎么做。它们在实现层交汇在同一段代码里——请求进入路由树之前的那一层，也就是 16.3 里由 middleware.ts 迁移而来的 proxy.ts（Node 运行时，见 9.2）。

管线只有三个判定，每个判定产出一个动作：

text
GET https://app.acme.com/invoices
  │ ① 解析租户     host → tenant        → 未命中：404 落地页
  │ ② 解析语言     路径/cookie/请求头     → 未命中：回落默认语言
  │ ③ 改写或跳转    内部路径 + 注入请求头
  ▼
内部渲染 /zh/invoices，请求头带 x-tenant: acme / x-locale: zh

① 从 host 解析租户 ​

两种常见的承载方式，实现上是「先精确、后通配」的顺序问题：

  • 自定义域：app.acme.com → 租户 acme，走精确匹配
  • 平台子域：acme.teamhub.app → 租户 acme，走「后缀是平台域 + 取第一段」的规则

顺序不能反。先做通配匹配会把 app.acme.com 误判成某个名叫 app 的租户——这正是 2.4 里「静态段必须优先于动态段」的同一条道理：越具体的规则越先匹配。

② 语言从哪里来 ​

三条来源，优先级从高到低：URL 路径段 → 用户偏好（cookie）→ 请求头 Accept-Language → 租户默认值。

但优先级不等于都要参与渲染。这套管线里，cookie 与请求头只用来决定跳转到哪个 URL，真正渲染时用的语言始终来自路径段——原因见下一节。

③ 改写与跳转：两个动作，两种语义 ​

rewrite（改写）和 redirect（跳转）经常被混用，它们的区别决定了 SEO 与用户体验：

rewriteredirect
地址栏不变变成新地址
导航历史不产生新条目产生一条（浏览器行为）
典型用途隐藏内部结构、个性化入口把「不规范地址」纠正成唯一地址
状态码无（内部改写）308 永久 / 307 临时

本站的规则是：

  • /invoices 缺少语言段 → 308 跳到 /zh/invoices。地址不规范，搜索引擎也只应记住规范地址
  • /xx/invoices 里的 xx 不被该租户支持 → 307 跳回默认语言。这是「用户走错了」，不是「地址变了」
  • 带合法语言段的请求 → rewrite 到内部路径，地址栏保持用户看到的那个，请求头带上租户与语言

④ 为什么 locale 要进 URL，而不是进 cookie ​

这是全章最关键的一条工程取舍。

如果页面直接读 cookie 决定语言，那么渲染结果依赖于请求上下文——页面立刻变成动态渲染（动态信号），静态化与 ISR 全部失效；更糟的是同一个 URL 对不同用户产出不同内容，CDN 无法共享任何缓存。

把语言放进路径后，URL 唯一确定了内容：/zh/invoices 永远是中文账单页，可以被 ○ 静态化、可以被 use cache 缓存、可以放心地交给 CDN。cookie 退化成一个纯跳转提示，只在 proxy 层参与一次 308 决策，从不进入渲染。

DANGER

缓存键里漏掉租户，等于跨租户数据泄漏。x-tenant 请求头只是传递，不是隔离。在 Cache Components 下，凡是按租户取数的缓存条目都必须把租户写进标签：cacheTag('tenant:' + slug)，并在租户数据变更时定向失效（14.2 模块三）。这类 bug 的可怕之处在于它不报错、只在「另一个租户的请求恰好命中同一份缓存」时才现形——属于必须靠代码评审与 13.x 的端到端用例兜住的类型。

手写：约 70 行的改写管线 ​

整条管线写成一个纯函数：进请求描述，出决策对象，不碰响应对象也不碰数据库——这样才能被单测覆盖（9.2 里 proxy 层该有多薄，这里给出了具体形态）。

ts
type Tenant = {
  slug: string;             // 内部标识，也是缓存标签的前缀
  host?: string;            // 自定义域名；为空表示走 <slug>.teamhub.app
  locales: string[];
  defaultLocale: string;
};

const ROOT_DOMAIN = 'teamhub.app';

const TENANTS: Tenant[] = [
  { slug: 'acme', host: 'app.acme.com', locales: ['en', 'zh'], defaultLocale: 'en' },
  { slug: 'globex', locales: ['zh'], defaultLocale: 'zh' },
];

type Decision =
  | { kind: 'not-found' }
  | { kind: 'redirect'; pathname: string; status: 307 | 308 }
  | { kind: 'rewrite'; pathname: string; headers: Record<string, string> };

/** ① 租户解析：自定义域精确优先，平台子域次之 */
function resolveTenant(host: string): Tenant | undefined {
  const bare = host.split(':')[0].toLowerCase();
  return (
    TENANTS.find((t) => t.host === bare) ??
    TENANTS.find(
      (t) => bare.endsWith(`.${ROOT_DOMAIN}`) && bare.split('.')[0] === t.slug,
    )
  );
}

/** ② 路径切段：剥离可选的 locale 前缀，返回剩余路径 */
function splitLocale(pathname: string): { locale: string | null; rest: string } {
  const [, first = '', ...tail] = pathname.split('/');
  const looksLikeLocale = /^[a-z]{2}(-[A-Z]{2})?$/.test(first);
  return looksLikeLocale
    ? { locale: first, rest: '/' + tail.join('/') }
    : { locale: null, rest: pathname };
}

/** ③ 改写：地址栏不变，内部渲染带语言段的路径，并注入上下文 */
function rewrite(tenant: Tenant, locale: string, rest: string): Decision {
  return {
    kind: 'rewrite',
    pathname: rest === '/' ? `/${locale}` : `/${locale}${rest}`,
    headers: { 'x-tenant': tenant.slug, 'x-locale': locale },
  };
}

/** 判定 + 动作：整条管线的唯一出口，纯函数，可单测 */
export function routeRequest(req: {
  host: string;
  pathname: string;
  acceptLanguage?: string;
  cookieLocale?: string;
}): Decision {
  const tenant = resolveTenant(req.host);
  if (!tenant) return { kind: 'not-found' };

  const { locale: inPath, rest } = splitLocale(req.pathname);

  // 已带语言段：合法的直接改写；不被支持的就地回落，省掉一次往返
  if (inPath) {
    if (tenant.locales.includes(inPath)) return rewrite(tenant, inPath, rest);
    return { kind: 'redirect', pathname: `/${tenant.defaultLocale}${rest}`, status: 307 };
  }

  // 未带语言段：cookie → Accept-Language → 租户默认值，再 308 到规范地址
  const preferred =
    (req.cookieLocale && tenant.locales.includes(req.cookieLocale) && req.cookieLocale) ||
    tenant.locales.find((l) => req.acceptLanguage?.startsWith(l)) ||
    tenant.defaultLocale;

  return { kind: 'redirect', pathname: `/${preferred}${rest}`, status: 308 };
}

三处值得停下来看 ​

  • 判定与执行分离。管线只产出「决策对象」，由调用方去 NextResponse.rewrite(...)、redirect(...) 或抛 404。这层薄，就测得住；厚了，就只能靠端到端用例兜。
  • 308 与 307 是有意的。规范地址的纠正用 308（永久），语言回落的纠正用 307（临时）。搜索引擎对两者的处理不同，选错会让索引里残留一批不该存在的地址。
  • 语言段从路径读、由 proxy 注入，页面拿到的仍是 params。渲染侧不需要知道 cookie 的存在，静态化与缓存因此不受影响。
自测

为什么不把语言偏好存进 cookie、让页面直接读 cookie 渲染？

小结 ​

  • 多租户、缓存分层、i18n 三个决策交汇在同一段请求改写管线上
  • 租户解析「精确优先、通配次之」，与静态段优先是同一道理
  • 改写（地址不变）与跳转（地址规范）语义不同，状态码不能被随手写
  • 语言进 URL 才能保留可缓存性；cookie/请求头只用于一次跳转决策
  • 缓存键必须包含租户，否则是最隐蔽的跨租户数据泄漏

全书收口 ​

从 1.x 的心智模型到 14.x 的上线灰度，这本书走完了一条完整链路：先建立模型，再逐层拆解原理，最后把它落进一个能上线的多租户产品。到这里，本书的常规章节告一段落——但代码层面还有两处值得继续挖：

  • 想反复复现故障、练排障手感：排障图谱 按症状给了分支路径，每条路径都能一键进沙箱
  • 想继续往源码里钻：源码深潜 用真实 next/dist 源码逐段对照运行时行为
