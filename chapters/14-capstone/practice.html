场景：第一次发布与之后的一百次迭代 ​

TeamHub 面临两类发布：功能发布（每周多次）与平台能力发布（开启 cacheComponents、升级 Next）。前者追求快，后者追求稳。把两类发布的纪律分开，才不会让“开个开关”演变成通宵回滚。

第一步：环境矩阵固化 ​

维度dev（本地）preview（每 PR 一份）prod
数据本地/脱敏快照脱敏共享库生产库（强隔离）
环境变量.env.local（不入库）平台注入，命名隔离密钥管理服务，审计留痕
缓存内存/本地磁盘独立缓存前缀，避免污染Redis 多实例共享
新框架特性全开，含实验项先于生产开启灰度后开启
可观测终端/控制台上报到独立项目生产 OTel + Web Vitals 看板
部署触发pnpm devPR 创建/更新主干合并 + 人工确认

TIP

preview 环境是“特性灰于生产之前”的关键：cacheComponents、i18n、OTel 这类横切能力先在 preview 跑过真实流量形态的 E2E，再进生产。每个 PR 自动获得独立 URL，验收与产品确认都在那里完成。

第二步：灰度 cacheComponents——它是编译期开关 ​

必须先澄清一个事实：cacheComponents 在 next.config.ts 中，属于构建期配置，无法像运行时 feature flag 那样对 10% 用户动态切换。真正可操作的灰度轴是环境 × 路由：

ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  reactCompiler: true,
  // 灰度轴：preview 与内部构建先开；生产构建待路由改造完成后打开
  cacheComponents: process.env.NEXT_BUILD_TARGET !== 'prod',
  partialPrefetching: process.env.NEXT_BUILD_TARGET !== 'prod',
};
export default nextConfig;

::: steps

  1. preview 全量开启：用 Instant Insights 逐段修校验错误，instant() 用例补齐
  2. 生产标记迁移面：暂未改造的页面显式 export const instant = false，保持阻塞语义不回退
  3. 生产内部租户构建开启：先让内部团队的租户在开启配置的构建上使用
  4. 逐路由摘牌：每改完一个段删掉它的 instant = false，观察 LCP 与错误率
  5. 全量开启：所有段通过即时导航 E2E 后，生产构建默认打开，移除构建目标分支 :::
ts
export const instant = false; // 该段暂不承诺即时导航；改造完成后删除本行

::: warn 不要把 instant = false 当成永久状态留在代码里。给每个标记登记 issue 与负责人，灰度结束后统一清除，否则技术债会以“性能永远差一点”的形式长期存在。 :::

第三步：功能发布走小步闭环 ​

功能发布不需要动构建开关，纪律是小步、可观测、可回滚：

  1. PR 关联 preview URL，产品在 preview 验收
  2. E2E 守关键路径（登录、项目操作、403 越权、即时导航）
  3. 合并后观察 30 分钟：错误率（onRequestError）、p75 Web Vitals、缓存命中率
  4. 出问题先回滚镜像，再在分支上复盘——回滚不需要新构建

变更缓存数据的功能上线时，额外确认写操作的 updateTag 标签与读路径完全一致；标签写错命名空间是“数据更新了页面不变”的首要原因。👉 上线前可在 cache-hit 全栈实验 再走一遍“命中→写→失效→重取”的完整时序。

第四步：生产检查清单（全书收口） ​

  • [ ] 环境矩阵就绪：preview 每 PR 部署，生产变量经密钥管理注入
  • [ ] NEXT_PUBLIC_* 终检：构建产物中无密钥；环境相关值走运行时变量
  • [ ] 多实例：Action 加密密钥统一、Redis 缓存后端连通、镜像经 standalone 多阶段构建
  • [ ] 安全：会话五属性、Action/Handler 重复鉴权、CSP、错误页不泄密（第 11 章 13 项）
  • [ ] 性能：预算看板上线、第三方脚本造册、图片字体走内建优化（第 12 章 10 项）
  • [ ] 质量：CI 全绿，含四条关键 E2E 与至少一条 instant() 断言
  • [ ] 缓存：标签命名空间审查、CDN purge 流程演练、RSC/_rsc 转发确认
  • [ ] SEO：metadata、JSON-LD、sitemap、robots、OG 在生产域名验证通过
  • [ ] 可观测：OTel 链路、错误告警、Web Vitals 上报均指向生产后端并人工验证
  • [ ] 灰度：instant = false 标记有 issue 跟踪；内部租户观察期已满
  • [ ] 回滚：上一版本镜像保留，数据库迁移脚本可逆
  • [ ] 值班：告警阈值与值班表确认，Runbook 含第 13 章故障排查表链接

第五步：演练一次 16.4 升级 ​

呼应第 1 章的版本演进纪律。假设 16.4 发布，升级永远走独立 PR，不夹带业务需求：

bash
# 1. 自动化迁移打底（在独立分支）
pnpm dlx @next/codemod@latest upgrade latest

# 2. 对齐精确版本
pnpm add next@16.4.0

# 3. 机械检查最高频的异步 API 漏网
# 全仓搜索 params. / searchParams. / cookies() / headers()，逐一确认 await
pnpm typecheck && pnpm build

# 4. 重点回归
pnpm exec playwright test        # 含 instant() 与越权用例
pnpm next experimental-analyze    # 对比 bundle 有无意外膨胀

升级 PR 的验收要点：

检查项原因
阅读新版随包文档与发布说明codemod 不覆盖语义变更；AGENTS 指向的 dist/docs 已随版本更新
实验特性状态复核useOffline、SRI、Build Adapters 等可能改状态或改配置位
proxy/Cache 配置逐行核对横切配置的默认值在大版本间最易调整
preview 完整回归后再合并独立 PR 可随时关闭，不阻塞业务发布线
锁文件提交、CI 全绿团队装出完全一致的依赖树

INFO

升级后让 AI 智能体先读新版 node_modules/next/dist/docs/（AGENTS 托管块会自动指向），再让它产出“受影响代码点”清单，人工复核后执行——这比凭记忆迁移可靠得多，也是 16.4 铺这条链路的最终用途。

小结 ​

  • 发布分两类：功能发布走小步可回滚闭环；平台能力走环境 × 路由灰度
  • cacheComponents 是编译期开关，灰度载体是构建目标与逐路由 instant 标记，标记必须有退出计划
  • 生产检查清单收口全书；16.4 升级走独立 PR：codemod 打底、异步 API 全仓核对、preview 完整回归
  • 智能体读新版随包文档产出受影响清单，人工门禁不变

至此 14 章旅程结束：你已经拥有从路由、组件、数据、缓存、即时导航、Action、渲染、接口、样式、安全、性能到测试部署的完整心智，以及一个可以跟随 Next.js 持续演进的全栈 SaaS 蓝本。保持“先读随包文档、再写代码”的纪律，框架怎么变你都跟得上。
