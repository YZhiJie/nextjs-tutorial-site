项目设定：TeamHub ​

最后一章我们综合前 13 章，设计一个多租户团队协作 SaaS：每家公司是一个租户（tenant），成员在租户内管理项目与文档；营销站、应用区、API 共用一个 Next.js 16.4 应用。蓝图阶段做错的决策，上线后修复成本十倍于此，所以本篇只做一件事：把选型讨论清楚再写代码。

决策一：多租户数据隔离 ​

租户识别有三种入口：独立域名、子域名（acme.app.com）、路径段（/t/acme）。对中小团队 SaaS，路径段 /[tenant] 起步最省心——证书与 DNS 复杂度最低，后续需要品牌独立域名时再在 proxy 层映射。

真正的安全核心不是“识别出租户”，而是每一层都强制租户隔离：

text
① 会话载荷带 tenantId（登录时确定，不接受前端传参）
② DAL 的每个查询都带 where: { tenantId }，且不导出绕过它的函数
③ 数据库层加唯一约束/行级安全策略（RLS），作为应用层漏网时的兜底

ts
import 'server-only';
import { cache } from 'react';
import { getCurrentUser } from './auth';

export const getTenantContext = cache(async () => {
  const user = await getCurrentUser(); // 第 11 章：private 缓存的会话出口
  if (!user.tenantId) throw new Error('用户不属于任何租户');
  return { tenantId: user.tenantId, userId: user.id, role: user.role };
});

// 所有租户数据查询都从这里走，调用方没有机会传入“别人的 tenantId”
export async function listProjects() {
  const { tenantId } = await getTenantContext();
  return queryProjectsByTenant(tenantId);
}

DANGER

绝不能用客户端传来的 tenant 搜索参数或表单字段做归属判断，那等同于让用户自选能看哪家公司的数据。租户身份只能来自服务端会话；searchParams.tenant 之类只允许用于非敏感的界面偏好。

决策二：路由规划 ​

路由组把“营销站”和“应用区”彻底分开，它们共享同一依赖但拥有不同布局与缓存策略：

text
app/
├── (marketing)/              # 路由组：公共、强缓存、SEO 优先
│   ├── page.tsx              # 落地页
│   ├── pricing/page.tsx
│   └── blog/[slug]/page.tsx
├── (app)/
│   └── t/[tenant]/           # 应用区：动态租户段
│       ├── layout.tsx        # 租户壳：侧边栏 + 身份 UI（Suspense 内读会话）
│       ├── projects/[...]
│       └── settings/[...]
├── api/
│   ├── webhooks/stripe/route.ts   # 第三方回调
│   └── export/[id]/route.ts       # 文件/流式下载
├── proxy.ts                  # 语言协商、租户路由粗筛（不查库）
└── instrumentation.ts        # OTel + 错误上报

决策三：缓存策略分层 ​

每个数据类型在 Stream / Cache / Block 三选一中只有一个正确答案。按数据特征分层，而不是按页面分层：

数据策略标签/键理由
营销页、博客、定价表'use cache' + cacheLife('days')内容 id公共、可进静态外壳、CDN 友好
租户内共享数据（项目名、成员列表）'use cache'，参数含 tenantIdtenant:${id}:projects租户内可共享，写后按标签失效
用户私有数据（我的待办、通知）'use cache: private' 或流式不跨用户合规上不落服务端共享缓存
实时性数据（在线状态、用量）仅 Stream：Suspense 边界内动态取无新鲜度优先，外壳先出
强个性化且暂未改造的页export const instant = false无迁移期显式 Block，逐页再优化

TIP

缓存标签的命名空间要在蓝图阶段定死。建议 域:租户:资源 三段式，如 tenant:t_88:projects。标签明文存储，租户 id 是稳定标识可以入标签；租户名称、用户邮箱不可以。

决策四：BFF 与 Route Handler 的边界 ​

Next 可以做 BFF，但官方明确它不是完整后端替代品。边界要在第一天划清：

需求放在哪里
服务端组件取内部服务数据组件/DAL 直接 fetch，不要绕自家 /api（多一跳）
第三方 Webhook（支付、CMS）Route Handler：验原始 body、验签、幂等
文件下载/流式响应Route Handler
客户端必须轮询/订阅的接口Route Handler（每个入口都要重复鉴权）
粗粒度重定向、语言协商、灰度proxy.ts（不查库）
核心业务规则、跨服务事务独立后端服务，Next 只做编排

决策五：i18n 方案 ​

官方推荐的结构是 proxy 协商语言 + app/[lang] 动态段：proxy 读 Accept-Language，无语言前缀时重定向到 /zh-CN/...；所有布局页面嵌套在 [lang] 下，通过 await params 取 lang。

ts
import { NextResponse, type NextRequest } from 'next/server';

const LOCALES = ['zh-CN', 'en-US'];
const DEFAULT = 'zh-CN';

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const hasLocale = LOCALES.some((l) => pathname === `/${l}` || pathname.startsWith(`/${l}/`));
  if (hasLocale) return NextResponse.next();

  // 简化演示：生产可用 @formatjs/intl-localematcher 做质量值匹配
  const accepted = request.headers.get('accept-language') ?? '';
  const lang = accepted.includes('en') ? 'en-US' : DEFAULT;
  return NextResponse.redirect(new URL(`/${lang}${pathname}`, request.url));
}

与租户段组合时，顺序建议为 app/[lang]/t/[tenant]/...——语言是最外层，营销站也能复用同一套本地化结构。

决策六：PWA 与离线，要不要做 ​

  • 可安装性成本低：app/manifest.ts 用 MetadataRoute.Manifest 内建生成，图标与主题色配齐即可
  • 离线可用成本高：Service Worker 不在 Next 一等公民范围内，通常借助第三方 Workbox 类方案自行注册与维护缓存版本，缓存策略写错会让用户长期卡在旧版本
  • 16.4 另有实验性 experimental.useOffline：断网期间导航、RSC 取数与 Server Action 不抛错而是挂起重试，配 useOffline hook 提示用户；其前提是 Cache Components + Partial Prefetching，且明确标注实验，不建议作为产品核心承诺

对 TeamHub 的结论：营销站与应用外壳做可安装；离线只做“断网提示 + 请求挂起重试”，不承诺离线编辑——协作产品的离线写入冲突代价远大于收益。

小结 ​

  • 多租户安全靠三道防线：会话定租户、DAL 强过滤、数据库兜底；租户身份永不信客户端
  • 路由组拆营销与应用；缓存按数据特征在 Cache/Stream/Block 间分层，标签命名空间先行
  • BFF 边界：组件直连内部服务，Handler 留给 webhook/流/客户端接口
  • i18n 用 proxy + [lang]，第三方库按其官方文档验证；离线只承诺提示与挂起重试
