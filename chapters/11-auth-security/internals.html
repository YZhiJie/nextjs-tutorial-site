JWT 的三段结构 ​

基础篇记的是 createSession / decrypt 的用法，本篇换角度只看两块原理：令牌的字节结构与签名凭什么防篡改，以及守卫放在哪一层才绕不过去。先看令牌本身——JWT（JSON Web Token，JSON Web 令牌）是一串用两个点分三段的字符串：

3
  • header：{"alg":"HS256","typ":"JWT"}，声明用哪种算法签
  • payload：载荷（claims，声明集），放 userId、role、exp
  • signature：对 header.payload 的签名，唯一用来证明“没被改过”
  • 三段都按 base64url 编码：+→-、/→_、去掉 =，好放进 Cookie

签名 = HMAC-SHA256(header.payload, secret)：签发把前两段原样喂进 HMAC-SHA256（基于哈希的消息认证码），用服务端密钥算出签名拼在末尾；验签用同一密钥重算再比对。它只依赖密钥、不查网不查库，所以能塞进 Cookie，proxy 里也能验。

注意 base64 不是加密（encryption），只是编码（encoding）：payload 拿去 base64url 解码就能读出 role——载荷明文可读，签名只保证“没被篡改”，不保证“看不见”。

手写约 45 行的 sign 与 verify ​

用 node:crypto 的 createHmac / timingSafeEqual 复刻 jose 的内核，保留真实算法；顺序是先验签、后解析、最后查 exp：

ts
import 'server-only';
import { createHmac, timingSafeEqual } from 'node:crypto';
export type SessionPayload = { userId: string; role: 'user' | 'admin'; exp: number };

/** 对象 → base64url(JSON)：base64url 只是编码，不是加密 */
const encode = (obj: unknown): string =>
  Buffer.from(JSON.stringify(obj)).toString('base64url');
/** 对 data 用 secret 算 HMAC-SHA256 */
const hmac = (data: string, secret: string): string =>
  createHmac('sha256', secret).update(data).digest('base64url');
/** 签发：base64url(header).base64url(payload).base64url(签名) */
export function signToken(payload: Omit<SessionPayload, 'exp'>, secret: string): string {
  const header = encode({ alg: 'HS256', typ: 'JWT' });
  const exp = Math.floor(Date.now() / 1000) + 7 * 24 * 60 * 60; // 7 天
  const data = `${header}.${encode({ ...payload, exp })}`; // 被签名的正是这两段
  return `${data}.${hmac(data, secret)}`;
}

/** 验签：结构 → 签名 → 载荷 → 过期，任一关不过都返回 undefined */
export function verifyToken(token: string | undefined, secret: string): SessionPayload | undefined {
  if (!token) return undefined;
  const parts = token.split('.');
  if (parts.length !== 3) return undefined; // 结构不符：直接拒绝
  const [header, body, signature] = parts;

  /* ① 先验签，且必须常数时间比较 */
  const expected = Buffer.from(hmac(`${header}.${body}`, secret));
  const actual = Buffer.from(signature);
  if (expected.length !== actual.length || !timingSafeEqual(expected, actual)) return undefined;

  /* ② 验签通过后，载荷才可信，再解析 */
  let payload: SessionPayload;
  try {
    payload = JSON.parse(Buffer.from(body, 'base64url').toString('utf8'));
  } catch {
    return undefined;
  }
  if (typeof payload?.userId !== 'string') return undefined;

  /* ③ 最后看过期时间（exp 是秒） */
  if (payload.exp <= Math.floor(Date.now() / 1000)) return undefined;
  return payload;
}

  • 用 timingSafeEqual，不用 ===。=== 比到第一个不同字节就返回，耗时随“猜对前几位”变化，攻击者靠统计耗时逐位逼近签名，这叫时序攻击（timing attack）。timingSafeEqual 恒定耗时，但要求两 Buffer 等长，所以先比长度。

伪造演示：改 role 不动签名 ​

把 payload 的 role 从 user 改成 admin，签名原样复制，看 verifyToken 给什么：

ts
const secret = process.env.SESSION_SECRET!;
const token = signToken({ userId: 'u1', role: 'user' }, secret);
const [header, , signature] = token.split('.');
// 攻击者能解码 payload（明文），却拿不到 secret
const forgedBody = encode({ userId: 'u1', role: 'admin' }); // role 改成 admin
const forged = `${header}.${forgedBody}.${signature}`;      // 签名没换
verifyToken(token, secret);  // → { userId: 'u1', role: 'user' }  ✅
verifyToken(forged, secret); // → undefined  ❌ 签名对不上

会话守卫该放在哪一层 ​

验签只解决“令牌是真的”，真正的安全问题是守卫放在哪：

Route Handler ─┘        （匿名/越权在此被拦下）           ▲

proxy（只读 Cookie 的乐观粗筛）──► 只决定要不要提前跳转 ───┘
        ↑ 可被绕过：直接 POST Action、直连 API 都绕过它

DANGER

只在页面里守卫、API 不校验，是全章最典型的真实漏洞。页面里的 redirect('/login') 只决定“渲染哪套 UI”，而 Server Action 与 Route Handler 是独立 HTTP 入口，可被直接请求。守卫必须待在数据访问层（DAL，Data Access Layer）——所有入口都经它取数，从哪进来都会被拦下。

diff

+ const s = await requireUser(); // 数据旁再认证一次
+ const post = await db.post.findUnique({ where: { id } });
+ if (post?.authorId !== s.userId && s.role !== 'admin') throw new Error('FORBIDDEN');
+ await db.post.delete({ where: { id } }); // 越权与 IDOR 在此被拒

DAL 里的 requireUser / requireRole ​

把身份判定收束到 DAL 一个出口，cache() 让它在一趟渲染里只解一次 Cookie：

ts
import 'server-only';
import { cache } from 'react';
import { cookies } from 'next/headers';
import { verifyToken } from './token';
// 只解会话、不跳转：留给 Action/Handler 决定 401 还是 403
export const getSession = cache(async () => {
  const token = (await cookies()).get('session')?.value;
  return verifyToken(token, process.env.SESSION_SECRET!);
});
// 页面/组件用：没登录就跳登录页
export async function requireUser() {
  const s = await getSession();
  if (!s) throw new Error('UNAUTHENTICATED');
  return s;
}

// 需要角色时用：单调的权限阶梯
export async function requireRole(role: 'user' | 'admin') {
  const s = await requireUser();
  const rank = { user: 0, admin: 1 } as const;
  if (rank[s.role] < rank[role]) throw new Error('FORBIDDEN');
  return s;
}

cookie 属性与 Cache Components 的动态信号 ​

令牌放进 Cookie，三属性缺一不可，否则守卫再严也会被从旁路偷走：

属性值防的是什么
httpOnlytrue客户端 JS 读不到 Cookie，XSS 偷不走令牌
sameSite'lax'跨站表单默认不带 Cookie，挡住大部分 CSRF
securetrue仅 HTTPS 发送，防中间人嗅探

16.4 里 cookies() 是异步的，读会话写成 const token = (await cookies()).get('session')?.value;，漏写 await 只会拿到一个 Promise。开启 cacheComponents: true（Cache Components）后，页面由预渲染静态外壳 + 动态补入组成；读 Cookie 天然依赖请求，读它就是动态信号，一旦调用 cookies() 这段渲染就不能进静态外壳。所以带会话的组件要放在 <Suspense> 之后，或写进 'use cache: private'（只缓存于当前浏览器，永不落服务端缓存）——口诀是读身份用 private、共享数据用普通缓存且键里带 userId；普通 'use cache' 里禁止读 cookies()。

四个必须记住的陷阱 ​

  • 只在 UI / proxy 鉴权而 API 不校验：proxy 只是前厅保安，Action 与 Route Handler 必须各自经 DAL 重新认证
  • 把未验证的 payload 当可信数据：任何时候先 verifyToken、再读 role；直接 base64 解码就用，等于把角色交给攻击者填
  • 用 == / === 比较签名：带来时序侧信道；一律 timingSafeEqual，且先比长度
  • 无签名，或 secret 硬编码在前端：没签名的载荷随手可改；NEXT_PUBLIC_ 会把密钥内联进公开 JS，密钥只能待在服务端 DAL

小结 ​

  • JWT 是 base64url(header).base64url(payload).base64url(signature)；载荷明文可读，签名只保证没被篡改
  • 签名 = HMAC-SHA256(header.payload, secret)；验签顺序是结构 → 签名（timingSafeEqual）→ 载荷 → exp（秒）
  • 会话守卫必须下沉到 DAL：requireUser() / requireRole() 靠近数据，页面、Action、Route Handler 共用同一出口
  • 读会话即动态信号：cookies() 要 await，Cache Components 下用 'use cache: private'，Cookie 三属性 httpOnly / SameSite / Secure 缺一不可
