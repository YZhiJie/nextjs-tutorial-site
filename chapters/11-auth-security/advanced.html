缓存与鉴权的根本矛盾 ​

开启 cacheComponents: true 后，页面由可预渲染的静态外壳和请求时流式补齐的动态部分组成。而“读会话”这件事依赖请求 Cookie，天生不能进静态外壳。16.3 给这个矛盾的解法是一组明确规则：

  • 普通 'use cache' 函数内禁止调用 cookies()、headers()，直接抛错
  • 需要读请求的函数用 'use cache: private'：结果只存在浏览器内存里，永不落服务端缓存
  • 读会话的组件必须位于 <Suspense> 边界之后，外壳先秒出，身份 UI 流式补入
能力'use cache''use cache: private'
读 cookies() / headers() / searchParams禁止允许
服务端缓存是（内存尽力缓存，压力下驱逐）否
跨实例/跨用户共享可以不可以
进入静态外壳可以不可以
读 connection()禁止禁止

TIP

记忆口诀：读身份用 private（只在浏览器），共享数据用普通缓存（键里带 userId）。合规要求“某些数据连临时落服务端都不行”时，private 是唯一选择。

模式一：会话读取收敛进 private 函数 ​

ts
import 'server-only';
import { redirect } from 'next/navigation';
import { getSession } from '@/lib/session'; // 内部读 Cookie + unseal
import { findUserById } from '@/lib/user-dal';

export async function getCurrentUser() {
  'use cache: private'; // 允许读 Cookie；结果只缓存于当前浏览器

  const { userId } = await getSession();
  if (!userId) redirect('/login'); // redirect 抛错中断渲染，不会被缓存

  const user = await findUserById(userId);
  if (!user) redirect('/login');

  return { id: user.id, name: user.name, role: user.role }; // 窄对象
}

export default function Page() {
  return (
    <main>
      <Announcements /> {/* 公共内容，'use cache' 进外壳预渲染 */}
      <Suspense fallback={<p className="muted">正在载入你的面板…</p>}>
        <UserPanel /> {/* 边界内 await getCurrentUser()，身份 UI 流式补入 */}
      </Suspense>
    </main>
  );
}

模式二：会话派生数据用普通缓存，键里带 userId ​

private 缓存不共享、不跨刷新；用户的笔记列表这类数据既要按人隔离、又想在服务端命中，做法是在缓存函数外解析身份，只把 userId 作为参数传进去——参数就是缓存键：

ts
import 'server-only';
import { cacheLife, cacheTag } from 'next/cache';
import { getCurrentUser } from './auth';

export async function getNotes() {
  const user = await getCurrentUser(); // 此处读会话
  return getNotesByUserId(user.id);
}

// 不导出：外部无法通过传入别人的 id 拿到别人的笔记
async function getNotesByUserId(userId: string) {
  'use cache';
  cacheTag(`notes:${userId}`); // 写操作后按标签失效
  cacheLife('minutes');
  return db.notes.findMany({ where: { userId } });
}

DANGER

缓存键和标签在默认缓存中以明文存储（远程缓存同理），不要把邮箱、令牌、原始手机号写进参数或 cacheTag。标签一律挂在稳定 id 上，如 notes:${userId}。

Server Action：页面检查管不到 Action ​

这是全章最容易出真实漏洞的一点。页面里的 redirect('/login') 只决定渲染哪套 UI；Server Action 是独立的 HTTP 入口，可被直接 POST 调用。因此每个 Action 必须在内部重新认证 + 校验资源归属：

ts
'use server';

import { getSession } from '@/lib/session';
import { db } from '@/lib/db';
import { updateTag } from 'next/cache';
import { redirect } from 'next/navigation';

export async function deleteNote(noteId: string) {
  const { userId, role } = await getSession(); // ① 重新认证，不信客户端
  if (!userId) redirect('/login');

  const note = await db.note.findUnique({ where: { id: noteId } });
  if (!note) return { error: '笔记不存在' };

  // ② 授权：所有权或管理员，缺一不可，防 IDOR 越权
  if (note.authorId !== userId && role !== 'admin') {
    throw new Error('Forbidden');
  }

  await db.note.delete({ where: { id: noteId } });
  updateTag(`notes:${note.authorId}`); // ③ 失效该用户的缓存条目
}

框架已经替你做了三层 CSRF 防护，理解它们才敢正确排障：

防线机制
方法限制Action 只能用 POST 调用，GET 无法触发变更
Cookie 策略会话 Cookie 默认 SameSite=Lax，跨站表单不带 Cookie
来源校验框架比对 Origin 与 Host/X-Forwarded-Host，不一致直接中止

反向代理后域名与源站不同导致合法请求被拦时，在 next.config.ts 的 experimental.serverActions.allowedOrigins 中显式声明安全来源（支持 *.example.com 通配）。

INFO

Action 的加密 id 在构建时生成、最长缓存 14 天；组件内闭包捕获的变量也会被加密。自托管多实例时，若各实例构建产物不同，需用环境变量 NEXT_SERVER_ACTIONS_ENCRYPTION_KEY 统一密钥（openssl rand -base64 32 生成）。但加密只是纵深一层，不能替代 Action 内部鉴权。

密钥边界：什么代码能碰到什么秘密 ​

  • 默认环境变量只在服务端可见。加了 NEXT_PUBLIC_ 前缀的变量会在构建时内联进客户端 JS——它不是“方便点的服务端变量”，而是公开信息
  • 只有 DAL 直接访问 process.env，数据库密钥、会话密钥不透出这一层
  • DAL、会话模块首行加 import 'server-only'，误导入客户端组件时构建失败
  • 需要额外防线时可开启 Taint：experimental.taint: true，用 React 的 taint API 阻止敏感对象/值被传过边界，但它只是补充，DAL 的 DTO 裁剪才是根本

CSP：nonce 方案与它的性能代价 ​

严格 CSP 依赖每请求随机的 nonce。在 proxy.ts 生成 nonce 并下发头，Next.js 渲染时会自动把 nonce 注入框架脚本与页面 bundle：

ts
import { NextResponse, type NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64');
  const isDev = process.env.NODE_ENV === 'development';
  const csp = [
    "default-src 'self'",
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'${isDev ? " 'unsafe-eval'" : ''}`,
    `style-src 'self' 'nonce-${nonce}'`,
    "object-src 'none'",
    "frame-ancestors 'none'",
    'upgrade-insecure-requests',
  ].join('; ');

  const headers = new Headers(request.headers);
  headers.set('x-nonce', nonce);
  const res = NextResponse.next({ request: { headers } });
  res.headers.set('Content-Security-Policy', csp);
  return res;
}

Draft Mode：编辑预览未发布内容 ​

draftMode() 是专门的预览开关：enable() 设置 __prerender_bypass Cookie，此后 fetch 缓存与 'use cache' 全部旁路，页面以 private, no-store 响应；其他访客照常看缓存版本。

ts
import { draftMode } from 'next/headers';
import { redirect } from 'next/navigation';

export async function GET(request: Request) {
  const { searchParams } = new URL(request.url);
  const secret = searchParams.get('secret');
  const slug = searchParams.get('slug');

  if (secret !== process.env.DRAFT_SECRET || !slug) {
    return new Response('Invalid token', { status: 401 });
  }
  const post = await getPostBySlug(slug); // 先确认内容存在
  if (!post) return new Response('Invalid slug', { status: 401 });

  const draft = await draftMode();
  draft.enable();
  redirect(post.slug); // 重定向到服务端取回的路径，杜绝开放重定向
}

小结 ​

  • Cache Components 下：读会话用 'use cache: private' + Suspense；共享数据在普通缓存里以 userId 为键
  • Action 是独立入口：内部重新认证、校验资源归属，防 IDOR；CSRF 已有 POST/SameSite/Origin 三层防护
  • 密钥只在 DAL 触达，NEXT_PUBLIC_ 等于公开；CSP nonce 安全但牺牲静态化
  • Draft Mode 用旁路 Cookie 实现编辑预览，入口必须验密钥、防开放重定向

实战篇我们把这些模式组装成一个访客/编辑/管理员三角色后台，并给出可逐项勾选的安全上线清单。
