场景：一个内容团队后台 ​

假设你在为一个媒体产品做后台，路由与角色如下：

  • /login、文章详情页：访客可读已发布内容
  • /studio：编辑的工作台，可写稿、发布自己的文章
  • /studio/admin：管理员可删除任意文章、管理成员

每个角色都是同一套登录入口，差别只在会话里的 role 字段。真正的难点不是“登录”，而是保证每一层被绕过后，下一层还在。这就是纵深防御：proxy 拦路由 → DAL 定身份 → 组件按角色渲染 → Action/Route Handler 再次鉴权并校验归属。

::: steps

  1. 把角色写进会话载荷，建一个带角色断言的 DAL
  2. 用 proxy 把未登录用户挡在 /studio 之外（只查 Cookie）
  3. 页面与叶子组件按角色渲染，布局不做唯一闸门
  4. 每个 Server Action 内部重复认证 + 资源归属校验
  5. Route Handler 作为 JSON API 时显式返回 401/403
  6. 变更成功后用 updateTag 精确失效对应用户的缓存 :::

第一步：角色断言放进 DAL ​

基础篇的 verifySession() 只回答“你是谁”。角色系统再加一个 requireRole()，让“你是不是管理员”也只有一个实现：

ts
import 'server-only';
import { cache } from 'react';
import { cookies } from 'next/headers';
import { redirect } from 'next/navigation';
import { decrypt } from '@/lib/session';

type Role = 'guest' | 'editor' | 'admin';

export const verifySession = cache(async () => {
  const cookie = (await cookies()).get('session')?.value;
  const session = await decrypt(cookie);
  if (!session?.userId) redirect('/login');
  return { userId: String(session.userId), role: session.role as Role };
});

// 页面用：角色不足直接跳走
export async function requireRole(role: Role) {
  const session = await verifySession();
  const rank = { guest: 0, editor: 1, admin: 2 } as const;
  if (rank[session.role] < rank[role]) redirect('/studio');
  return session;
}

// Action/API 用：不跳转，返回 null，由调用方抛 401/403
export async function getSessionOrNull() {
  const cookie = (await cookies()).get('session')?.value;
  const session = await decrypt(cookie);
  return session?.userId
    ? { userId: String(session.userId), role: session.role as Role }
    : null;
}

第二步与第三步：proxy 拦截 + 组件级授权 ​

proxy 只做前缀级粗筛；细到“管理员页面”的判断放在页面组件里，因为布局不随客户端导航重渲染，不能当唯一闸门：

tsx
import { requireRole } from '@/lib/dal';
import { MemberTable } from './member-table';

export default async function AdminPage() {
  await requireRole('admin'); // 非管理员被重定向，且每次进入都会执行
  return (
    <section>
      <h1>成员管理</h1>
      <MemberTable />
    </section>
  );
}

叶子组件同样自查，控制“删除”按钮这类操作位：

tsx
import { verifySession } from '@/lib/dal';
import { DeleteArticleButton } from './delete-button';

export async function ArticleActions({ authorId }: { authorId: string }) {
  const session = await verifySession();
  const canDelete = session.role === 'admin' || session.userId === authorId;
  // 注意：这里只决定按钮显不显示，真正的删除鉴权在 Action 里
  return canDelete ? <DeleteArticleButton articleAuthorId={authorId} /> : null;
}

第四步与第五步：Action 与 JSON API 各自鉴权 ​

页面可以重定向，接口必须返回状态码。下面是一个被后台脚本调用的 Route Handler：

ts
import { getSessionOrNull } from '@/lib/dal';
import { db } from '@/lib/db';
import { updateTag } from 'next/cache';

export async function DELETE(_req: Request, { params }: { params: Promise<{ id: string }> }) {
  const session = await getSessionOrNull();
  if (!session) return new Response(null, { status: 401 }); // 未认证

  const { id } = await params; // 动态段参数必须 await
  const article = await db.article.findUnique({ where: { id } });
  if (!article) return new Response('Not found', { status: 404 });

  // 授权：管理员或作者本人，否则 403（防 IDOR 越权）
  if (session.role !== 'admin' && article.authorId !== session.userId) {
    return new Response('Forbidden', { status: 403 });
  }

  await db.article.delete({ where: { id } });
  updateTag(`articles:${article.authorId}`); // 写后立即失效
  return Response.json({ ok: true });
}

::: warn 401 与 403 的语义要分清：未认证（没有有效会话）返回 401；已登录但无权（角色/归属不足）返回 403。统一文案、统一在 DAL 旁落审计日志，越权尝试本身就是值得告警的安全信号。 :::

TIP

同一条删除能力同时提供 Action（表单用）和 Route Handler（API 用）时，把数据库操作与鉴权下沉到一个 server-only DAL 函数（如 deleteArticle(session, id)），两个入口都调用它。逻辑只有一份，审计也只看一处。

第六步：在全栈实验里串起来 ​

这套“proxy 粗筛 + Route Handler 细鉴权”的组合可以直接在实验容器里验证：未登录访问受保护路由被重定向、带上会话 Cookie 后 JSON 接口返回 200、越权删除别人资源返回 403。

最佳实践速查 ​

决策点推荐做法

安全上线检查清单 ​

  • [ ] 会话 Cookie 五个属性齐全（httpOnly/secure/sameSite/过期/path），密钥不在 Git 中
  • [ ] 所有 Action 与 Route Handler 内部完成认证，敏感操作额外校验资源归属
  • [ ] 搜索一遍客户端组件 props，确认没有整行 user 记录、密码哈希、令牌下发
  • [ ] NEXT_PUBLIC_ 变量逐个过审：它们会被内联进公开 JS
  • [ ] DAL/会话模块均有 server-only；数据库驱动未在这些模块之外被导入
  • [ ] proxy 的 matcher 排除了 _next/static、_next/image 与 API 路由
  • [ ] 表单、params、searchParams 全部经服务端 schema 校验
  • [ ] 登录/找回密码等端点有限流与统一错误文案（不暴露“邮箱是否已注册”）
  • [ ] 反向代理后已配置 serverActions.allowedOrigins，多实例统一 Action 加密密钥
  • [ ] 生产环境配置 CSP（严格场景用 nonce，兼顾静态化时评估 SRI）
  • [ ] 预览 Draft Mode 入口有密钥校验，重定向使用服务端取回的路径
  • [ ] global-error.tsx 不向用户回显堆栈、SQL 等内部信息
  • [ ] 审计日志覆盖登录、权限变更、删除操作，可用 onRequestError 上报服务端异常

小结 ​

  • 三角色后台的骨架是四层纵深：proxy 粗筛 → DAL 定身份 → 组件控渲染 → Action/Handler 重复鉴权
  • 页面用重定向、接口用 401/403；归属校验防住 IDOR；变更后 updateTag 精确失效
  • 上线不是“功能可用”，而是清单逐项打勾
