先分清三件事 ​

安全章节的术语必须先对齐，否则后面每一步都会混：

  1. 认证（Authentication）：你是谁——校验用户名密码、签发会话
  2. 会话管理（Session Management）：如何在多个请求之间记住“你已登录”
  3. 授权（Authorization）：你能做什么——普通用户不能进后台，编辑不能删别人的文章

在 App Router 里，这三件事分别落在四个地方：登录表单 + Server Action（认证）、Cookie（会话）、数据访问层 DAL（授权）、proxy.ts（粗粒度路由拦截）。本篇把最小骨架搭起来，授权深水区留给进阶篇。

INFO

Next.js 不是认证框架。官方文档明确建议生产项目使用成熟认证库（如 NextAuth 类方案、iron-session、jose）。本篇用 jose 手写最小实现，是为了让你看清每一块在框架里的位置；换库后模式完全一致。

为什么会话存在 Cookie 里 ​

HTTP 请求天然无状态，服务器要靠请求里携带的凭证认出你。把加密后的会话载荷放进 Cookie，浏览器之后每个请求都会自动带上，服务端用 cookies() 读取即可。

会话 Cookie 的每个属性都不是装饰：

属性推荐值作用
httpOnlytrue客户端 JS 读不到 Cookie，XSS 偷不走会话
securetrue仅 HTTPS 发送（本地 http 开发除外）
sameSite'lax'跨站请求默认不带 Cookie，挡住大部分 CSRF
expires / maxAge7 天等到期自动失效，不发永久票据
path'/'限定 Cookie 生效路径

DANGER

会话载荷里只放最小且不敏感的数据：用户 id、角色。不要放手机号、邮箱、密码——Cookie 在用户浏览器里，它不属于“服务端内部存储”。

会话模块只允许在服务端运行，首行加 server-only，一旦被客户端组件误导入，构建直接报错：

ts
import 'server-only';
import { SignJWT, jwtVerify } from 'jose';
import { cookies } from 'next/headers';

const encodedKey = new TextEncoder().encode(process.env.SESSION_SECRET);

// 加密：把 { userId, role, expiresAt } 签成 7 天有效的 JWT
async function encrypt(payload: { userId: string; role: string; expiresAt: Date }) {
  return new SignJWT(payload)
    .setProtectedHeader({ alg: 'HS256' })
    .setIssuedAt()
    .setExpirationTime('7d')
    .sign(encodedKey);
}

// 解密：校验失败或过期时返回 undefined，调用方按“未登录”处理
export async function decrypt(session = '') {
  try {
    const { payload } = await jwtVerify(session, encodedKey, { algorithms: ['HS256'] });
    return payload;
  } catch {
    return undefined;
  }
}

// 登录成功后调用：把加密会话写进 httpOnly Cookie
export async function createSession(userId: string, role: string) {
  const expiresAt = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000);
  const session = await encrypt({ userId, role, expiresAt });
  const cookieStore = await cookies(); // 16.x：cookies() 必须 await
  cookieStore.set('session', session, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    expires: expiresAt,
    path: '/',
  });
}

// 登出时调用：删除 Cookie
export async function deleteSession() {
  const cookieStore = await cookies();
  cookieStore.delete('session');
}

登录与登出：Server Action 骨架 ​

认证逻辑必须运行在服务端。Server Action 天然如此，还自带渐进增强——禁用 JS 时表单依然能提交：

ts
'use server';

import { redirect } from 'next/navigation';
import { createSession, deleteSession } from '@/lib/session';
import { verifyPassword, findUserByEmail } from '@/lib/user-dal';

export async function login(_prev: unknown, formData: FormData) {
  const email = String(formData.get('email') ?? '');
  const password = String(formData.get('password') ?? '');

  const user = await findUserByEmail(email);
  // 密码必须用 bcrypt/argon2 哈希后比对，绝不明文存储
  if (!user || !(await verifyPassword(password, user.passwordHash))) {
    return { error: '邮箱或密码错误' };
  }

  await createSession(user.id, user.role);
  redirect('/dashboard');
}

export async function logout() {
  await deleteSession();
  redirect('/login');
}

在服务端组件里读会话：DAL 的起点 ​

不要在每个组件里各自解密 Cookie。建一个**数据访问层（DAL）**函数，用 React 的 cache() 在一次渲染中记忆结果，全树共享一次读取：

ts
import 'server-only';
import { cache } from 'react';
import { cookies } from 'next/headers';
import { redirect } from 'next/navigation';
import { decrypt } from '@/lib/session';

export const verifySession = cache(async () => {
  const cookie = (await cookies()).get('session')?.value;
  const session = await decrypt(cookie);
  if (!session?.userId) {
    redirect('/login');
  }

  // 只返回后续渲染需要的最小字段
  return { userId: String(session.userId), role: String(session.role) };
});

proxy.ts：粗粒度的第一道门 ​

proxy.ts 在路由渲染前运行，适合把未登录用户挡在 /dashboard 之外。注意它是“乐观检查”——只读 Cookie，不查数据库：

ts
import { NextResponse, type NextRequest } from 'next/server';
import { cookies } from 'next/headers';
import { decrypt } from '@/lib/session';

// 前缀匹配即可覆盖 /dashboard、/dashboard/settings 等子路由
const protectedPrefix = '/dashboard';

export default async function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const cookie = (await cookies()).get('session')?.value;
  const session = await decrypt(cookie); // 只解 Cookie，不查数据库

  if (pathname.startsWith(protectedPrefix) && !session?.userId) {
    return NextResponse.redirect(new URL('/login', request.nextUrl));
  }
  return NextResponse.next();
}

// 排除静态资源与图片优化接口，避免鉴权逻辑误伤 CSS/JS
export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'],
};

DANGER

proxy 运行在包括预取在内的每一次路由请求上，绝不能在里面查数据库，否则每个 <Link> 入屏都会打一次库。它只是“前厅保安”，真正的授权必须在数据旁边再做一次——这是进阶篇的主题。

常见误区 ​

  • 在 layout 顶层做鉴权然后 return null：布局在客户端导航时不重渲染，且拦不住并行槽位和 Server Action。检查要靠近数据与被保护组件。
  • 在渲染过程中删 Cookie 实现登出（如读 searchParams.logout）：渲染中禁止副作用，Next 会直接阻止。变更一律走 Action。
  • 把整个 user 对象（含密码哈希）下发给客户端组件：跨边界传递的是序列化数据，先用 DTO 裁成最小字段。
  • 依赖 localStorage 存会话：JS 可读意味着 XSS 可读，且无法做服务端拦截。会话票据请用 httpOnly Cookie。

小结 ​

  • 认证、会话、授权是三件事；16.4 的落点是 Action、Cookie、DAL、proxy
  • 会话 Cookie 五件套：httpOnly、secure、sameSite: 'lax'、过期时间、path
  • cookies() 必须 await；verifySession() 用 React cache() 收敛成单一入口
  • proxy 只做不查库的乐观拦截，真正的授权在数据层
