整页阻塞：你在等最慢的那个数据 ​

基础篇讲过"没有 Suspense 就整页等待"，进阶篇讲过"嵌套边界让快的先走"，但都刻意跳过了一个问题：服务器究竟怎么把一个页面"分几次"发给浏览器？ 这一篇把它压到最小模型——不借助 React，在 Node 原生 http 模块上用约 70 行代码手写流式 SSR。

先承认阻塞式的本质。同一个页面有两个数据源：统计卡片 800ms、推荐列表 300ms。整页等待时，响应的第一个字节被最慢的那个扣住：

text
请求 ──▶ 渲染整页（await stats 800ms + recos 300ms）
              │
              ▼ 全部就绪才一次性写出完整 HTML
TTFB ≈ 800ms：recos 早在 300ms 就已就绪，白白陪等了 500ms

2
3
4

流式渲染消灭的就是这段陪等，思路只有一句话：先发 shell，再按 Suspense 边界补发。

out-of-order：占位先行，内容插队 ​

shell 里每个 Suspense 边界渲染的不是真实内容，而是一段占位 DOM（对应你写的 fallback）。数据就绪后，服务器往响应流追加两样东西：装着真实 HTML 的隐藏节点，和一段内联 <script>——script 一到浏览器就执行，把真实 HTML 替换进占位，用户看到骨架"原地变成"内容。

关键在发送顺序：先就绪的先发，不等兄弟边界。统计卡片在页面里排在推荐列表前面，但它 800ms 才就绪；推荐列表 300ms 就绪就先走。内容的到达顺序与页面顺序脱钩，这就是 out-of-order streaming：

text
t ≈ 0ms    [shell] <h1> + slot-stats(骨架) + slot-reco(骨架)
t ≈ 300ms  [补发]  template#reco  + 替换 script   ← 排在后面，却先到
t ≈ 800ms  [补发]  template#stats + 替换 script
t ≈ 800ms  [收尾]  </body></html> → res.end()，连接此刻才关闭

2
3
4

浏览器为什么接得住

响应没有声明 Content-Length，Node 自动改用 chunked 传输编码：连接保持打开，每一块到达即解析。HTML 解析器本来就是增量工作的——"文档说到一半又继续说"，对它只是日常。

完整实现：约 70 行的 mini-stream ​

ts
import http from 'node:http';

const PORT = 3000;

/* ---------- ① 慢数据源：setTimeout 模拟一次慢查询 ---------- */
function slowQuery<T>(delay: number, result: T): Promise<T> {
  // 定时器触发时 Promise 才兑现：模拟数据在 800ms / 300ms 后才可用
  return new Promise((resolve) => setTimeout(() => resolve(result), delay));
}

/* ---------- ② shell：先发给浏览器的页面骨架 ---------- */
// 两个占位 div 就是两个 Suspense 边界的 fallback。
// 故意不写闭合标签：后面还要往这条响应流里继续追加内容。
const shell = `<!doctype html>
<html lang="zh">
<head><meta charset="utf-8"><title>mini-stream</title></head>
<body>
  <h1>经营概览</h1>
  <section><h2>统计卡片</h2><div id="slot-stats">统计加载中…</div></section>
  <section><h2>今日推荐</h2><div id="slot-reco">推荐加载中…</div></section>`;

/* ---------- ③ 补发块：隐藏 template + 一段内联 script ---------- */
// template 里的真实 HTML 到达即解析、但不显示；
// script 立即执行，把内容搬进占位 div——"补发"的全部机关就是这一搬。
function replacement(slot: string, html: string): string {
  return (
    `<template id="tpl-${slot}">${html}</template>` +
    `<script>
      document.getElementById('slot-${slot}').replaceChildren(
        document.getElementById('tpl-${slot}').content
      );
    </script>`
  );
}

/* ---------- ④ 流式响应：shell 先行，谁就绪谁先补发 ---------- */
http
  .createServer((_req, res) => {
    // 不设 Content-Length：Node 自动改用 chunked 编码，边写边发
    res.writeHead(200, { 'content-type': 'text/html; charset=utf-8' });

    res.write(shell); // 第 0 块：标题 + 两个"加载中"此刻已可见

    // 每次请求都重新"查询"：两个 Promise 同时起跑，互不等待
    const stats$ = slowQuery(800, '<ul><li>销售额 ¥128,400</li><li>订单 1,024</li></ul>');
    const reco$ = slowQuery(300, '<ul><li>无线鼠标</li><li>机械键盘</li><li>4K 显示器</li></ul>');

    // 每个边界独立订阅自己的 Promise——out-of-order 的来源
    const pending = [
      { slot: 'stats', data: stats$ },
      { slot: 'reco', data: reco$ },
    ];
    for (const { slot, data } of pending) {
      data.then(
        (html) => res.write(replacement(slot, html)),
        () => res.write(replacement(slot, '<p>该模块加载失败</p>'))
      );
    }

    // 最慢的数据到齐才能收尾：补上闭合标签，关闭连接
    Promise.all([stats$, reco$]).then(() => {
      res.write('</body></html>');
      res.end();
    });
  })
  .listen(PORT, () => console.log(`监听 http://localhost:${PORT}`));

代码只有 66 行，分四段，有三处细节值得停下来：

  • 占位与替换是纯 DOM 操作。<template> 里的内容到达即解析但不渲染，replaceChildren 把它搬进占位 div——没有框架、没有虚拟 DOM，"边界补发"的全部机关就是这一搬。
  • res.end() 被刻意推迟。连接必须活到最慢的数据到齐，Promise.all 之后才能补上闭合标签；若提前 end()，后来的补发块会直接写进已关闭的响应。
  • 补发块自带执行时机。替换逻辑写在 <script> 里随块到达，浏览器解析到它就执行——不需要客户端预先注册任何监听器。

React 的真实实现与此同构：占位是 <div hidden id="S:0">，补发块是第二个 hidden div 加一段调用 $RC() 的内联 script，$RC 负责搬 DOM 并清理占位。机制同类，只是簿记更完整。

阻塞式 vs 流式：只差几个 res.write ​

把两种写法放进同一张时间表，差异一目了然：

diff
- // 阻塞式：整页等最慢的数据，一个字节都不先发
- const [stats, recos] = await Promise.all([stats$, reco$]);
- res.writeHead(200, { 'content-type': 'text/html; charset=utf-8' });
- res.write(renderFullPage(stats, recos)); // 第 800ms 才有第一个字节
- res.end();                               // TTFB = 最慢请求
+ // 流式：shell 先走，边界各自补发
+ res.writeHead(200, { 'content-type': 'text/html; charset=utf-8' });
+ res.write(shell);                                             // t ≈ 0ms
+ reco$.then((html) => res.write(replacement('reco', html)));   // t ≈ 300ms
+ stats$.then((html) => res.write(replacement('stats', html))); // t ≈ 800ms
+ Promise.all([stats$, reco$]).then(() => res.end());           // 连接 800ms 才关

边界不是越多越好：页头别塞进 Suspense

最伤的划分错误，是把页头、侧边栏这类布局骨架整个包进 Suspense。它们也许只慢 100ms，但每次补发替换都会顶着页面重新排版——补一块抖一次；更糟的是 LCP 元素若被困在边界里，LCP 直接退化为最慢请求。进阶篇"骨架预留真实尺寸"只是缓解，根治靠划分：边界只包"数据慢、但替换后不影响布局骨架"的区域——列表、图表、推荐位。页头真有慢数据，就拆成"立即渲染的外壳 + 只包数据条的边界"，而不是整块扔进去。

距离真实的 Next.js 还差什么 ​

mini-stream 跑通了"shell 先行 + 边界补发"的主干，距离生产实现还差四层：

  • RSC payload 双流：真实响应里交织着两股数据——给浏览器直接渲染的 HTML，和给客户端运行时水合用的 RSC payload。mini-stream 只有前者，刷新后组件状态无法在客户端"复活"。
  • 选择性水合（selective hydration）：真实实现按边界记录水合进度，哪块内容先到就先水合哪块，交互不必等整页就绪；mini-stream 没有客户端运行时，无从谈起。
  • 状态码与 header 先行：res.writeHead 之后再无回头路。真实框架必须在开流之前推断这次渲染该回 200 还是 500；开流后才发生的错误，只能往已发出的流里写兜底内容。
  • error 边界兜底：数据就绪前抛错，React 会把该边界的补发块换成错误 UI；shell 阶段就抛错则整体降级到 error 页。mini-stream 的 catch 只写了句"加载失败"占位。

小结 ​

  • 阻塞式 SSR 的本质是"等最慢的那个数据"：第一字节被最慢请求扣住
  • 流式 = 先发 shell（含各边界 fallback），数据就绪后以内联 script 逐块替换占位
  • out-of-order：先就绪的先发，到达顺序与页面顺序脱钩，chunked 编码让浏览器边收边渲染
  • 边界只包"数据慢但不影响布局骨架"的区域，页头侧栏进边界会抖动并拖垮 LCP
  • 真实 Next.js 在此之上叠加 RSC payload 双流、选择性水合、先行确定状态码与 error 兜底

流式解决"让用户早点看见"，第 5 章的 'use cache' 解决"让数据本来就不用等"——基础篇留下的两条路在此汇合。
