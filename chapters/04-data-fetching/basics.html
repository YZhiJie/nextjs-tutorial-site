组件就是取数单元 ​

App Router 不需要 getServerSideProps 之类的前置取数层。组件本身是 async 函数，在渲染过程中直接读取资源：可以是 fetch，也可以是 ORM、数据库驱动、内部 gRPC 客户端。

tsx
type Post = { id: string; title: string };

export default async function BlogPage() {
  const res = await fetch('https://api.example.com/posts');
  if (!res.ok) throw new Error(`文章列表请求失败：${res.status}`);
  const posts: Post[] = await res.json();

  return (
    <ul>
      {posts.map((post) => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  );
}

16.x 的第一前提：fetch 默认不缓存 ​

这是与早期 App Router 最大的语义差异，必须先刻进脑子：

写法16.x 行为
fetch(url)（默认）不持久化缓存；路由动态时每次请求都重新获取
fetch(url, { cache: 'force-cache' })显式纳入框架持久缓存
fetch(url, { next: { revalidate: 60 } })显式缓存 60 秒
ORM / 数据库驱动无自动缓存；需要时用 'use cache'（第 5 章）

开发环境还有一个易混淆点：HMR 期间默认会跨模块热替换记忆化 fetch 响应以省费用，导航或整页刷新后清空。如果你发现改完代码数据“没变”，先整页刷新一次再排查。

::: warn 未完成的数据请求会阻塞整段渲染——这是默认行为，不是 bug。想要“先出壳、数据后到”，有两条路：显式缓存（第 5 章）或本篇后半部分的 Suspense 流式。 :::

请求瀑布：被 await 顺序吃掉的时间 ​

同一组件里连续 await，第二个请求必须等第一个完成，即使两者毫无依赖：

tsx
export default async function ArtistPage(
  props: PageProps<'/artist/[username]'>
) {
  const { username } = await props.params;

  // 先等歌手信息（约 800ms）
  const artist = await getArtist(username);
  // 再等专辑列表（约 1200ms）——它本来不需要 artist 数据
  const albums = await getAlbums(username);

  return (
    <>
      <h1>{artist.name}</h1>
      <AlbumList items={albums} />
    </>
  );
}

修复方式是先同步发起所有请求，再统一等待：调用即发起，Promise 先握在手里：

tsx
export default async function ArtistPage(
  props: PageProps<'/artist/[username]'>
) {
  const { username } = await props.params;

  // 两行同步执行，两个请求此刻同时在飞
  const artistPromise = getArtist(username);
  const albumsPromise = getAlbums(username);

  const [artist, albums] = await Promise.all([artistPromise, albumsPromise]);

  return (
    <>
      <h1>{artist.name}</h1>
      <AlbumList items={albums} />
    </>
  );
}

TIP

两个额外的免费优化：

  • 同一次服务端渲染中，完全相同的 GET fetch 自动记忆化，多个组件请求同一 URL 只发一次
  • 不同路由段（布局、页面）默认就是并行渲染的，每段尽早发起自己的数据；别把所有取数堆到根布局里人为串起来

若一个请求失败时不希望拖垮整页，用 Promise.allSettled 替代 Promise.all，对 rejected 项渲染降级 UI。

用 Suspense 把“等待”切成块 ​

并行化压缩总时长，但页面仍要等最慢的请求才能发一个字节。流式渲染改变这点：静态外壳先发，慢数据在各自的 Suspense 边界后补齐。

tsx
import { Suspense } from 'react';
import { ArtistHeader } from '@/components/artist-header';
import { AlbumList } from '@/components/album-list';
import { AlbumListSkeleton } from '@/components/skeletons';

export default function ArtistPage(
  props: PageProps<'/artist/[username]'>
) {
  const { username } = await props.params;

  return (
    <>
      {/* 头部不依赖慢请求，立即出现在 HTML 里 */}
      <ArtistHeader username={username} />
      {/* 专辑列表慢：先给骨架，数据到了自动替换 */}
      <Suspense fallback={<AlbumListSkeleton />}>
        <AlbumList username={username} />
      </Suspense>
    </>
  );
}

AlbumList 在自己的异步函数里发起请求；React 先把 fallback 刷给浏览器，承诺解析后再流式推送真实内容。文件约定 loading.tsx 等价于在该段最外层自动包一层 Suspense（第 2 章已用），手写 <Suspense> 的优势是粒度更细：页面头、侧栏、列表可以各等各的。

常见误区 ​

  • 以为 16.x 的 fetch 还默认缓存：不写选项就是动态获取，“为什么数据不更新”通常要反过来查是否误用了缓存选项。
  • 在循环里 await：for 中逐条 await 天然串行；先 map 成 Promise 数组再 Promise.all。
  • 所有请求塞根布局：布局无法被同段 loading.tsx 兜底，慢接口会卡住导航；数据尽量下沉到使用它的段。
  • Suspense 包了但 fallback 占位高度为 0：内容到达后布局跳动，CLS 恶化；骨架要预留与真实内容相近的尺寸。
  • 用 Promise.all 却在前面 await 过一次：请求必须在同一同步执行栈内发起才并行，别提前 await 任意一个。

小结 ​

  • 服务端 async 组件直接 await 任意异步 I/O，取数与渲染同处一地
  • 16.x 动态默认：fetch 不持久缓存，缓存与保鲜全部显式声明
  • 无依赖的请求先统一发起再 Promise.all，总耗时取最慢请求
  • Suspense 让外壳先到、慢数据按边界流式补齐，loading.tsx 是段级快捷方式
