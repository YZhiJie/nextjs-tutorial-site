嵌套 Suspense：边界即优先级 ​

一个真实页面的数据到达速度天然分层：用户信息 50ms、统计图表 800ms、推荐列表 2s。给每层套独立 Suspense，快的部分不等慢的：

tsx
import { Suspense } from 'react';
import { StatsCards, StatsSkeleton } from '@/components/stats';
import { RevenueChart, ChartSkeleton } from '@/components/revenue-chart';
import { Recommendations, RecoSkeleton } from '@/components/recommendations';

export default function DashboardPage() {
  return (
    <div className="space-y-6 p-6">
      <h1>经营概览</h1>
      {/* 三块各自流式，互不阻塞 */}
      <Suspense fallback={<StatsSkeleton />}>
        <StatsCards />
      </Suspense>
      <Suspense fallback={<ChartSkeleton />}>
        <RevenueChart />
      </Suspense>
      <Suspense fallback={<RecoSkeleton />}>
        <Recommendations />
      </Suspense>
    </div>
  );
}

嵌套边界则表达“渐进详情”：外层先出列表骨架，列表到达后，每行内部的详情再各自补齐。两个设计原则：

  • LCP 元素放在边界之外（或之上）：主标题、首屏主图不要困在 Suspense 里，否则 LCP 等于最慢请求
  • fallback 预留真实尺寸：骨架与最终内容等高，避免内容替换时累积布局偏移（CLS）

loading.tsx 与手写 Suspense 的分工也要明确：

手段粒度适用
loading.tsx整个路由段（自动包 page 及其子树）导航瞬间的段级骨架
手写 <Suspense>任意子树页内多块差异化流式、包裹组件级慢数据

::: warn 同段 loading.tsx 包不住同段 layout 里的异步访问。布局直接 await cookies() 或慢 fetch 会阻塞整段导航——要么把数据下沉进 page，要么在布局内部就近写 <Suspense>。 :::

fetch 的显式缓存选项 ​

默认动态之外，fetch 的两个扩展选项让你按请求声明语义：

tsx
// ① 永久缓存（配合 revalidateTag 按需失效，适合 CMS 内容）
const terms = await fetch('https://cms/terms', {
  cache: 'force-cache',
});

// ② 60 秒寿命的周期刷新（库存、价格类准实时数据）
const stock = await fetch('https://api/stock', {
  next: { revalidate: 60 },
});

// ③ 打标签，供 revalidateTag('posts') 精确失效
const posts = await fetch('https://api/posts', {
  cache: 'force-cache',
  next: { tags: ['posts'] },
});

选项语义对照：

选项含义
cache: 'force-cache'命中且新鲜则直接返回缓存；无缓存或过期则回源并写入（仅 200 入库）
cache: 'no-store'即使路由没有任何动态 API，也每次回源
next.revalidate: n缓存寿命 n 秒；false 为无限；0 等同不缓存
next.tags: [...]为条目挂标签（单标签 ≤256 字符、单次 ≤128 个）

DANGER

{ cache: 'no-store', next: { revalidate: 3600 } } 这类互相冲突的选项会被双双忽略，开发服务器终端打印警告。同一 URL 在同一路由内有不同 revalidate 时，取更小值。

非 fetch 数据源：React.cache 做请求内记忆化 ​

数据库驱动、ORM、Redis 客户端不受 fetch 缓存扩展控制。两层手段分开使用：

  • 跨请求持久缓存：第 5 章的 'use cache' + cacheLife，这是 16.x 的主路径
  • 单次请求内去重：React 的 cache()，多个组件调用同一函数共享一次结果
ts
import { cache } from 'react';
import { db } from '@/lib/db';

// 同一渲染过程中，布局、页面、卡片各处调用 getUser() 只查一次库
export const getUser = cache(async () => {
  return db.user.findFirst();
});

用 use() 把 Promise 流到客户端 ​

服务端组件可以不 await，把 Promise 本身作为 prop 交给客户端组件，由 React 的 use() 在客户端读取：

tsx
import { Suspense } from 'react';
import PostsClient from '@/app/ui/posts-client';
import { getPosts } from '@/lib/posts';

export default function BlogPage() {
  const postsPromise = getPosts(); // 请求此刻发起，但不阻塞外壳

  return (
    <Suspense fallback={<p>文章加载中…</p>}>
      <PostsClient posts={postsPromise} />
    </Suspense>
  );
}

}

什么时候才在客户端取数 ​

首屏数据优先走服务端；客户端取数（SWR、TanStack Query 等）只服务三类场景：

  1. 数据完全由客户端交互产生：拖拽看板的位置、摄像头权限后的位置流
  2. 需要高频轮询、重连、焦点刷新等库内置能力的实时数据
  3. 用户操作后增量加载的“下一页/详情抽屉”，且不便走服务端预取

这类库有独立的缓存语义，与框架缓存不互通；最佳搭配是服务端首屏 + 客户端水合接管：把服务端取到的初始数据通过 SWR 的 fallback/revalidate 机制喂给库，避免水合后二次请求白屏。

预告：prefetch=

第 6 章的即时导航中，<Link prefetch={true}> 会在点击前带着目标 URL 的 params/searchParams 重新渲染目标树，让依赖 URL 数据的缓存结果也提前就绪。本节先记住这个开关，到时再串起来。

小结 ​

  • Suspense 边界决定流式优先级：LCP 元素留在边界外，骨架预留尺寸
  • force-cache/no-store/next.revalidate/next.tags 是 fetch 的四个显式开关，冲突选项会被忽略
  • DB/ORM 用 React.cache 做请求内去重，跨请求缓存交给 'use cache'
  • Promise 可作为 prop 下发，由客户端 use() 读取并配合 Suspense
  • 客户端取数只服务交互产生数据、实时能力与增量加载，首屏仍归服务端
