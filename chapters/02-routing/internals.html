本页目录

app/ 目录是怎么变成 URL 的 ​

基础篇记住了“文件夹即路由”，但这条约定背后其实是一条三段管线（pipeline）：

  1. 目录扫描（directory scan）：递归遍历 app/，登记每个 page.tsx 与它的段序列
  2. 路由树构建（route tree）：把页面清单折叠成按段嵌套的树，每个节点对应一层 layout 的挂载点
  3. URL 匹配（URL matching）：把请求路径切成段，沿树逐级下钻，命中节点即拿到要渲染的文件与 params
text

  ▼

  │  ② buildRouteTree()    按 segment 折叠成树，静态段排前
  ▼
路由树 root: RouteNode
  │  ③ match(root, url)    逐级下钻：先静态、后动态
  ▼
{ file, params } 或 null（404）

理解了这条管线，layout.tsx 为什么“沿路径组合”也顺理成章：路由树的每个节点都对应一段，渲染时从根到命中节点，把沿途各层的 layout/loading/error 依次包起来。迷你实现为了聚焦只登记 page.tsx，但节点结构已经预留了这个位置。

第一段：目录扫描 scanPages ​

扫描器的职责很单一：给定目录，产出“文件 → 段数组”的清单。例如 app/blog/[slug]/page.tsx 的扫描结果是 { file, segments: ['blog', '[slug]'] }。段数组就是后续建树与匹配的原材料，这一步完全不关心“路由长什么样”，只关心“文件在哪里”。

第二段：折叠成路由树 buildRouteTree ​

把清单逐条插入一棵树：每个 segment 一个节点，相同前缀共享父节点——blog/a 与 blog/b 共用 blog 节点。插入完成后做一次排序：静态段排在动态段前面，这是匹配正确性的关键，稍后会用反例说明。

路由树同时解释了嵌套布局的渲染顺序：匹配路径经过的每一个节点，都是一层潜在的外壳。Next.js 构建期生成的正是这样一棵树，只是真实产物里每个节点还挂着 layout、loading、error 等模块引用。

第三段：URL matcher ​

匹配器把 /blog/hello 切成 ['blog', 'hello']，从根节点逐级下钻：每一级先在静态段里找精确命中，找不到再退到动态段 [xxx]，并把这一段记入 params。任一级都没有命中就返回 null——这就是文件系统路由的 404。

完整实现：约 70 行的迷你路由 ​

ts
import fs from 'node:fs';
import path from 'node:path';

type PageEntry = { file: string; segments: string[] };

/* ---------- ① 目录扫描 ---------- */
function scanPages(dir: string, base = dir): PageEntry[] {
  const pages: PageEntry[] = [];
  for (const name of fs.readdirSync(dir)) {
    const full = path.join(dir, name);
    if (fs.statSync(full).isDirectory()) {
      pages.push(...scanPages(full, base)); // 递归进入子目录
    } else if (/^page\.(tsx?|jsx?)$/.test(name)) {
      const rel = path.relative(base, path.dirname(full));
      pages.push({ file: full, segments: rel ? rel.split(path.sep) : [] });
    }
  }
  return pages;
}

/* ---------- ② 路由树 ---------- */
type RouteNode = {
  segment: string; // '' 表示根，'about' 静态段，'[slug]' 动态段
  file?: string;   // 该节点命中时要渲染的 page
  children: RouteNode[];
};

const isDynamic = (seg: string) => seg.startsWith('[') && seg.endsWith(']');

function buildRouteTree(pages: PageEntry[]): RouteNode {
  const root: RouteNode = { segment: '', children: [] };
  for (const page of pages) {
    let node = root;
    for (const seg of page.segments) {
      let child = node.children.find((c) => c.segment === seg);
      if (!child) node.children.push((child = { segment: seg, children: [] }));
      node = child;
    }
    node.file = page.file; // 末端节点登记渲染目标
  }
  // 关键：每层都把静态段排到动态段之前
  const sort = (n: RouteNode) => {
    n.children.sort(
      (a, b) => Number(isDynamic(a.segment)) - Number(isDynamic(b.segment))
    );
    n.children.forEach(sort);
  };
  sort(root);
  return root;
}

/* ---------- ③ URL 匹配 ---------- */
type Match = { file: string; params: Record<string, string> } | null;

function match(root: RouteNode, url: string): Match {
  const segments = url.split('/').filter(Boolean);
  const params: Record<string, string> = {};
  let node = root;

  for (const seg of segments) {
    const hit =
      node.children.find((c) => c.segment === seg) ?? // 先静态
      node.children.find((c) => isDynamic(c.segment)); // 再动态
    if (!hit) return null;
    if (isDynamic(hit.segment)) params[hit.segment.slice(1, -1)] = seg;
    node = hit;
  }
  return node.file ? { file: node.file, params } : null;
}

//   → { file: 'app/blog/[slug]/page.tsx', params: { slug: 'hello' } }

三段函数各司其职，但有两处细节值得停下来看：

  • 建树时排序，而不是匹配时临时判断。sort 只跑一次，之后每次匹配都可以放心地“按顺序找第一个命中”，把正确性从匹配的热路径里挪了出去。
  • 有 file 才代表可渲染。/blog 命中 blog 节点，但它的父节点（根）没有 file——中间节点只是“经过点”。这正对应“有 page.tsx 才是可访问路由”的约定。

幼稚实现 vs 正确实现 ​

很多人写的第一版路由是字符串前缀匹配。把两种写法放在一起看：

diff
- // 幼稚实现：URL 当字符串，路由表当前缀
- function matchNaive(routes: string[], url: string) {
-   return routes.find((r) => url.startsWith(r)) ?? null;
- }
- // matchNaive(['/blog'], '/blogroll')      → 误命中 '/blog'
- // matchNaive(['/[slug]', '/about'], '/about') → 被 '/[slug]' 抢走
+ // 正确实现：先切段，再逐级下钻，每级静态优先
+ const hit =
+   node.children.find((c) => c.segment === seg) ??
+   node.children.find((c) => isDynamic(c.segment));
+ if (!hit) return null;

前缀匹配有两个致命伤：段边界丢失（/blogroll 被 /blog 吃掉），以及优先级依赖注册顺序（谁先注册谁赢）。逐级匹配把“段”变成一等公民，两个问题同时消失。

DANGER

动态段排错位置，是文件系统路由最经典的坑。如果 app/ 下同时存在 [slug]/page.tsx 与 about/page.tsx，而匹配时先查动态段，那么 /about 会被 [slug] 以 { slug: 'about' } 命中——关于页永远不可达，且不报任何错。Next.js 的规则是静态段永远优先于动态段，上面的 sort 就是这条规则的最小实现。

距离真实的 Next.js 路由还差什么 ​

这个 70 行实现能跑通“静态段 + 单级动态段”，但真实路由树还承载着更多维度：

  • 并行路由（parallel routes）：@slot 意味着同一 URL 对应多棵子树，匹配结果不是一个节点，而是一组节点
  • 拦截路由（intercepting routes）：(.)、(..) 让匹配结果依赖导航来源——同一 URL，软导航与硬访问命中不同子树
  • 路由组与 catch-all：(group) 建段但不进 URL；[...slug] 需要“吃掉剩余段”的新段类型
  • 渲染装配：真实节点登记的不止 page，还有 layout/loading/error/template；匹配前还有 middleware、basePath、i18n 等改写

这些都能在今天的三段管线上扩展出来：管线的骨架不变，变的是树节点携带的信息量与匹配时的上下文。

小结 ​

  • App Router 的本质是三段管线：扫描 → 建树 → 匹配
  • 路由树的节点即段，layout 沿匹配路径逐层组合
  • 匹配必须逐级进行且静态优先；字符串前缀匹配会丢段边界、依赖注册顺序
  • 单个动态段只覆盖一级路径，多级路径交给 catch-all
