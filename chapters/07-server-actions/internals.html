拆掉魔法：一张表、一个引用、一次 POST ​

基础篇讲过「调用 action 像调用本地函数」，进阶篇讲过一次往返如何同时带回返回值与重渲染。这篇把窗户纸捅破：'use server' 不是运行时咒语，而是构建期的登记指令——编译器扫到它，就把这个函数收进一张 id → fn 的表；客户端组件导入它时，真正下发的只是一串可序列化的引用（加密 id）。所谓「跨端调用本地函数」，拆开就是一套朴素的三步 RPC：

text
'actions.ts' 里的 'use server'
  │  ① 构建期：扫描导出函数，登记 action id → fn 的表
  ▼
服务端注册表 { a3f2: createTodo, b7c1: deleteTodo }
  │  ② 客户端 createReference(id)：只拿到可序列化的引用
  ▼
客户端代理 actions.createTodo —— 调用即 POST { id, args }
  │  ③ 序列化边界：只有 JSON 能表示的东西能过网
  ▼
服务端 handleAction：解出 id → 查表 → 执行 fn(...args)
  │  ④ 若 action 内触发了 revalidate / redirect
  ▼
同一响应附带：返回值 + 关联路由重渲染的 RSC payload

登记发生在构建期，引用发生在模块加载时，RPC 发生在用户点击时。下面把每个阶段写成可运行的 TypeScript。

第一段：构建期，函数变成表里的一个 id ​

编译器遍历 'use server' 模块的导出，为每个异步函数生成 id 并登记进服务端注册表。客户端的 import 拿到的不是函数体，而是 createReference(id) 的产物——一个带着 id 的可调用占位。这一步直接解释了基础篇的一条规则：客户端组件不能定义 action，只能导入——登记表只存在于服务端构建产物里，客户端凭空多出来的函数无处登记。

第二段：客户端，id 变成「看起来是函数」的代理 ​

引用要能当函数用，靠一层薄代理：拦截属性访问，按方法名生成 (...args) => send({ id, args })。调用方写 actions.createTodo('x')，实际发出的是一次 POST，body 里只有 id 和参数——没有任何函数体过网。

第三段：服务端，查表执行与序列化边界 ​

端点收到 { id, args } 后查表、校验、执行。执行前要先过一道序列化边界：参数必须在 POST body 里活着到达，所以函数、Symbol、带循环引用的对象都进不了这道门；返回值同样要能活着回去。

一次往返，两份载荷

迷你版只返回函数结果。真实实现在 action 触发了缓存失效或 redirect 时，会把返回值与当前路由新的 RSC payload 拼进同一个响应——基础篇讲的「一次往返同时带回数据与 UI」，落点就在这里。

完整实现：约 70 行的迷你 RPC ​

ts
/* ---------- 服务端：一张 id → fn 的表，加一个 RPC 端点 ---------- */

type AnyFn = (...args: any[]) => Promise<unknown>;

// ① 等价于构建期登记：'use server' 文件的每个导出都进这张表
const registry = new Map<string, AnyFn>();

export function registerActions(actions: Record<string, AnyFn>) {
  for (const [name, fn] of Object.entries(actions)) {
    if (registry.has(name)) throw new Error(`action 重名：${name}`);
    registry.set(name, fn); // 真实实现里 id 是构建期生成并加密的哈希
  }
}

// ② 运行期端点：拿到请求体，查表执行
export async function handleAction(body: { id: string; args: unknown[] }) {
  const fn = registry.get(body.id);
  if (!fn) throw new Error(`未知 action：${body.id}`); // id 来自网络，必须防伪造

  // 序列化边界检查：过不了网的参数，在入口处就该报错
  for (const arg of body.args) {
    if (typeof arg === 'function' || typeof arg === 'symbol') {
      throw new TypeError(`参数含 ${typeof arg}，无法跨网络传输`);
    }
    try {
      JSON.stringify(arg); // 类实例在这里会丢光方法，循环引用直接抛错
    } catch {
      throw new TypeError('参数不可序列化（含循环引用？）');
    }
  }

  return await fn(...body.args); // 返回值同样要能过序列化边界
}

/* ---------- 客户端：把 id 包装成「看起来是本地函数」的代理 ---------- */

type Send = (payload: { id: string; args: unknown[] }) => Promise<unknown>;

// ③ createClient(send)：按方法名生成可调用代理，调用即发 RPC
export function createClient<T extends Record<string, AnyFn>>(send: Send): T {
  return new Proxy({} as T, {
    get(_target, name: string) {
      // actions.createTodo('x') ⇒ send({ id: 'createTodo', args: ['x'] })
      return async (...args: unknown[]) => send({ id: name, args });
    },
  });
}

/* ---------- 把两端接起来 ---------- */

// 服务端注册两个业务函数，等价于 'use server' 文件的导出
registerActions({
  createTodo: async (text: string) => {
    const todo = { id: crypto.randomUUID(), text, done: false };
    await db.todo.create({ data: todo }); // db 是服务端闭包，客户端永远摸不到
    return todo;
  },
  deleteTodo: async (id: string) => {
    await db.todo.delete({ where: { id } });
  },
});

// 客户端：一次 POST 就是「跨机器的函数调用」
const actions = createClient(send);

async function send(payload: { id: string; args: unknown[] }) {
  const res = await fetch('/api/action', {
    method: 'POST',
    body: JSON.stringify(payload), // 序列化边界就在这一行
  });
  if (!res.ok) throw new Error(await res.text());
  return res.json();
}

两端各只有两个导出：服务端 registerActions 与 handleAction，客户端 createClient。有两处细节值得停下来看：

  • 查表失败要显式报错。id 来自网络，可被伪造、也可能在发版后过期，registry.get 落空就抛错，这是迷你版的「防伪造」底线。
  • 参数校验做在入口。服务端执行前先试序列化每个参数，把「过不了网」的错误提前暴露，而不是等执行到一半才炸。

序列化边界：什么过不了网 ​

把一个函数直接当 props 传给客户端组件，与把它变成 action 引用，在网络上是两种命运：

diff
- // ✗ 把任意服务端函数当 props 传给客户端组件
- <TodoList onDelete={async (id) => {
-   await db.todo.delete({ where: { id } }); // 函数体只活在服务端内存里
- }} />
- // 序列化时函数不复存在：客户端拿到的不是函数，是 undefined 或直接报错
+ // ✓ 函数顶部写 'use server'，构建期把它登记进 id → fn 表
+ async function deleteTodo(id: string) {
+   'use server';
+   await db.todo.delete({ where: { id } });
+ }
+ // <TodoList onDelete={deleteTodo} /> 传下去的只有几十字节的加密 id
+ // 客户端组件照常调用，调用被代理成 POST { id, args }，执行仍在服务端

跨不过去的原因很物理：函数体活在服务端进程的内存里，序列化器能带走的只有「数据」。action 引用之所以能过网，是因为它本来就只是 id——一个几十字节的字符串；闭包里的 db、环境变量、连接池，全都留在服务端。

闭包是全局的，网络是不排队的

两类事故都源于把本地调用直觉带过网。其一：在 'use server' 文件顶层写 let todos = [] 这类模块级可变状态，所有请求共享同一份内存，并发用户的写入互相串数据，单用户本地开发根本看不出问题——请求级状态应放进参数或 cookies()，而不是闭包。其二：参数里夹带函数、类实例或 Symbol，序列化时函数静默变 undefined、类实例丢光方法，故障拖到服务端执行时才爆。像设计 REST API 一样设计 action 签名：只收原始值与普通对象。

距离真实的 Next.js 还差什么 ​

这套约 70 行的实现跑通了「登记 → 引用 → POST → 查表」的主干，真实协议在每个环节都加了量：

  • action id 的加密与防伪造：迷你版用方法名当 id，攻击者可以枚举着调用任意函数；真实实现里 id 是构建期生成的加密哈希，配合 Origin/Host 的 CSRF 校验与死代码消除，未被引用的函数连端点都不存在
  • FormData 与渐进增强：迷你版只认 JSON；真实 action 原生接收 multipart/form-data，禁用 JavaScript 时浏览器直接原生 POST，服务端照样执行并返回新页面——这正是基础篇「零客户端 JS」表单的底层支撑
  • useActionState / useOptimistic 封装层：迷你版裸收返回值；真实管线在这层之上包装出状态回显、pending 与乐观回滚
  • 错误重试与竞态：客户端对 action 是串行 dispatch，避免并发写乱序；发版后旧页面的 id 可能失效（Failed to find Server Action），UI 上要有「刷新重试」的兜底，而不是硬失败

小结 ​

  • 'use server' 是构建期登记指令：函数进 id → fn 表，客户端只拿到可序列化引用
  • 调用即 RPC：POST { id, args }，序列化边界横在请求参数与返回值两端
  • 闭包变量留在服务端，但模块级可变状态是全局单例，并发请求会互相串数据
  • UI 更新靠响应携带的 RSC 重渲染，而不是函数返回值

现在回到 7.3 的待办实战：每一次创建、删除，在网络上的形状都是一次 POST { id, args }——魔法拆完，剩下的全是工程。
