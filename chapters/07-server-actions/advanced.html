pending 反馈：useFormStatus 的边界规则 ​

useActionState 的 pending 只能在定义表单的那个组件里用。实践中提交按钮往往是独立的通用组件，React 提供 useFormStatus 让按钮自己感知所属表单的提交状态——但它有一条硬规则：调用它的组件必须作为 <form> 的子组件存在，不能和表单写在同一个函数里。

tsx
'use client';

import { useFormStatus } from 'react-dom';

export function SubmitButton() {
  const { pending } = useFormStatus(); // 读取最近的父级 <form> 状态
  return (
    <button type="submit" disabled={pending}>
      {pending ? '保存中…' : '保存'}
    </button>
  );
}

乐观更新：useOptimistic ​

网络往返再快也有感知延迟。useOptimistic 让你在 Action 结果返回前先假设成功更新 UI，Action 失败或完成后再与真实状态对齐。典型结构：乐观状态 + 一个客户端本地的 transition 包装函数。

tsx
'use client';

import { useOptimistic, useTransition } from 'react';
import { incrementLike } from '@/app/actions';

export function LikeCount({ initialLikes, postId }: { initialLikes: number; postId: string }) {
  const [optimisticLikes, addOptimistic] = useOptimistic(
    initialLikes,
    (state) => state + 1 // 乐观派生：先 +1
  );
  const [, startTransition] = useTransition();

  return (
    <button
      onClick={() =>
        startTransition(async () => {
          addOptimistic(null);       // 1. UI 立刻 +1
          await incrementLike(postId); // 2. 服务端确认真实结果
        })
      }
    >
      ♥ {optimisticLikes}
    </button>
  );
}

::: warn 乐观更新必须有「退路」 乐观 UI 是对成功的赌注：Action 抛错后 React 会自动回滚到真实状态，但你需要确保错误能被用户感知（error.tsx 边界或 try/catch 提示），否则用户会以为操作已生效。涉及金额、权限的操作不要做乐观更新。 :::

写之后：四种刷新手段怎么选 ​

Action 改完数据，Next.js 提供四种让 UI 与数据重新对齐的手段，语义差别必须记牢：

手段调用位置语义响应里是否带重渲染
updateTag(tag)仅 Server Action立即失效标签，下一次读取等新数据（read-your-own-writes）是
revalidateTag(tag, 'max')Action / Route Handlerstale-while-revalidate：先给旧值，后台刷新否
revalidatePath(path)Action / Route Handler按 URL 路径失效，适合只有单一路由受影响是
refresh()Server Action不取缓存失效，只重新拉取当前路由 RSC是
ts
'use server';

import { updateTag } from 'next/cache';
import { revalidatePath } from 'next/cache';

export async function createPost(formData: FormData) {
  const post = await db.post.create({
    data: { title: String(formData.get('title')) },
  });

  // 列表页与详情页都打了对应标签：下一次读取等待新数据
  updateTag('posts');
  updateTag(`post-${post.id}`);
  // 需要跳转时：先失效、后 redirect（redirect 抛控制流异常，其后代码不执行）
  revalidatePath('/posts');
}

updateTag 只能在 Server Action 里调

在 Route Handler 或 Webhook 中调用会抛错。外部系统触发的失效走 revalidateTag(tag, 'max')——第二个参数缓存 profile 是 16 中新模型下的必填项。

after()：响应之后的后台工作 ​

日志、埋点、发欢迎邮件这类副作用不该拖慢用户响应。after() 从 next/server 导入，把回调安排在响应发送（或预渲染）完成之后执行，可用于 Server Components、Server Functions、Route Handlers 与 proxy：

ts
'use server';

import { after } from 'next/server';
import { headers } from 'next/headers';

export async function deletePost(postId: string) {
  await db.post.delete({ where: { id: postId } });

  after(async () => {
    // 响应已返回给用户后执行；此处可以读 headers/cookies
    const ua = (await headers()).get('user-agent') ?? 'unknown';
    await auditLog.delete(postId, ua);
  });
}

Action 安全：框架给了什么，你还要补什么 ​

层框架已做你必须自己做
CSRF比对 Origin 与 Host，不匹配拒绝；反代/CDN 域名配 serverActions.allowedOrigins——
体积请求体默认上限 1MB大文件场景配 serverActions.bodySizeLimit
引用action id 构建期加密，未使用的函数被死代码消除，无公开端点——
闭包内联 action 捕获的变量加密后下发客户端多实例/自托管部署设置稳定的 NEXT_SERVER_ACTIONS_ENCRYPTION_KEY
业务——每个 action 内鉴权 + 输入校验 + 返回值收窄 + 所有权复核

所有权复核最容易被忽略：客户端合法地告诉你「操作哪个 id」，但不应该由它提供行内容或归属。正确做法是只接收 id，用会话里的用户身份重新查库确认归属：

ts
'use server';

export async function completeItem(itemId: string) {
  const session = await auth();
  if (!session?.user) return;

  // 按 id + ownerId 双条件查询，杜绝越权改别人的数据
  const item = await db.item.findFirst({
    where: { id: itemId, ownerId: session.user.id },
  });
  if (!item) return;
  await db.item.update({ where: { id: item.id }, data: { completed: true } });
}

滚动部署与「Failed to find Server Action」

每个 action 由构建产物中的 action id 标识，Next 至多每 14 天轮换一次。用户开着旧页面时发版，可能命中已不存在的 id。官方建议活跃用户时段用滚动发布、保持加密密钥稳定，并在 UI 上把该错误呈现为「刷新重试」而不是硬失败。

文件上传与大表单 ​

表单的 enctype="multipart/form-data" 由框架自动处理，Action 里直接从 FormData 取 File：

ts
'use server';

export async function uploadAvatar(formData: FormData) {
  const file = formData.get('avatar');
  if (!(file instanceof File)) throw new Error('缺少文件');

  const bytes = await file.arrayBuffer(); // 在服务端读取二进制内容
  await objectStore.put(`avatars/${crypto.randomUUID()}.png`, bytes);
}

小结 ​

  • useFormStatus 必须在表单的独立子组件中调用；useOptimistic 提供先更新后确认的乐观 UI，失败会自动回滚
  • 写后刷新按语义选择：要自己的变更立刻可见用 updateTag，后台渐进刷新用 revalidateTag(tag, 'max')，单路由用 revalidatePath
  • after() 承接不阻塞响应的副作用；安全上框架负责 CSRF/加密/体积，业务鉴权与所有权复核必须落在每个 action 内部
