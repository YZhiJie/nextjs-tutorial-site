从「写一个 API 路由」到「直接写函数」 ​

在 App Router 之前，一次表单变更通常意味着：写一个 API 路由 → 客户端 fetch('/api/...', { method: 'POST' }) → 手动处理 loading → 提交后再重新取数刷新页面。

Server Actions 把这条链路压缩成一个异步函数：在函数顶部写 'use server'，它就只在服务端执行；把它直接绑给 <form>，提交、序列化、重渲染全部由框架接管。

  • 传给 <form> 的 action 属性，或传给 <button> 的 formAction 属性
  • 或在客户端组件的事件处理器、useEffect 中通过 startTransition 调用

底层使用 HTTP POST，也只有 POST 能调用它们。

定义一个 Server Action ​

'use server' 可以标在文件顶部（该文件所有导出都是 Server Function，客户端组件只能以这种方式导入），也可以标在单个异步函数内部：

ts
'use server';

export async function createPost(formData: FormData) {
  const title = formData.get('title');
  const content = formData.get('content');

  // 服务端：写库（这里省略真实数据库调用）
  await db.post.create({ data: { title: String(title), content: String(content) } });
}

最小表单：零客户端 JS ​

在服务端组件里把 action 直接绑给表单，不需要任何 'use client'：

tsx
import { createPost } from '@/app/actions';

export default function NewPostPage() {
  return (
    <form action={createPost}>
      <label>
        标题
        <input type="text" name="title" required />
      </label>
      <label>
        正文
        <textarea name="content" required />
      </label>
      <button type="submit">发布</button>
    </form>
  );
}

渐进增强是默认行为

服务端组件中的表单在 JavaScript 未加载或被禁用时照样可以提交——浏览器原生 POST 到当前路由，服务端执行函数后返回新页面。客户端组件里的表单则会在 JS 未就绪时排队等待水合，水合后提交不再整页刷新。

三种调用方式 ​

调用位置写法适用场景
服务端组件表单<form action={fn}>标准提交，支持无 JS
客户端组件表单导入模块级 action，<form action={fn}>需要错误展示、pending 反馈、乐观更新
客户端事件onClick 里包 startTransition 调用点赞、计数等非表单触发

在客户端组件里不能定义 Server Function，只能从 'use server' 模块导入。也可以把 action 作为 props 从服务端组件下发给客户端组件。

useActionState：表单三态 ​

只要需要「校验错误回显」或「提交中禁用按钮」，就把表单放进客户端组件，用 React 19 的 useActionState。它返回三元组：状态、包装后的 action、pending 布尔值。

服务端函数的签名要相应改变：第一个参数是上一次的状态（或初始状态），FormData 退居第二：

ts
'use server';

export type FormState = { message: string; ok: boolean };

export async function createUser(
  _prev: FormState,
  formData: FormData
): Promise<FormState> {
  const email = String(formData.get('email') ?? '');
  if (!/^\S+@\S+\.\S+$/.test(email)) {
    return { ok: false, message: '邮箱格式不正确' }; // 校验失败，状态回显
  }
  await db.user.create({ data: { email } });
  return { ok: true, message: '创建成功' };
}

tsx
'use client';

import { useActionState } from 'react';
import { createUser, type FormState } from '@/app/actions';

const initialState: FormState = { message: '', ok: false };

export function SignupForm() {
  // 三态：state（服务端返回）、formAction（绑给表单）、pending（提交中）
  const [state, formAction, pending] = useActionState(createUser, initialState);

  return (
    <form action={formAction}>
      <input type="email" name="email" required />
      <button type="submit" disabled={pending}>
        {pending ? '提交中…' : '注册'}
      </button>
      <p aria-live="polite" style={{ color: state.ok ? 'green' : 'crimson' }}>
        {state.message}
      </p>
    </form>
  );
}

一次往返同时带回数据与 UI ​

当 action 内调用了 updateTag、revalidatePath、refresh()、设置/删除 cookie 或 redirect() 时，Next.js 会在同一个 POST 往返里执行函数并重渲染当前路由，响应中的 Flight 流同时包含：

  1. action 的返回值（供 useActionState 或 await 使用）
  2. 当前路由新的 RSC Payload（客户端直接提交，无需二次请求）

这是 Server Actions 与「手写 API + 手动刷新」相比最核心的效率差异。

::: warn 不要把动作当成可随意访问的内部接口 Server Action 通过对所在页面发 POST 调用，任何能发 POST 的人都能直接请求它，不经过你的 UI。框架做了 CSRF 校验（比对 Origin/Host）、1MB 请求体限制、加密 action id，但鉴权必须在每个函数内部重复做，「这个表单只在登录后渲染」不是安全边界。 :::

常见误区 ​

  • 误区一：在客户端组件里写 'use server'。 客户端只能导入模块级 action，定义留在服务端文件。
  • 误区二：action 里不做鉴权，只靠 UI 隐藏按钮。 Action 可被直接 POST，必须函数内鉴权。
  • 误区三：忘记 useActionState 改签名。 接入 hook 后服务端函数第一个参数是 prevState，FormData 后移。
  • 误区四：用 Promise.all 并行调多个 Action。 客户端对 Server Actions 是串行 dispatch；要并行就把并行逻辑放进同一个 Action 内部。

小结 ​

  • Server Action 是标记 'use server' 的异步函数，通过表单 action 或 transition 调用，底层走 POST
  • 服务端组件表单天然渐进增强，禁用 JS 也能提交；useActionState 提供状态、action、pending 三态
  • 一次 Action 往返可以同时完成执行、缓存失效与路由重渲染；每个 Action 都是不可信入口，鉴权必须内置
