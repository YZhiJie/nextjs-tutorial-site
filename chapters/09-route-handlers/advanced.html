Webhook：必须读原始文本，不能先 json() ​

接收第三方 Webhook 时，对方通常用「原始请求体 + 密钥」算一个 HMAC 签名放在头里。如果你先 await request.json() 再序列化回去，字段顺序、空白差异都会导致签名对不上。正确做法是 await request.text() 拿原始字节，先验签再解析：

ts
import { createHmac, timingSafeEqual } from 'node:crypto';
import { revalidateTag } from 'next/cache';

export async function POST(request: Request) {
  const rawBody = await request.text(); // 关键：原始文本，不做 JSON 转写
  const signature = request.headers.get('x-webhook-signature') ?? '';

  const expected = createHmac('sha256', process.env.WEBHOOK_SECRET!)
    .update(rawBody)
    .digest('hex');

  // 等长恒定时间比较，防止计时侧信道
  const valid =
    signature.length === expected.length &&
    timingSafeEqual(Buffer.from(signature), Buffer.from(expected));

  if (!valid) {
    return Response.json({ error: '签名无效' }, { status: 401 });
  }

  const event = JSON.parse(rawBody); // 验签通过后才解析
  if (event.type === 'post.published') {
    // 外部触发的再生：Route Handler 不能用 updateTag
    revalidateTag('posts', 'max');
  }
  return new Response('ok', { status: 200 });
}

App Router 不需要 bodyParser

Pages Router 时代要配置 bodyParser: false 才能拿到原始请求体；App Router 的 Route Handler 直接基于 Web Request，request.text() 天然是未解析的原始内容。

CORS 与缓存头 ​

跨域开放给浏览器的端点要显式返回 CORS 头。简单场景在 Handler 内直接设置；预检请求（OPTIONS）单独导出处理：

ts
const CORS_HEADERS = {
  'Access-Control-Allow-Origin': 'https://app.example.com',
  'Access-Control-Allow-Methods': 'GET, POST, OPTIONS',
  'Access-Control-Allow-Headers': 'Content-Type, Authorization',
};

export async function OPTIONS() {
  return new Response(null, { status: 204, headers: CORS_HEADERS });
}

export async function GET() {
  const data = await getPublicData();
  // 可缓存的公开响应：浏览器/CDN 缓存 60 秒
  return Response.json(data, {
    headers: { ...CORS_HEADERS, 'Cache-Control': 'public, max-age=60' },
  });
}

proxy.ts：请求到达页面前的 Node 代理 ​

16 把 middleware.ts 更名为 proxy.ts，导出名从 middleware 改为 proxy，默认运行在 Node.js 运行时（不能再设置 runtime，设置会报错）。它在路由渲染之前执行，适合做粗粒度的重定向、重写、请求/响应头改写。

ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  const session = request.cookies.get('session');
  const { pathname } = request.nextUrl;

  // 未登录访问 /dashboard：重定向到登录页，并带上回跳地址
  if (pathname.startsWith('/dashboard') && !session) {
    const loginUrl = new URL('/login', request.url);
    loginUrl.searchParams.set('from', pathname);
    return NextResponse.redirect(loginUrl);
  }

  // 已登录：把会话标识写入请求头，供下游 Route Handler/页面读取
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set('x-session-present', '1');

  return NextResponse.next({ request: { headers: requestHeaders } });
}

// matcher：只在目标路径上运行，排除静态资源与图片优化
export const config = {
  matcher: ['/dashboard/:path*', '/admin/:path*'],
};

NextResponse 的四种产出：redirect() 跳转、rewrite() 内部重写（URL 不变）、next() 放行并可改写头、直接 new Response() 短路响应。

proxy 不是鉴权边界

官方明确：proxy 适合「乐观检查」（基于 cookie 是否存在的跳转），不是完整的会话管理或授权方案。Server Action 是 POST 到所在页面路由的，matcher 改动可能让代理覆盖悄悄失效；真正的鉴权必须在每个 Server Action 和 Route Handler 内部重复执行。proxy 里也不应做慢查询取数，它跑在所有匹配请求的最前面。

matcher：精确匹配是必修课 ​

不写 matcher，代理会对每个请求运行，包括 _next/static、_next/image 和 public/ 资源——鉴权逻辑一旦误伤，CSS/图片都会被拦截。matcher 支持字符串、数组、参数修饰符（:path* 零或多个、:path? 零或一个）和负向正则：

ts
export const config = {
  matcher: [
    // 排除 api、_next/static、_next/image 以及 .png 文件
    '/((?!api|_next/static|_next/image|.*\\.png$).*)',
  ],
};

完整请求链路上代理的位置：headers() → redirects() → proxy → beforeFiles 重写 → 文件系统路由 → afterFiles 重写 → 动态路由 → fallback 重写。需要在响应发出后做日志埋点时，代理的第二个参数 event 提供 waitUntil(promise)，保持函数存活直到后台任务结束。

middleware → proxy 迁移对照 ​

维度旧：middleware.ts新：proxy.ts
文件名middleware.ts（项目根或 src/）proxy.ts（位置相同）
导出函数middleware(request)proxy(request) 或默认导出
运行时历史为 Edge，15.x 逐步支持 Node默认且仅 Node，声明 runtime 会报错
类型NextMiddleware 等NextRequest/NextResponse，简写类型 NextProxy
能力变化——重定向、重写、matcher、waitUntil 语义不变

官方 codemod 只做机械更名，改名后仍需自行回归代理逻辑：

bash
npx @next/codemod@canary middleware-to-proxy .

为什么不再需要 Edge

Edge Runtime 带来两套运行时行为分叉（API 子集不同、边缘冷启动心智、生态适配成本）。16 的 SSR 已迁移到原生 Node.js 流，官方称高负载吞吐有约 22% 的提升空间；代理统一到 Node 后，node:crypto、数据库驱动等完整生态直接可用，单运行时也消除了「这段代码在 Edge 能不能跑」的持续判断。

代理是「最后手段」：纯配置能解决的跳转优先用 next.config.ts 的 redirects()（构建期确定、无运行时代码）；只有需要请求数据或复杂条件逻辑时才动用 proxy。

小结 ​

  • Webhook 必须 request.text() 取原始 body 做 HMAC 验签，通过后再解析；CORS 与缓存头都是标准响应头，多路由共用时收敛到 proxy/config
  • proxy.ts 是 16 的 Node 代理：proxy 函数 + matcher + NextResponse 四件套，跑在渲染之前但不是鉴权边界
  • middleware 到 proxy 是文件/函数更名加运行时统一，codemod 打底、逻辑自行回归
