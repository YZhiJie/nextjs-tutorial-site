洋葱模型：一次请求的两半程 ​

基础篇把 Route Handler 当作一个「真正的 HTTP 端点」，进阶篇在它前面加了一层 proxy.ts。两者之间其实隔着一条更古老的管线——中间件洋葱链（middleware onion）。理解它，proxy 为什么只能粗筛、route.ts 为什么必须独立验真，才会从「官方建议」变成「结构上的必然」。

它只有一个心智：请求沿链路逐层穿入，命中处理函数后再原路逐层返回。每层都经历两半程——next() 之前是「前半段」（before），next() 返回之后是「后半段」（after）。

text
 请求
  │
  ├─▶ ① logger    before：记录开始时间
  │    ├─▶ ② auth     before：校验会话
  │    │    ├─▶ ③ handler  命中：写出响应   ← 洋葱核
  │    │    ◀─┤     auth 的后半段
  │    ◀─┤     logger 的后半段：打印总耗时
  ▼
 响应（沿进入顺序原路返回）
 实际顺序：before1 → before2 → handler → after2 → after1

手写 Koa 式 compose：约 70 行的迷你中间件引擎 ​

核心只有两个概念：dispatch(i) 负责「进入第 i 层」，next 则是「进入第 i+1 层」的函数。

dispatch(i) 递归：next 就是「下一层的调用」 ​

ts
type Ctx = { path: string; method: string; user?: { id: string }; res?: Response };

// 每层中间件：拿到上下文与 next（调用即进入下一层），返回 Promise
type Middleware = (ctx: Ctx, next: () => Promise<void>) => Promise<void> | void;

/* ---------- ① 引擎：把中间件数组折成一个 run(ctx) ---------- */
function compose(middlewares: Middleware[]) {
  return async function run(ctx: Ctx): Promise<Response> {
    let index = -1; // 已进入的最大层号，用于拦截重复调用 next

    function dispatch(i: number): Promise<void> {
      if (i <= index) {
        // 同一个 next 被调用两次：洋葱链会被撕成两条，必须报错
        return Promise.reject(new Error(`next() 在第 ${i} 层被重复调用`));
      }
      index = i;

      const fn = middlewares[i];
      if (!fn) return Promise.resolve(); // 没有更多层：到达洋葱核

      const next = () => dispatch(i + 1); // 关键一行：next 即「进入下一层」

      try {
        // 必须 return：把当前层的 Promise 接进整条链，
        // 下半程才会被等待，控制权也才在整条链走完后回到 run
        return Promise.resolve(fn(ctx, next));
      } catch (err) {
        return Promise.reject(err);
      }
    }

    await dispatch(0);
    return ctx.res ?? new Response(null, { status: 204 });
  };
}

/* ---------- ② 三层中间件：日志 / 鉴权 / 处理器 ---------- */
const logger: Middleware = async (ctx, next) => {
  const start = Date.now();          // before：进入时
  await next();                      // 等待下半程回卷
  console.log(`${ctx.method} ${ctx.path} ${Date.now() - start}ms`); // after：返回时
};

const requireSession: Middleware = async (ctx, next) => {
  if (!ctx.user) {
    // 不调用 next，直接给出响应：短路，后续所有层都不执行
    ctx.res = Response.json({ error: 'unauthorized' }, { status: 401 });
    return;
  }
  await next();
};

const handler: Middleware = async (ctx) => {
  ctx.res = Response.json({ ok: true, path: ctx.path }); // 洋葱核
};

/* ---------- ③ 组装并体验两种结局 ---------- */
const app = compose([logger, requireSession, handler]);
// await app({ path: '/api/orders', method: 'GET', user: { id: 'u1' } }) // → 200
// await app({ path: '/api/orders', method: 'GET' })  // 未登录 → 短路 401

递归在这里不是炫技：next 一旦被调用，控制权就深入下一层；只有当下一层连同它之后的整条链都 resolve，控制权才回卷到这一层 next() 调用的下一行。「后半段」就是这一行之后的代码。

为什么必须 return next() ​

上面那句 return Promise.resolve(fn(ctx, next)) 是整个引擎的命门。把两种写法并排看：

diff
- // ✗ 只调用 next，不等它完成
- const logger: Middleware = async (ctx, next) => {
-   const start = Date.now();
-   next(); // 交出控制权就立刻往下走，没有 await、没有 return
-   console.log('耗时', Date.now() - start); // handler 还没跑完，耗时是错的
- };
+ // ✓ await next()：等整条下半程原路回卷后才继续
+ const logger: Middleware = async (ctx, next) => {
+   const start = Date.now();
+   await next(); // 等到洋葱核返回、后半段层层回卷
+   console.log('耗时', Date.now() - start); // 此刻才是真正的总耗时
+ };

漏掉 await/return 时，logger 在「进入下一层」的瞬间就继续执行后半段，而下一层的 Promise 还悬在空中——after 逻辑要么在响应发出之后才跑（日志与真实请求脱节），要么因为没人等待而被丢弃。返回 Promise 是「后半段存在」的前提，不是可选优化。

短路：不调用 next 就是鉴权 ​

洋葱链还有一条隐藏规则：某层不调用 next，直接给出响应，从这一层起的后续链路就此短路（short-circuit）。它自己写在 next() 之后的代码被跳过，它后面的层连 before 都不会进入——上面 requireSession 里那个 return 就是它。注意区分：短路层之前的外层因为已经调用过 next，它们的后半段仍会正常回卷（next() 只是正常 resolve 了）。短路的价值在于成本前置：未登录请求在第二层就被挡住，昂贵的处理器与数据库查询根本不会启动。

自测

链是 [logger, auth, handler]。auth 不调用 next、直接返回 401 时：auth 自己写在 next() 之后的代码、handler 层、以及 logger 写在 next() 之后的代码，各会执行吗？

对照真实的 Next.js 16.3：proxy.ts 与 matcher ​

真实框架把这条链挪进了框架层。16 里 middleware.ts 已更名为 proxy.ts（导出函数名同步改为 proxy），默认运行在 Node.js 运行时，跑在路由匹配之前——它就是洋葱链固定在页面/Route Handler 之外的第一层外壳。

ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  const hasSession = request.cookies.has('session'); // 只判断 cookie 是否存在
  const { pathname } = request.nextUrl;

  if (pathname.startsWith('/dashboard') && !hasSession) {
    // 不进入下一层，直接返回：等价于中间件短路，后续全部跳过
    return NextResponse.redirect(new URL('/login', request.url));
  }
  return NextResponse.next(); // 等价于 next()：放行到下一层
}

// matcher：只有命中的路径才进入这层洋葱，静态资源与图片天然排除
export const config = { matcher: ['/dashboard/:path*'] };

NextResponse.next() 与 NextResponse.redirect() 恰好对应洋葱链的「调用 next」与「短路」两种结局；matcher 则决定哪些请求站在链的入口。:path*（零或多段）、:path?（零或一段）与负向正则都是 matcher 的表达式语法。

proxy 与 route handler：谁负责哪一半 ​

层洋葱里的位置该做什么不该做什么
proxy.ts最外层 beforecookie 存在性、轻量验签、重定向查库、慢查询、作为授权依据
route.ts洋葱核真实会话校验（DAL）+ 业务依赖 proxy 已放行

proxy 不是鉴权边界

proxy 只做「乐观检查」（optimistic check）——看一眼 cookie 在不在，挡的是随手输错地址的流量。真实鉴权必须落到数据层（DAL）：校验签名与有效期、查用户是否存在。在 proxy 里查数据库是经典误区：它跑在每个匹配请求的最前面，一次慢查询会拖垮全站；而且静态资源、Server Action 等路径可能绕过或覆盖它。鉴权的真相只认数据层，不认小区门口那道栏杆。

三个经典陷阱 ​

  • 只 return next 不 await：after 链在响应发出后才跑或彻底丢失，日志耗时失真（见上文 diff）。任何需要收尾的层，都必须 return/await 下一层的 Promise。
  • 真实鉴权放在 proxy、API 路由却不校验：curl 直连 /api/orders 时 cookie 可能是伪造或过期的，proxy 只知道「有这个字符串」。Handler 内不调用 getSessionUser()，等于把后门留在洋葱核里——短路只挡浏览器流量，不挡攻击者。
  • matcher 写错：漏写或写成「匹配一切」，会让 _next/static、/_next/image、public/ 资源也进入这层洋葱；鉴权逻辑一旦误伤，CSS 与图片被重定向，页面直接破相。用 '/((?!api|_next/static|_next/image|.*\\.png$).*)' 这类负向匹配把非页面路径排除在外。

距离真实实现还差什么 ​

  • matcher 编译：路径模式在构建期被编译成正则或前缀树，代理只对命中路径启动，避免每个请求都付一次匹配成本
  • 响应后钩子与只读契约：event.waitUntil(promise) 让函数在响应发出后继续存活完成 after 埋点；proxy 又拿不到请求体、改不了响应体，能力被刻意收窄——这也是它不适合做鉴权的结构性原因

小结 ​

  • 洋葱模型 = 前半段（next 之前）+ 洋葱核 + 后半段（next 之后），顺序是 before1 → before2 → handler → after2 → after1
  • compose 用 dispatch(i) 递归实现，next = () => dispatch(i+1)；必须 return/await next 才能保证后半段执行
  • 不调用 next 即短路，后续层的 before 与 after 全部跳过——这正是鉴权层的工作方式
  • 真实 Next.js 16.3 里，proxy.ts 是最外层的乐观检查（cookie 存在 + 轻量验签），真实鉴权必须下沉到数据层，绝不在 proxy 里查库
