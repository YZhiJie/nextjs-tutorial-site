场景：带登录墙的用户后台 ​

需求由三部分组成：

  • 未登录用户访问 /dashboard/* 一律跳转到登录页，登录后跳回原目标
  • /api/me、/api/orders 等 JSON 接口给前端与移动端共用，未登录返回 401（而不是跳转 HTML）
  • 静态资源、图片优化请求绝不能被拦截拖慢

这恰好是 proxy 与 Route Handler 的分工：proxy 负责浏览器页面的乐观拦截，Handler 负责接口层的真实鉴权——两层都不可省。

防护层检查内容未登录的反馈能否单独依赖
proxy.tscookie 是否存在（不验签、不查库）页面 307 跳登录页否，只挡随手流量
Route Handler会话签名/有效期 + 用户存在性401 JSON是，接口的真实边界
页面数据层同 Handler 的真实会话校验redirect('/login')是，页面的真实边界
数据查询ownerId 归属过滤空结果/404是，防越权读他人数据

第一步：proxy 只做「有没有会话」的乐观检查 ​

ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

const PROTECTED_PAGE = /^\/dashboard(\/|$)/;

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const hasSession = request.cookies.has('session');

  // 只拦截后台页面；API 的 401 交给 Route Handler 自己返回
  if (PROTECTED_PAGE.test(pathname) && !hasSession) {
    const loginUrl = new URL('/login', request.url);
    loginUrl.searchParams.set('from', pathname); // 登录后回跳
    return NextResponse.redirect(loginUrl);
  }

  return NextResponse.next();
}

// 精准 matcher：后台页面才进代理，静态资源天然排除
export const config = {
  matcher: ['/dashboard/:path*'],
};

::: warn cookie 存在 ≠ 已登录 proxy 只检查 cookie 是否存在（一次字符串判断，不做数据库/密钥验证），它挡住的是「随手输错地址的未登录流量」。过期、伪造的 cookie 必须由页面数据层与 Handler 用真实会话校验再拦一道。 :::

第二步：登录动作写入 httpOnly cookie ​

登录是 UI 表单变更，用 Server Action 设置会话 cookie，并在设置后框架自动重渲染当前页面：

ts
'use server';

import { cookies } from 'next/headers';
import { redirect } from 'next/navigation';
import { createSession, verifyPassword } from '@/lib/auth';

export async function login(formData: FormData) {
  const email = String(formData.get('email') ?? '');
  const password = String(formData.get('password') ?? '');
  const from = String(formData.get('from') ?? '/dashboard'); // 回跳目标随表单带回

  const user = await verifyPassword(email, password);
  if (!user) {
    return { error: '邮箱或密码错误' };
  }

  const token = await createSession(user.id);
  const jar = await cookies();
  jar.set('session', token, {
    httpOnly: true, // JS 读不到，防 XSS 窃取
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax', // 跨站 POST 默认不带，缓解 CSRF
    path: '/',
    maxAge: 60 * 60 * 24 * 7,
  });

  redirect(from.startsWith('/') ? from : '/dashboard'); // 开放重定向防护：只允许站内路径
}

第三步：API 层做真实鉴权 ​

接口不跳转，统一返回状态码。把会话解析收敛成一个辅助函数，所有 Handler 复用：

ts
import { NextRequest } from 'next/server';
import { getSessionUser } from '@/lib/auth';
import { db } from '@/lib/db';

export async function GET(request: NextRequest) {
  // 真实鉴权：校验签名、有效期，查用户；与 proxy 的乐观检查完全独立
  const user = await getSessionUser();
  if (!user) {
    return Response.json({ error: 'unauthorized' }, { status: 401 });
  }

  const url = new URL(request.url);
  const page = Number(url.searchParams.get('page') ?? '1');
  const orders = await db.order.findMany({
    where: { ownerId: user.id }, // 数据层再次按归属隔离
    skip: (page - 1) * 20,
    take: 20,
  });

  return Response.json({ page, orders });
}

::: steps 一次未登录访问的完整链路

  1. 浏览器请求 /dashboard/orders，proxy 发现无 session cookie → 307 跳 /login?from=/dashboard/orders
  2. 登录成功，Action 写 httpOnly cookie 并跳回原路径
  3. 再次进入 /dashboard，proxy 放行；页面调用 getSessionUser() 验真后渲染
  4. 页面内的客户端组件 fetch /api/orders，Handler 独立验真；cookie 过期时返回 401，前端据此跳登录
  5. 第三方直接 curl /api/orders（无 cookie）拿到 JSON 401，而非 HTML 登录页 :::

第四步：给 API 配可观测与兜底 ​

把 307 和 401 分开打点

用 after() 记录访问日志（不阻塞响应）时，区分「代理层 307」与「Handler 401」两种未授权来源：前者量大自然正常，后者在已登录用户身上突然升高，往往意味着会话过期策略出问题或有人在探测接口，告警阈值应该不同。

  • 用 after() 记录访问日志（不阻塞响应），日志中区分「代理拦截」与「Handler 401」两种未授权来源
  • 在 app/api/ 同级或全局 error.tsx/响应封装里统一错误形状：{ error: string }，便于移动端处理
  • 涉及跨域调用的开放接口（非 cookie 会话）按进阶篇配置 CORS，并优先用 token 方案

最佳实践清单 ​

  • [ ] proxy 的 matcher 精确到受保护前缀，不使用「匹配一切」的裸代理
  • [ ] proxy 只做 cookie 存在性等乐观检查，不含慢查询、不作为授权依据
  • [ ] 所有敏感 Handler 与页面数据层各自调用 getSessionUser()，不信任代理放行
  • [ ] 会话 cookie 三件套：httpOnly + secure（生产）+ sameSite: 'lax'
  • [ ] 回跳地址 from 校验为站内相对路径，杜绝开放重定向
  • [ ] 接口按数据归属查询（ownerId），鉴权与对象级权限双重检查
  • [ ] 页面未授权用 redirect，API 未授权用 401 JSON，两条反馈路径分开

上线前检查 ​

  • [ ] 无 cookie 直接访问 /dashboard 被 307 到登录页，且 from 正确回跳
  • [ ] 无 cookie 请求 /api/orders 返回 401 JSON
  • [ ] 伪造/过期 cookie 能通过 proxy 但被数据层与 Handler 拒绝
  • [ ] CSS、JS、/_next/image 请求不经过代理（用 Network 面板确认无多余 307）
  • [ ] 越权请求他人订单 id 返回空或 404，查不到他人数据
  • [ ] 登出后点浏览器后退不会看到受保护内容（配合 Cache-Control: no-store 评估敏感页）

小结 ​

  • 生产级防护是两层结构：proxy 用精确 matcher 做页面乐观跳转，Handler/数据层用真实会话做接口验真
  • 会话 cookie 走 httpOnly/secure/sameSite，回跳参数限定站内，查询再按 ownerId 隔离
  • 页面未授权走重定向、API 未授权走 401，两条链路在演练场与实验中都可以完整复现
