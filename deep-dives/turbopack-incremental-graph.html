从第二次构建变快说起 ​

同一个项目连续构建两次，第一次九十秒，第二次二十几秒；但如果中间改了 next.config、.env 或 tsconfig，第三次又回到九十秒。开发服务器里则是另一组现象：改一个组件，页面几百毫秒内更新；改一个路由处理函数，'use cache' 的结果也跟着失效，但内存没有一路涨上去。

这三组现象分别对应三条机制：持久化缓存（产物能不能跨进程复用）、增量应用（一次变更能不能只改图的一部分）、代际失效（缓存键怎么知道代码已经换了）。

需要先划清引用层次：增量构建图本身在 Turbopack 的 Rust 内核里，next/dist 看不到节点和边的数据结构。这一篇引用的是 Next.js 编排层能控制的东西——交给内核的参数与触发失效的信号。这个边界本身，就是理解 16.3 Turbopack 缓存行为的关键。

逐项读：

  • persistentCaching 来自 experimental.turbopackFileSystemCacheForBuild：它被原样传给内核的 isPersistentCachingEnabled。也就是说，构建期是否落盘复用，是由 Next 配置显式决定的，而不是内核自己猜
  • dependencyTracking 跟着持久化缓存一起开：persistentCaching || hasDeferredEntries。没有依赖追踪，就没有「这个产物依赖了哪些文件」的记录，缓存命中也就无从判断
  • turbopackMemoryEviction 与 skipCompaction 是资源侧调节：前者对应内存回收模式，后者在 NEXT_USE_POST_BUILD=1 时跳过压缩，避免后构建阶段再花一次磁盘整理的成本
  • turbopackSeedCacheFromWorktree 走的是另一条路：它不是「本次构建的缓存」，而是从同一仓库的其它 worktree 里找一份最新的同版本缓存，直接种进来

最后一个细节值得注意：rootPath、projectPath、nextConfig、defineEnv、buildId 都参与了项目创建。它们任何一个变化，都可能让缓存键整体不再匹配——这正是后面「改配置就变慢」的伏笔。

② 缓存的失效单位是「版本目录 + 不可变文件」 ​

持久化缓存的目录布局，比开关更能说明它为什么敢跨进程复用：

源码对照 · next/dist/lib/turbopack-cache-seed.js · L62–L104
js
function seedTurbopackCacheIfNeeded({ projectDir, distDir }) {
    // This gets the version assuming that nothing is dirty.
    // If things are dirty, turbopack would write things
    // in a different location. There are other circumstances
    // as well. This only matters for people developing turbopack
    // see handle_db_versioning in turbotask backend for more details.
    const version = (0, _swc.getTurbopackCacheVersion)();
    if (!version) return;
    const worktreeInfo = (0, _gitworktree.getGitWorktreeInfo)(projectDir);
    if (!worktreeInfo) return;
    const cacheDir = _path.default.join(distDir, 'cache', 'turbopack');
    const targetVersionDir = _path.default.join(cacheDir, version);
    if (dirHasEntries(targetVersionDir)) return;
    let sourceVersionDir;
    try {
        sourceVersionDir = findSeedSource(worktreeInfo, projectDir, distDir, version);
    } catch  {
        return;
    }
    if (!sourceVersionDir) return;
    const tmpDir = `${targetVersionDir}.seeding`;
    // Making sure we don't copy partial data if process interrupted
    // There is a potential race condition here
    // if someone wrote to the cache while we were seeding it
    // but with the immutable design and all that, I'm not super worried
    try {
        _fs.default.mkdirSync(cacheDir, {
            recursive: true
        });
        _fs.default.rmSync(tmpDir, {
            recursive: true,
            force: true
        });
        seedCacheDir(sourceVersionDir, tmpDir);
        _fs.default.renameSync(tmpDir, targetVersionDir);
        _log.info(`Seeded Turbopack cache from ${sourceVersionDir}.`);
    } catch  {
        _fs.default.rmSync(tmpDir, {
            recursive: true,
            force: true
        });
        _log.warn(`Failed to seed Turbopack cache from ${sourceVersionDir} to ${targetVersionDir}.`);
    }

三个设计选择：

  • 版本目录隔离：缓存写在 <distDir>/cache/turbopack/<version> 下，version 来自 getTurbopackCacheVersion()。内核二进制或缓存格式变了，新版本自然落在一个空目录，不会读到旧格式
  • 只在空目录上种：dirHasEntries(targetVersionDir) 为真就放弃。种子缓存永远不会覆盖一份正在被写的目标缓存
  • 临时目录 + rename：先种到 <target>.seeding，成功后再原子改名。进程中断只会留下一个临时目录，清理掉即可，不会产生半份可被读取的缓存

更关键的是文件的写法。同一个文件里，缓存文件按后缀分成两类：

  • .sst、.blob、.meta、.del 是不可变文件：种缓存时用硬链接（linkSync）共享 inode，说明内核从不原地修改它们
  • CURRENT、LOG 这类可变或未知文件：复制一份，保证各自有独立 inode

.del 的存在尤其能说明问题：删除不是「改旧文件」，而是写一个删除标记，再让新版本覆盖。不可变设计换来的是无锁读取、崩溃后仍能读到一致快照；代价是磁盘上会积累旧版本，需要靠压缩/回收来清理。

③ Dev 下的两条增量路径：partial 与 restart ​

开发服务器把内核的 HMR 事件直接接进 Node 运行时：

源码对照 · next/dist/server/dev/hot-reloader-turbopack.js · L151–L208
js
function setupServerHmr(project, { reEvaluateAllModulesExpensive, onApplied }) {
    async function runSubscription() {
        const subscription = project.allHmrEvents(_swc.HmrTarget.Server);
        // Subscribing immediately emits one event describing the current state.
        // There's no previous state to diff it against, so it never carries anything
        // to apply. Drop it; real updates start with the second event.
        await subscription.next();
        for await (const result of subscription){
            const update = result;
            // A 'restart' from the wire protocol means the update can't be applied
            // incrementally, so we must fully re-evaluate all chunks from disk. This
            // clears the module cache and notifies browsers to refetch RSC.
            const requiresFullReEvaluation = update.type === 'restart';
            if (requiresFullReEvaluation) {
                await reEvaluateAllModulesExpensive();
                continue;
            }
            if (update.type !== 'partial') {
                continue;
            }
            // `EcmascriptMergedUpdate` is the only instruction the Node.js runtime
            // knows how to apply; `ChunkListUpdate` is browser-only. Anything else is
            // unknown to us, so ignore it rather than evicting the module cache.
            const instruction = update.instruction;
            if (!instruction || instruction.type !== 'EcmascriptMergedUpdate' && instruction.type !== 'ChunkListUpdate') {
                throw Object.defineProperty(new Error(`[Server HMR] unreachable: unexpected update instruction type ${instruction.type}`), "__NEXT_ERROR_CODE", {
                    value: "E1460",
                    enumerable: false,
                    configurable: true
                });
            }
            // No handler registered yet (before first request, or right after
            // reEvaluateAllModulesExpensive()) — nothing live to update, so skip
            // until the next request.
            const handlers = globalThis.__turbopack_server_hmr_handlers__;
            if (!handlers || handlers.size === 0) {
                continue;
            }
            if (typeof __turbopack_server_hmr_apply__ === 'function') {
                try {
                    __turbopack_server_hmr_apply__(update);
                } catch  {
                    // A matching runtime tried the apply and threw. Evict require.cache
                    // so the next request loads fresh, then skip onApplied. (A no-match
                    // update is a no-op and does not throw.)
                    await reEvaluateAllModulesExpensive();
                    continue;
                }
                const updatedChunkPaths = collectUpdatedChunkPaths(instruction);
                // An empty partial only advances the version state (e.g. the seed
                // transition or a new endpoint); nothing changed on disk, so don't
                // invalidate manifests or ping browsers to refetch RSC.
                if (updatedChunkPaths.length > 0) {
                    await onApplied(updatedChunkPaths);
                }
            } else {
                await reEvaluateAllModulesExpensive();
            }

这段代码把「增量」拆成两种截然不同的结果：

  • partial：尝试调用 __turbopack_server_hmr_apply__(update)，把变更应用到已经加载的模块。EcmascriptMergedUpdate 是 Node 运行时唯一认识的指令；ChunkListUpdate 是浏览器侧的东西
  • restart：协议层面已经判定这次变更无法增量应用，于是 reEvaluateAllModulesExpensive() 清掉模块缓存、从磁盘重新求值
  • apply 失败也回退到全量：只要运行时抛错，就清 require.cache，下次请求重新加载。这条兜底比「想办法局部修补」更可靠
  • 空的 partial 不触发失效：updatedChunkPaths.length === 0 时只推进版本状态，不失效 manifest，也不通知浏览器重取 RSC

这里要区分两张「缓存」：构建图可以被增量更新，但 Node 的模块缓存不一定能。图更新成功而模块缓存无法应用时，Next 选择全量重求值，而不是让两边状态分叉。

④ 配置变更没有增量路径 ​

.env、tsconfig.json、jsconfig.json 这类文件不在某条依赖边上，而是影响整个项目的解析与注入环境。Hot reloader 对它们的处理是完全失效：

  • 清掉所有 entrypoint 的 require.cache
  • clearAllModuleContexts() 清空模块上下文
  • 向浏览器广播 SERVER_COMPONENT_CHANGES

这不是实现偷懒，而是语义决定的：defineEnv、路径别名、环境变量会改变大量模块的编译结果，任何「只失效一部分」的做法都可能留下新旧混合的图。与其猜哪条边受影响，不如整体作废。

⑤ 失效还要传进数据缓存：hmrHash ​

构建图的失效只解决「模块要不要重编」，'use cache' 的数据缓存还需要另一个信号：

注释把边界写得很清楚：

  • 只有真正的重编译会推进 hmrHash；页面 reload 与配置失效都不推进，所以同一个版本内多次请求拿到的值稳定
  • 未编辑时也返回 "0"，而不是 null。这样 'use cache' 的键在任何请求里都带着一个稳定分量，不会出现「首编辑前后键结构不同」的情况
  • 它最终进入 use cache 的键：请求元数据里的 hmrRefreshHash 会被拼进缓存键，因此编辑代码后旧条目自然不再命中

还有一个容易忽略的接线：app route 在 Dev 下的 HMR 订阅主要目的不是刷新浏览器，而是推进这个哈希。路由处理函数没有可重取的 RSC，订阅只为了让它的 'use cache' 条目在编辑后失效。

⑥ 收益、代价与边界 ​

  • 收益：CI 重复构建可以复用磁盘缓存；Dev 长会话靠内存回收与增量应用把内存压住；构建图与数据缓存各自有明确的失效信号，不靠「全量重启解决一切」
  • 代价：缓存目录会增长，依赖压缩与回收；不可变文件换来无锁读取，也换来磁盘占用；配置类变更只能全量失效，构建会明显变慢
  • 边界：next/dist 能调的只有开关，图的节点、边、命中率都在内核里；持久化缓存是正确性优先的——它不会因为「看起来一样」就命中，版本、配置、依赖记录任何一项不匹配都会退化成重编。CI 上共享 .next/cache 时，缓存键至少要覆盖 lockfile、Next 版本与会影响构建的环境；不要手工编辑缓存目录，也不要把它当成可提交的产物

小结 ​

  • Next 编排层只决定开关：持久化缓存、依赖追踪、内存回收、压缩跳过与 worktree 种子，图本身在 Turbopack 内核
  • 种子缓存按版本目录隔离，且只写进空目录；临时目录 + rename 保证不会读到半份缓存
  • .sst/.blob/.meta/.del 是不可变文件，硬链接共享；CURRENT/LOG 才复制
  • Dev 的增量有 partial 与 restart 两条路，apply 失败一律回退到全量重求值
  • 配置类变更没有增量路径，必须清模块缓存、清模块上下文并通知浏览器
  • hmrHash 只在真正重编译时推进，并进入 'use cache' 的键；构建图缓存与数据缓存是两套失效机制
