从一次点击和一次后退说起 ​

点一个站内链接，地址栏立刻变成目标 URL，内容却晚了几十毫秒才接上；按后退键时，上一页几乎在同一帧恢复，没有骨架屏，也没有网络往返。

这两个现象属于同一条软导航生命周期的两端：前进是「查预取状态，能复用就复用，不能就补一次请求」；后退是「从另一张表里读已经渲染过的结果」。把它们连起来看，EntryStatus 这个四态枚举就不只是缓存字段，而是一台真正的状态机。

① 导航入口先查状态，而不是先发请求 ​

navigate 的硬导航分支之外，真正干活的是 navigateImpl：

这里有三条路径，值得逐一对照：

  • Fulfilled：缓存里有一棵完整的路由树，直接走 navigateUsingPrefetchedRouteTree。这就是「点击时不需要网络」的来源
  • Rejected：不是「没有数据」，而是「这条路由的预取被明确否定了」。代码刻意不为它构造 optimistic route，因为拒绝可能来自基于 search params 的 rewrite 或 redirect；猜一棵树反而会渲染错页面
  • null 或其它状态：没有可用的预取，走 navigateToUnknownRoute，由服务端在一条动态响应里同时给出结构与数据

注意 optimistic route 只在 route === null 或状态不是 Rejected 时才尝试。这是一个很实用的边界：负缓存也要被尊重，否则「猜错再重试」会把一次错误放大成两次渲染。

四个状态的含义不是 HTTP 语义，而是缓存条目的生命周期：

状态含义谁会产生
Empty条目已创建，但请求还没发起createDetachedSegmentCacheEntry / 路由条目占位
Pending请求在途，条目带 promise 与阻塞任务预取调度器真正发起请求前
Fulfilled数据可用，带 rsc、staleAt、isPartial响应处理或 BFCache 命中
Rejected明确失败或取消，但仍有 staleAt请求失败、取消或服务器拒绝

Rejected 带 staleAt 这一点常被忽略：它意味着拒绝不是永久的，条目过期后仍可重新尝试。状态机因此不是「失败即终点」，而是「失败也要有过期时间」。

这段代码做了四件事：

  • 状态改为 Pending，并记录这次请求的 fetchStrategy
  • Full 策略把 isPartial 置为 false：完整响应到达后，导航请求可以安全地省略这一段，不必重复取
  • 在发请求前写入 version：下一次缓存版本递增时，这个条目会「事实上被驱逐」。写在请求前而不是响应后，是为了保证版本一定早于服务端读数据
  • 挂上阻塞任务（测试模式下还有导航锁）：后续的 fulfillSegmentCacheEntry 或 rejectSegmentCacheEntry 会 resolve promise 并 pingBlockedTasks，所以等待者不需要轮询状态

这也是「预取状态机」最容易被误解的地方：它不是靠定时器检查状态，而是靠阻塞任务 + promise 推进。状态字段只是给读取方做分支判断用的。

④ 未命中时，一次动态请求当两次用 ​

没有预取的路由不会先阻塞等预取，而是直接发一条同时包含静态与动态数据的请求：

  • navigateToUnknownRoute 根据 freshnessPolicy 选择 dynamicRequestTree：默认、历史遍历、手势导航只带当前树；水合、刷新、HMR 刷新则要求整条路由
  • 响应若是一个字符串，说明服务端要求 MPA 导航，直接 completeHardNavigation
  • 否则用 convertServerPatchToFullTree 把动态响应伪装成一棵预取树，再走与「预取命中」相同的缓存写入流程
  • 响应里如果带 staticStageData 或 runtimePrefetchStream，还会顺手写进 segment cache，让下一次导航直接命中

所以「未命中」并不是慢路径的全部：这一次请求的产物会被拆成结构、静态段与运行时段，分别落入缓存。第二次访问同一路由时，它已经变成 Fulfilled。

三个字段决定了这次导航的「软」边界：

  • changedPath 决定新的 nextUrl：它描述从旧树到新树哪一段变了，服务端靠它决定拦截路由的行为
  • previousNextUrl 保存的是「取回这份数据时用的 Next-Url」：刷新时要沿用它，才能保持与首次导航相同的拦截语义
  • onlyHashChange 单独建模：只有 hash 变化时，不重新取数，只触发滚动

如果目标不同源、或者服务端返回 MPA 重定向，走的是 completeHardNavigation；如果是历史遍历，则走 completeTraverseNavigation。软导航不是「所有导航都软」，而是「同源 App Router 导航且树可复用」时才软。

⑥ 后退为什么几乎瞬时 ​

后退走的是另一张表：bfcacheMap。它在导航提交后写入 rsc、prefetchRsc、head、navigatedAt 与 dynamicStaleAt，并且：

  • invalidateBfCache 只做一件事：递增 currentBfCacheVersion。版本一换，旧条目整体失效，不需要逐条删除
  • 后退/前进会忽略 staleAt：注释明确写了 back/forward navigation 不看过期时间。理由是用户对「返回上一页」的期待是恢复现场，而不是重新校验
  • BFCache 命中可以直接把 Empty 段升级成 Pending 再同步 fulfill，因为数据已经在内存里，没有真实请求要等

这也解释了为什么后退有时会看到「旧数据」：它不是没刷新，而是设计上优先恢复现场。需要新鲜度的场景应使用刷新或重新导航，而不是依赖后退。

⑦ 收益、代价与边界 ​

  • 收益：预取命中时点击零往返；未命中时一条请求同时完成结构与数据；后退从 BFCache 恢复，不触发网络
  • 代价：segment cache 与 BFCache 都占内存，需要 LRU 与版本驱赶；Rejected 条目会占位到过期；预取可能为永不点击的链接付出带宽
  • 边界：状态机描述的是客户端缓存条目，不是服务端渲染状态；Fulfilled 也不保证数据新鲜，staleAt 仍会触发后台校验。策略分级与优先级调度见源码深潜：预取策略的分级与链接意图调度

小结 ​

  • navigateImpl 先读路由缓存状态：Fulfilled 复用，Rejected 不猜树，缺失才发动态请求
  • EntryStatus 是四态生命周期：Empty → Pending → Fulfilled / Rejected，拒绝也带过期时间
  • 预取在发请求前把条目推到 Pending 并写入 version，等待者靠 promise 与阻塞任务推进，不靠轮询
  • 未命中时一条动态请求同时产出结构、静态段与运行时段，并回写成预取树
  • completeSoftNavigation 用 changedPath、previousNextUrl、onlyHashChange 划定软导航边界
  • 后退走 BFCache，靠版本号整体失效、忽略 staleAt，用「恢复现场」换瞬时体验
