从一次悬停说起 ​

第 6 章的主线是「导航之所以瞬时，是因为内容早就到了」。到了代码层，「早就到了」不是一句形容——它由三段机制拼成：策略分级（这次预取要拿到多完整的内容）、优先级调度（谁先发、谁让路）、缓存落位（拿到的东西存哪儿）。

这一篇顺着 Link 组件的一个 prefetch 属性往下走，看前两段。

function getFetchStrategyFromPrefetchIntent(prefetchIntent) {
    if (process.env.__NEXT_CACHE_COMPONENTS) {
        if (prefetchIntent === 'full') {
            return _types.FetchStrategy.Full;
        }
        // `"auto"`: the default mode, where we will prefetch partially if the link is in the viewport.
        prefetchIntent;
        return _types.FetchStrategy.PPR;
    } else {
        return prefetchIntent === 'auto' ? _types.FetchStrategy.PPR : // data to be prefetched, preserving backwards-compatibility.
        _types.FetchStrategy.Full;
    }

三个信息量很大的点：

  • 刻意排序：档位从 0 到 5 单调递增「完整度」，于是两个缓存条目谁更完整，只需要比较数字——不需要写一堆 if/else
  • 数值不过线：客户端内部的编号从不发给服务端；请求头 next-router-prefetch 的值是另外显式映射的。也就是说，重编号是安全的，但别把数字写进日志或缓存键，那会把内部实现变成外部契约
  • 每档代表什么：StaticShell 是「每段静态预取响应抽出的 App Shell」，能包含的内容少于 RuntimeShell（静态响应装不下依赖 cookie/请求头的内容），更少于具体路径上的 PPR（那里包含预渲染的参数相关内容）；Full 才是完整数据

Intent = 2 的注释值得逐句读：它只分配给最近一次悬停/触碰的那个链接，并且有专门的网络带宽预留；同一时刻只存在一个 Intent 级任务，新 Intent 出现时旧的降级为 Default。

这解释了一个反直觉的现象：把鼠标快速扫过一排链接，并不会让所有预取平等地慢下来——最后停住的那一个会插到最前面，前面的退居默认队列。

  • sortId 单调递增、越大越先处理：重新悬停等价于「取消 + 新建」，但复用了原任务对象，拿到新的 sortId 后跳到同优先级队首
  • task === mostRecentlyHoveredLink ? Intent : priority：被重新悬停的链接即使这次重排给的是低优先级，也维持 Intent——避免「用户明明指回了它，却被降级」的割裂
  • 注释里还留了两个容易误读的细节：fallback-retry 状态刻意不重置（一个任务最多跑一轮重试，反复悬停不会开第二轮）；REVALIDATION_COOLDOWN_MS = 300 的冷却期会阻塞预取任务，等 CDN 把新缓存传播开再发请求

INFO

300ms 冷却的存在说明预取不只要「快」，还要「对」：revalidate 刚发生时，边缘节点可能还在提供旧内容。宁可晚 300ms 再预取，也不要把一份即将过期的数据写进客户端缓存。

⑤ 这套设计的收益与代价 ​

  • 收益：悬停即命中，点击时不需要网络往返——这正是「Instant Navigations」四个字的实现来源
  • 代价：可能预取用户永远不点的内容，消耗带宽与客户端 CPU；出口是 prefetch={false}，以及默认的 auto 只处理视口内的链接
  • 边界：策略决定「拿多完整」，优先级决定「谁先拿」；两者都不管「拿到的东西放多久」——那是客户端缓存与 use cache 的职责（见源码深潜：use cache 的运行时包装与缓存条目）

与章节的对应 ​

本篇的调度链路对应第 6 章的三节：策略分级对应 6.1 基础认知：为什么导航是瞬时的，优先级与冷却对应 6.2 进阶理解：外壳合并、URL 级预取与 Instant Insights，把两者接到真实代码上，则是 6.4 原理篇：手写 Partial Prefetch。

小结 ​

  • prefetch 先归一化成意图（auto/full/none），再映射成策略（PPR/Full/不预取）
  • 六档策略刻意按完整度排序，但编号只在客户端内部比较，从不跨线传输
  • 优先级只有三档；唯一的那档 Intent 保留给最近悬停的链接，并占用专用带宽
  • 调度器用单调递增的 sortId 决定同优先级顺序，且重新悬停会保住 Intent
  • 300ms 的 revalidation 冷却提醒：预取追求的不只是快，还要避免搬运即将过期的数据
