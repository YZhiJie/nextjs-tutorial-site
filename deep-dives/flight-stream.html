Flight 不是 HTML ​

组件篇讲过：Server Component 的输出不是 HTML，而是一份 Flight 载荷——一种可流式传输的、带占位与引用关系的数据序列化格式。本篇要回答一个更底层的问题：这份载荷是在哪里、以什么形式被写进响应流的？

链路可以粗略记成：

这里再一次把调用包进 workUnitAsyncStorage.run(...)：React 渲染过程中任何 cookies()/headers() 等动态访问，都靠这个 ALS 上下文才认得「当前处于预渲染/请求的哪一态」。这与上一篇 use cache 的入口校验是同一个机制。

中段：把每个 chunk 包成 <script> ​

React 交出来的是 Web Stream。Node 侧要把它嵌进 HTML，就要做一层转换——createNodeInlinedDataStream 先写一段引导脚本，再逐块拉取 Flight 数据并包上 <script> 标签：

自测

如果把 Flight 载荷换成等价的纯 HTML 一次性输出，会失去什么？

静态壳与动态洞：postponed state ​

对 PPR 页面，请求里还会带一份 postponedState——它记录了「静态外壳中哪些位置被留成了洞」。渲染时先产出可直接缓存的静态壳；动态洞则在运行时通过相同的内联数据流补入。理解了上面 ShellStatic 阶段的推进，就能把「静态壳 + 动态洞」串成一条线，而不是两个孤立的特性。

小结 ​

  • Flight 是组件树的可流式序列化格式，不是 HTML；HTML 只是它的载体（一层 <script> 包装）。
  • app-render 先推进 ShellStatic 阶段，再调用 renderToReadableStream 生成 Flight 流，调用被 workUnitAsyncStorage.run 包住以携带动态访问上下文。
  • stream-ops 的 createNodeInlinedDataStream 负责把 Web Stream 转成可嵌入 HTML 的内联数据流：先写 bootstrap，再逐块包 <script>。
  • 内联块有明确的类型枚举（bootstrap / data / form state / binary），nonce 则服务于严格 CSP。

想先用眼睛看一遍「外壳先到、数据后到」的效果，可以运行 流式渲染实验；而缓存条目在被序列化之前的长相，见上一篇 源码深潜：use cache 的运行时包装。
