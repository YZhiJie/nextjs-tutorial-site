从一次 POST 说起 ​

第 7 章把 Server Action 讲成「像调本地函数一样调服务端」。但到了网络层，它仍然是一次普通的 POST：带着表单或序列化参数，打回当前页面 URL。真正把「POST 请求」变成「函数调用」的，是 action-handler.js 里的 handleAction——这一篇顺着它走一遍完整调用链。

① 入口：先认出「这是不是一次 action」 ​

handleAction 拿到任何 POST 都会先跑一遍，它的第一件事是分流：

源码对照 · next/dist/server/app-render/action-handler.js · L373–L399
js
async function handleAction({ req, res, ComponentMod, generateFlight, workStore, requestStore, serverActions, ctx, metadata }) {
    const contentType = req.headers['content-type'];
    const { page } = ctx.renderOpts;
    const serverModuleMap = (0, _manifestssingleton.getServerModuleMap)();
    const { actionId, isMultipartAction, isFetchAction, isURLEncodedAction, isPossibleServerAction } = (0, _serveractionrequestmeta.getServerActionRequestMetadata)(req);
    const handleUnrecognizedFetchAction = (err)=>{
        // If the deployment doesn't have skew protection, this is expected to occasionally happen,
        // so we use a warning instead of an error.
        console.warn(err);
        // Return an empty response with a header that the client router will interpret.
        // We don't need to waste time encoding a flight response, and using a blank body + header
        // means that unrecognized actions can also be handled at the infra level
        // (i.e. without needing to invoke a lambda)
        res.setHeader(_approuterheaders.NEXT_ACTION_NOT_FOUND_HEADER, '1');
        res.setHeader('content-type', 'text/plain');
        res.statusCode = 404;
        return {
            type: 'done',
            result: _renderresult.default.fromStatic('Server action not found.', 'text/plain')
        };
    };
    // If it can't be a Server Action, skip handling.
    // Note that this can be a false positive -- any multipart/urlencoded POST can get us here,
    // But won't know if it's an MPA action or not until we call `decodeAction` below.
    if (!isPossibleServerAction) {
        return null;
    }

三个信息量很大的点：

  • 识别靠请求元数据：getServerActionRequestMetadata 从 next-action 头与 content-type 里解出 actionId、isFetchAction、isMultipartAction——客户端 fetch 触发的 action 与 MPA 表单 action 在这里就分开了
  • 早退是常态：isPossibleServerAction 为假时直接返回 null，把请求交还给普通渲染管线。注释坦承这可能是误报——任何 multipart/urlencoded 的 POST 都会走到这里，是不是 MPA action 要等 decodeAction 才知道
  • 静态生成期禁入：构建期预渲染时调 action 是不变量违规，直接抛 E359

② 第一道闸门：origin 与 host 必须对得上 ​

通过分流后，校验的第一站不是参数，而是请求来源：

这是一道刻意的 CSRF 防线：action 是可写的（改数据库、改 cookie），而浏览器表单可以跨域 POST。origin 头的 host 部分必须与 host/x-forwarded-host 一致，否则直接中止——注释写得毫不含糊：「This is an attack」。唯一的例外是 allowedOrigins 白名单，给反向代理后 Host 被改写的部署留了出口。

过了这道闸，响应立刻被钉上 Cache-Control: no-cache, no-store, max-age=0, must-revalidate——action 响应永远不进 HTTP 缓存，这是「可写操作」的必然推论。

③ actionId 怎么找到对应模块 ​

客户端发来的只是一个 ID 字符串，找到真实模块要过一层清单：

源码对照 · next/dist/server/app-render/action-handler.js · L1014–L1039
js
/**
 * Attempts to find the module ID for the action from the module map. When this fails, it could be a deployment skew where
 * the action came from a different deployment. It could also simply be an invalid POST request that is not a server action.
 * In either case, we'll throw an error to be handled by the caller.
 */ function getActionModIdOrError(actionId, serverModuleMap) {
    // if we're missing the action ID header, we can't do any further processing
    if (!actionId) {
        throw Object.defineProperty(new _invarianterror.InvariantError("Missing 'next-action' header."), "__NEXT_ERROR_CODE", {
            value: "E664",
            enumerable: false,
            configurable: true
        });
    }
    const entry = serverModuleMap[actionId];
    if (entry == null) {
        // The proxy throws for malformed IDs and IDs that are missing from the
        // manifest. It only returns undefined when the ID collides with a
        // well-known property name (e.g. `toString`) that the proxy excludes from
        // server reference validation so that framework reflection probes don't
        // throw. Next.js never produces such an ID, so this is almost certainly a
        // probe with a known-bad ID. Repeat the manifest's throw logic here so the
        // caller gets a diagnosable error instead of a `TypeError`.
        throw (0, _serverreferenceinfo.mightBeServerReferenceId)(actionId) ? (0, _manifestssingleton.getActionNotFoundError)(actionId) : (0, _manifestssingleton.getInvalidServerReferenceIdError)(actionId);
    }
    return entry.id;
}

serverModuleMap 来自构建期的 server actions manifest。查不到时分两种报错，区分得很讲究：

  • ID 长得像合法的服务端引用 → ActionNotFoundError，典型原因是 deployment skew：用户页面来自旧部署，action 在新部署里已经不存在
  • ID 连格式都不对（或撞上 toString 这类被代理排除的属性名）→ InvalidServerReferenceIdError，几乎必然是构造的探测请求

另外还有一个多进程细节：如果当前 worker 根本没有这个 action 的模块，请求会被转发给有的 worker（x-action-forwarded 头防止转发环路）。这就是大型部署里「页面 worker 与 action worker 分离」的实现支点。

  • fetch action：next-action 头给出 ID，body 用 decodeReply 还原成参数数组——客户端调 action 时参数是被 encodeReply 序列化成多行 Flight 数据的
  • MPA action：没有 ID 头，action 的标识藏在表单字段里（$ACTION_ID_... 或 $ACTION_REF_... 加描述符），交给 decodeAction 整个解出一个函数。解不出来就说明这只是一次普通 POST，返回 null 交还管线
  • decodeFormState 是 MPA 专属：配合 useActionState，把 action 的返回值转成下一次渲染的表单状态

正式 decodeAction 之前，Next 还会先用 areAllActionIdsValid 预扫一遍 FormData——这段逻辑刻意镜像 React 内部的解码规则，确保每个 $ACTION_ 字段指向的 ID 都在本应用清单里，伪造的引用在解码前就被挡掉。

⑤ 执行：先切 phase，再决定要不要重渲染 ​

真正调函数只有一行 action.apply(null, args)，但包裹它的前后处理才是精髓：

源码对照 · next/dist/server/app-render/action-handler.js · L976–L1013
js
async function executeActionAndPrepareForRender(action, args, workStore, requestStore, actionWasForwarded) {
    requestStore.phase = 'action';
    let skipPageRendering = actionWasForwarded;
    if (args.length > SERVER_ACTION_ARGS_LIMIT) {
        throw Object.defineProperty(new Error(`Server Action arguments list is too long (${args.length}). Maximum allowed is ${SERVER_ACTION_ARGS_LIMIT}.`), "__NEXT_ERROR_CODE", {
            value: "E986",
            enumerable: false,
            configurable: true
        });
    }
    try {
        const actionResult = await _workunitasyncstorageexternal.workUnitAsyncStorage.run(requestStore, ()=>action.apply(null, args));
        // If the page was not revalidated, or if the action was forwarded from
        // another worker, we can skip rendering the page.
        skipPageRendering ||= workStore.pathWasRevalidated === undefined || workStore.pathWasRevalidated === _actionrevalidationkind.ActionDidNotRevalidate;
        return {
            actionResult,
            skipPageRendering
        };
    } finally{
        if (!skipPageRendering) {
            requestStore.phase = 'render';
            // When we switch to the render phase, cookies() will return
            // `workUnitStore.cookies` instead of
            // `workUnitStore.userspaceMutableCookies`. We want the render to see any
            // cookie writes that we performed during the action, so we need to update
            // the immutable cookies to reflect the changes.
            (0, _requeststore.synchronizeMutableCookies)(requestStore);
            // The server action might have toggled draft mode, so we need to reflect
            // that in the work store to be up-to-date for subsequent rendering.
            workStore.isDraftMode = requestStore.draftMode.isEnabled;
            // If the action called revalidateTag/revalidatePath, then that might
            // affect data used by the subsequent render, so we need to make sure all
            // revalidations are applied before that.
            await (0, _revalidationutils.executeRevalidates)(workStore);
        }
    }
}

读这个函数要抓住三件事：

  • phase 切换：执行前 requestStore.phase = 'action'——这让 action 体内的 cookies().set() 合法（渲染期调用会抛错）；finally 里切回 'render'
  • cookie 同步：切回渲染前调 synchronizeMutableCookies，把 action 期间写进可变 cookie 的变更回灌到渲染要读的不可变快照——否则同一次请求里重渲染的页面看不到刚写的 cookie
  • skipPageRendering 的判定：只要 action 没调 revalidatePath/revalidateTag（或请求是转发来的），页面数据不可能变，就跳过重渲染；若调了，finally 里先 executeRevalidates 把失效落实，再渲染

⑥ 响应不是「结果」，是一次重渲染 ​

fetch action 的响应最能体现 Server Action 的设计哲学：

返回值不是裸的 action 结果，而是一次新的 generateFlight：响应体里同时装着 actionResult 和（除非跳过）重渲染后的页面 Flight 数据。客户端收到后一次完成「拿到返回值 + 更新 UI」——这正是第 7 章说的「变更与界面同往返一致」的来源。若 skipPageRendering 为真，还要把挂起的 revalidates 通过 waitUntil 交给运行时，保证响应关闭前失效真正落盘。

INFO

调用链全景：识别（元数据）→ 防线（origin/host）→ 定位（manifest + worker 转发）→ 解码（Flight）→ 执行（phase 切换 + cookie 回灌 + 失效落实）→ 响应（重渲染的 Flight）。每一环都对应第 7 章正文里的一条规则。

自测

action 体内执行了 cookies().set('theme', 'dark')，随后 Next 在同一次请求里重渲染页面。如果省掉 synchronizeMutableCookies 这一步，页面会读到什么？为什么这个动作本身在渲染期是非法的？

与章节的对应 ​

本篇的调用链对应第 7 章的三节：调用方式与序列化对应 7.1 基础认知：Server Action 与数据变更，origin 校验与 cookie 写入规则对应 7.2 进阶理解：安全边界与变更语义，Flight 编解码与重渲染机制对应 7.4 原理篇：手写 Flight 协议与 action 调用。

小结 ​

  • 入口靠请求元数据分流，非 action 的 POST 早退交还渲染管线
  • origin 与 host 不一致即视为 CSRF 攻击；action 响应永远 no-store
  • actionId 经 server actions manifest 解析，查不到时区分 deployment skew 与伪造 ID
  • fetch action 用 decodeReply 还原参数，MPA action 用 decodeAction 解出函数，外加 decodeFormState 承接表单状态
  • 执行夹在 phase 切换里：action 期允许写 cookie，切回 render 前回灌快照、落实 revalidates
  • 响应是一次重渲染的 Flight：返回值与新 UI 同往返抵达，这就是「变更与界面一致」的实现
