从一次构建报错说起 ​

在 next.config 里打开 cacheComponents 之后，某个页面写了 export const instant = ...，构建直接失败，报 E1162：这条路由不能在没有开启 cacheComponents 的情况下使用 instant。看起来只是一句配置校验，但它其实是四层机制里最表层的出口。

再往里走，还有几个更值得追问的现象：

  • 为什么同一个 cacheComponents 开关，会同时影响 instant、prefetch 和 'use cache' 三套语义？
  • 为什么编译后的客户端代码里，相关分支像是不存在一样？
  • 为什么一个「已经预渲染好的页面」，在运行时仍要再跑一次 prerender？

这一篇按「配置折叠 → SWC 转换 → 路由校验 → 运行时边界」的顺序，把这条管线拆开。需要先说明引用层次：next/dist 里能看到的是 Next.js 的编排代码；真正的指令重写发生在 SWC 内部，本篇引用的是传给 SWC 的语义参数与运行时消费这些参数的代码。

这里有三点值得记住：

  • 两个开关不是一回事：__NEXT_CACHE_COMPONENTS 对应 config.cacheComponents，而 __NEXT_USE_CACHE 对应更早的 experimental.useCache。前者是路由级缓存模型，后者只是 'use cache' 指令的能力开关
  • __NEXT_INSTANT_NAV_TOGGLE 是镜像值：它和 cacheComponents 绑定，说明 Instant Navigation 的开关并不独立于缓存模型
  • 常量的意义是死代码消除：这些值以字面量形式注入，打包器可以把 if (process.env.__NEXT_CACHE_COMPONENTS) 的分支直接裁掉。于是「运行时读配置」这件事，在产物里根本不存在

::: warn 这些 __NEXT_* 变量是内部实现细节，不是公开 API。它们会随版本改名字，也不保证在 Edge 运行时可用。Cache Components 的 CacheSignal 甚至在构造时就直接拒绝 Edge 运行时。 :::

这一段信息量很大：

  • 服务端组件与服务端动作分开配置：serverComponents 关心指令与组件边界，serverActions 关心引用 ID 与缓存种类
  • cacheComponentsEnabled 与 useCacheEnabled 同时存在：说明「Cache Components 的整页缓存模型」和「'use cache' 指令」在编译期是两个独立维度
  • hashSalt 与 cacheKinds 只出现在动作侧：'use cache' 函数会被编译成一种特殊的服务端引用；cacheKinds 里的 default、remote、private，以及自定义 cache handler 的名字，都要参与这次转换。运行时的 cache() 包装如何消费这些信息，见源码深潜：use cache 的运行时包装与缓存条目
  • taintEnabled 是另一条安全线：它让 experimental_taintObjectReference 之类的标记在编译期生效，与缓存边界无关，但同样属于「模块级语义」

换句话说，'use cache' 不是运行时才被解析的字符串。SWC 必须先把指令变成带 kind 的引用，后面的运行时才有的可查。

这段代码回答了两个常见困惑：

  • 为什么 instant / prefetch 不能和 'use client' 共存：它们是「服务端段」的配置，客户端模块没有对应的渲染段语义，所以直接抛 E1344 / E1323
  • 为什么没开 cacheComponents 就报错：instant 和 prefetch 都依赖 Cache Components 的预渲染/预取模型；没有这个模型，配置本身没有可执行的语义，于是抛 E1162 / E1322

注意这里的错误是路由级的，而不是模块级的。同名导出在别的文件里可能完全合法；只有把它放到某个 page/layout 的入口上，才构成冲突。这也解释了为什么同一份组件代码换个路由就可能构建失败。

四个动作构成了运行时的边界：

  • PrerenderResumeDataCache 是一块可变缓存：动态渲染期间读到的结果被写进去，供后续的运行时预渲染复用
  • CacheSignal 负责判断「缓存是否已经填完」：它跟踪缓存读取和模块加载，而不是跟踪所有 Promise
  • runtimePrefetchStream 是一条延迟流：可读端直接进入 RSC 载荷，Flight 会惰性序列化它；可写端要等缓存就绪后才有内容
  • 最后的 spawnRuntimePrefetchWithFilledCaches 是 fire-and-forget：它不阻塞当前响应，只是把「填好缓存的运行时预渲染」补进同一条载荷

所以「静态外壳 + 动态孔洞」在代码层的分界，不是某个组件被标记成静态或动态，而是这次渲染里还有没有未完成的缓存读取。外壳可以先发，是因为边界之外的内容不依赖那些读取。

⑤ CacheSignal 的计数为什么值得单独说 ​

CacheSignal 的实现只有一百多行，但语义很讲究：

  • beginRead / endRead 维护一个计数；计数归零并不立刻 resolve，而是先排一个 microtask，再排 setImmediate 与 setTimeout
  • 原因写在注释里：一次缓存 resolve 之后，React 可能在 microtask 或 setImmediate 里继续调度渲染，而新渲染很可能再次读缓存。如果立刻宣布「没有待处理读取」，就会把还没发起的读取漏掉
  • inputReady() 与 cacheReady() 是两种等待：前者允许后续继续追加读取，后者等到当前这批读取真正安定

这也是为什么 Cache Components 不能简单地在 Edge 运行时工作：它依赖 process.nextTick 和 Node 的事件循环顺序，构造时就会对 Edge 抛 E728。

⑥ 收益、代价与边界 ​

  • 收益：外壳的产出不再依赖「整页数据是否到齐」；运行时预渲染可以复用动态渲染刚填好的缓存，Instant Navigation 的「先骨架、后内容」因此有了服务端支点
  • 代价：编译期规则更严，instant、prefetch、'use client' 的组合会被提前拒绝；开启 Partial Prefetching 还会增加一次服务端预渲染和响应体积
  • 边界：cacheComponents 不等于「所有东西都被缓存」。没有显式缓存声明的 IO 仍会在预渲染期变成动态孔洞（见源码深潜：四层缓存在一次 fetch 里的交汇）；'use cache' 依然是显式 opt-in。跨请求续传 postponed state 的机制，则由源码深潜：PPR 的 postponed state 如何跨请求续传负责

与章节的对应 ​

本篇对应第 6 章的三节：6.1 基础认知：为什么导航是瞬时的讲清外壳与动态内容的分工，6.2 进阶理解：外壳合并、URL 级预取与 Instant Insights讲 Partial Prefetching 的开关，6.4 原理篇：手写 Partial Prefetch把这条链路落到可运行的实现。缓存判定本身则对应5.4 原理篇：静态外壳与动态孤岛的判定。

小结 ​

  • cacheComponents 在构建入口被折叠成 __NEXT_CACHE_COMPONENTS 等常量，运行时分支会被死代码消除
  • SWC 侧收到的是 cacheComponentsEnabled、useCacheEnabled、hashSalt、cacheKinds 这样的语义参数，'use cache' 在编译期就变成带 kind 的引用
  • 路由段配置在 page/layout 尺度再校验一次：instant、prefetch 不能与 'use client' 共存，也不能脱离 cacheComponents
  • 运行时边界由「未完成的缓存读取」定义，PrerenderResumeDataCache 与 CacheSignal 共同决定何时启动最终运行时预渲染
  • CacheSignal 归零后仍要绕一圈事件循环，是为了接住缓存 resolve 后新调度出来的读取
  • Cache Components 是缓存模型的开关，不是「自动缓存一切」；显式声明与动态孔洞的规则仍然生效
