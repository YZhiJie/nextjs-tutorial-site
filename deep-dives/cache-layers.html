四层各管什么 ​

第 5 章把缓存讲成四层：请求记忆化（单次渲染内去重）、数据缓存（跨请求的 fetch 结果）、完整路由缓存（预渲染的页面产物）、路由器缓存（客户端的导航片段）。它们分属不同模块，但会在一次 fetch() 里交汇——patch-fetch.js 替换了全局 fetch，每一次调用都要回答四个问题：去重吗？进数据缓存吗？让页面失去静态资格吗？客户端还认吗？

这一篇顺着这个补丁函数往下走，看它如何做前三道题，最后一题留给客户端的 reducer。

① 没有配置时，fetch 默认走向哪 ​

这是最容易答错的一道题。源码里的判定链比文档长得多：

三个要点：

  • 凭证与方法是硬条件：带 authorization/cookie 头、或非 GET/HEAD 方法的 fetch，在 revalidate === 0 的上下文里直接 autoNoCache——这类请求缓了就是事故

预渲染期遇到一个没有任何缓存配置的 fetch，Next 根本不发请求——直接返回一个挂起的 Promise（makeDynamicHangingPromise）。语义很直白：没声明 'use cache' 也没写 revalidate 的数据属于运行时，预渲染阶段算不出来，就把它留成页面上的动态孔洞，等真实请求来了再填。这就是「静态外壳 + 动态孤岛」在 fetch 层的实现。

  • 先加锁再读：incrementalCache.lock(cacheKey) 防止并发请求同时回源——同一 cacheKey 只允许一个请求穿透到上游，其余等锁

⑥ 客户端这一层：refresh 时谁失效、谁保留 ​

服务端的四层里，路由器缓存活在客户端。router.refresh() 时它的处置方式写在一个 reducer 的注释里：

源码对照 · next/dist/client/components/router-reducer/reducers/refresh-reducer.js · L29–L46
js
function refreshReducer(state, action) {
    // During a refresh, we invalidate the segment cache but not the route cache.
    // The route cache contains the tree structure (which segments exist at a
    // given URL) which doesn't change during a refresh. The segment cache
    // contains the actual RSC data which needs to be re-fetched.
    //
    // The Instant Navigation Testing API can bypass cache invalidation to
    // preserve prefetched data when refreshing after an MPA navigation. This is
    // only used for testing and is not exposed in production builds by default.
    const bypassCacheInvalidation = process.env.__NEXT_EXPOSE_TESTING_API && action.bypassCacheInvalidation;
    if (!bypassCacheInvalidation) {
        const currentNextUrl = state.nextUrl;
        const currentRouterState = state.tree;
        (0, _cache.invalidateSegmentCacheEntries)(currentNextUrl, currentRouterState);
    }
    // A full refresh has no HMR generation to cancel.
    return refreshDynamicData(state, _pprnavigations.FreshnessPolicy.RefreshAll, undefined);
}

注释把边界划得很清楚：route cache 保留（「哪些 URL 有哪些 segment」这个结构不会因刷新改变），segment cache 失效（里面的 RSC 数据可能已过时），随后把 refresh 建模成「到当前 URL 的一次导航」重新取数。Server Action 调了 revalidatePath 之后的客户端更新，走的正是这条路——服务端重渲染的 Flight 到达后，替换的是数据，不是结构。

INFO

把四层串起来：同一渲染内的重复 fetch 由记忆化去重（React cache / dedupe-fetch）；跨请求的结果存数据缓存（本篇 ④⑤）；整个页面的预渲染产物是完整路由缓存；客户端导航片段是路由器缓存（本篇 ⑥）。一次 fetch 要不要穿透这四层，由 ①②③ 的判定链决定。

自测

某 fetch 在运行时命中了数据缓存但条目 isStale。当前请求拿到的是旧数据还是新数据？后台那次重取如果失败，用户会看到什么？为什么静态生成期要改成前台等待？

与章节的对应 ​

本篇的判定链对应第 5 章的三节：四层分工与默认行为对应 5.1 基础认知：缓存全景与默认规则，路由级配置、标签与按需失效对应 5.2 进阶理解：revalidate 与缓存标签，动态信号如何否决静态资格对应 5.4 原理篇：静态外壳与动态孤岛的判定。

小结 ​

  • 无配置 + 带凭证/非 GET 的 fetch 自动不缓存；构建期是唯一例外，还要靠数据缓存复用
  • Cache Components 下无配置 fetch 在预渲染期直接变动态孔洞，请求都不发
  • 路由级 fetchCache 与局部配置冲突时直接抛错；force-cache 把缺省 revalidate 抬成无限期
  • 数据缓存读取先加锁防并发穿透，隐式标签让 revalidatePath 能命中相关条目
  • 过期条目走 stale-while-revalidate：旧数据先回，后台重取；静态生成期则前台等新
  • 客户端 refresh 保留 route cache、失效 segment cache——数据可换，结构不动
